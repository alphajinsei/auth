# 番外編：アクセス制御（認可）の来歴

最終更新：2026-11-20

ステップ7（認可）の背景。ステップ4・5で扱った認可は、OAuth の scope（「このアプリに、私の代わりに何をさせてよいか」という委譲の認可）だけだった。この記事は、もう1つの認可、**「この人は、このデータに、この操作をしてよいか」（アクセス制御）**が、どう答えられてきたかを追う。行き着く先は、今の主流の1つである ReBAC（関係にもとづくアクセス制御）と、判断を「モジュール」として外に出す作り。

## 1. 問い：誰が、何に、何をしてよいか

アクセス制御の問いは、昔から形が変わっていない。

> 主体（subject：人やプログラム）が、対象（object：ファイル、文書、行）に、操作（action：読む、書く、消す）をしてよいか

1971年、Butler Lampson が論文「Protection」で、これを**アクセス行列**として整理した。行が主体、列が対象、ます目が許される操作。

| | 給与表 | 議事録 | プリンター |
| --- | --- | --- | --- |
| alice | 読む・書く | 読む | 使う |
| bob | | 読む・書く | 使う |

理屈の上では、この表があれば答えは出る。ただ、主体も対象も何万とあると、表はほとんどが空のまま巨大になり、そのままでは持てない。以後の歴史は、ほぼ「**この行列を、どう畳んで持ち、誰が書き換えるか**」の工夫の歴史になる。

| 畳み方 | 持ち方 | 例 |
| --- | --- | --- |
| 列ごと（対象ごと） | 対象に「誰が何をしてよいか」の一覧を付ける＝ **ACL**（Access Control List） | ファイルの権限 |
| 行ごと（主体ごと） | 主体に「何に何をしてよいか」の札を持たせる＝ **ケーパビリティ** | 鍵、OAuth のアクセストークンも近い |

## 2. ACL と DAC：持ち主が決める（1960年代後半〜1970年代）

最初に広まったのは、対象ごとの ACL。1960年代の Multics がファイルに ACL を付け、1970年代の Unix が「持ち主・グループ・その他 × 読む・書く・実行」の9ビットまで単純化した（`rwxr-x---`）。

ここでの思想は、**持ち主が、誰に許すかを自分で決める**というもの。のちに **DAC**（Discretionary Access Control、任意アクセス制御）と呼ばれる。今の Google Drive の「共有」も、考え方としては DAC。

| 解消した不満 | 残った不満 |
| --- | --- |
| 行列の全体を持たなくても、対象ごとに一覧を付ければ済む | 持ち主の判断次第なので、組織として「この情報は外に出さない」を強制できない（持ち主がうっかり共有したら終わり）。人が増えると、ファイルごとの一覧を誰も管理できない |

## 3. MAC：組織が強制する（1970年代〜1980年代）

軍や政府は、持ち主の判断に任せられなかった。1973年の **Bell–LaPadula モデル**は、人と文書に等級（極秘、秘、…）を付け、「自分より上の等級は読めない（no read up）」「自分より下の等級へは書けない（no write down。機密を下に漏らさない）」を、本人にも変えられない規則として強制した。1985年の米国防総省の基準（TCSEC、通称 Orange Book）が、DAC と **MAC**（Mandatory Access Control、強制アクセス制御）という呼び方を定着させた。

今も、SELinux や AppArmor が MAC の系譜にある（「この Web サーバーのプロセスは、このディレクトリしか触れない」を、root にすら破らせない）。

| 解消した不満 | 残った不満 |
| --- | --- |
| 持ち主のうっかりで漏れない。組織の方針を強制できる | 硬すぎて、普通の会社の業務（部署、プロジェクト、異動）に合わない |

## 4. RBAC：仕事の役割で束ねる（1992年〜）

1990年代の企業システムで困っていたのは、軍のような機密区分ではなく、**人の出入り**だった。人が異動するたびに、何百ものファイルやシステムの権限を1つずつ付け外すのは無理がある。

1992年、NIST の David Ferraiolo と Richard Kuhn が **RBAC**（Role-Based Access Control）を論文にまとめた。思想は、**人と権限の間に「役割（ロール）」を挟む**こと。

```
人 ──(割り当て)──> ロール ──(付与)──> 権限（対象 × 操作）
alice            経理担当            給与表を読む・書く
```

異動したら、人に付けたロールを付け替えるだけでよい。権限の一覧はロールの数だけで済み、監査（「経理担当は何ができるか」）もしやすい。1996年の Ravi Sandhu らの RBAC96 がロールの継承（上位のロールは下位の権限を含む）や職務の分離（同じ人に「発注」と「承認」を持たせない）を整理し、2004年に ANSI の標準（INCITS 359）になった。

普及した理由は、**組織図とそのまま対応する**から。Active Directory のグループ、データベースの `GRANT ... TO role`、AWS や GCP の IAM のロール、Kubernetes の RBAC（2017年に正式）まで、今もいちばん使われているモデル。

| 解消した不満 | 残った不満 |
| --- | --- |
| 人の出入りのたびに、権限を1つずつ付け外さずに済む。組織に合う | **データごとの条件が書けない。**「自分が作ったメモだけ」「この文書を共有された人だけ」を表すには、文書ごとにロールを作るしかない（`doc123-editor`、`doc124-editor`…）。これが**ロールの爆発**（role explosion） |

## 5. ABAC と、判断を外に出す（2000年〜）

ロールの爆発への1つ目の答えが、**ABAC**（Attribute-Based Access Control、属性にもとづくアクセス制御）。ロールの代わりに、主体・対象・状況の**属性**を、**規則（ポリシー）**で照らす。

```
許す if 主体.部署 == 対象.部署 and 操作 == "読む" and 時刻 が 業務時間内
許す if 主体.id == 対象.作成者
```

ロールを何千も作らなくても、規則1行で「自分が作ったものだけ」が書ける。2003年に OASIS が規則の書き方と判断の仕組みを **XACML** として標準にし、2014年に NIST が SP 800-162 で ABAC を整理した。AWS IAM のポリシー（JSON の `Condition`。2011年ごろから）も ABAC の考え方を取り入れている。

この時期に、もう1つ大事な考え方が固まった。**「止める場所」と「判断する場所」を分ける**こと。2000年の RFC 2753（ネットワークの帯域の予約の文脈）が名前を付け、XACML が認可の世界に持ち込んだ。

| 部品 | 役割 | たとえ |
| --- | --- | --- |
| **PEP**（Policy Enforcement Point） | 要求を受けて止める場所。「この人がこれをしたいと言っている。いいか？」と聞き、答えに従う | 改札 |
| **PDP**（Policy Decision Point） | 規則を照らして「許す／許さない」を返す場所 | 運賃の計算 |
| **PIP**（Policy Information Point） | 判断に要る属性を取ってくる場所（人の部署、文書の作成者） | 定期券の情報 |
| **PAP**（Policy Administration Point） | 規則を書いて管理する場所 | 運賃表を決める部署 |

アプリの中に `if (user.role === 'admin')` を散らばらせず、PEP（アプリの各 API）は「聞く」だけ、判断は PDP に集める。これが「認可を**モジュール**として切り出す」ときの基本の形になる。

| 解消した不満 | 残った不満 |
| --- | --- |
| ロールの爆発。データごとの条件を規則で書ける。判断をアプリから切り離せる | **逆引きができない。**「alice が見られる文書を全部出して」に答えるには、全文書に規則を当てるしかない（検索の画面や共有の一覧が作れない）。規則が増えると、誰が何をできるのか人間が読み解けない。属性があちこちのシステムに散らばる |

## 6. ReBAC：関係をたどる（2007年〜、Google Zanzibar 2019年）

2000年代後半、SNS とクラウドの共有が広まると、許可の形が変わった。

- 「alice の**友だち**の**友だち**まで見られる」（SNS）
- 「このフォルダを共有された人は、**中の**文書も見られる」（Google Drive）
- 「**エンジニアのチーム**に入っている人は、このリポジトリに書ける」（GitHub）

どれも、許可が**人と物の関係のつながり**で決まる。ロールで書くと爆発し、ABAC の規則で書くと逆引きができない。2007年に Carrie Gates がこれを **ReBAC**（Relationship-Based Access Control）と名付け、2011年に Philip Fong が形式的なモデルにした。

決定打になったのが、2019年に Google が発表した論文「**Zanzibar: Google's Consistent, Global Authorization System**」。Drive、YouTube、Photos、Calendar、Cloud などの共有と権限を、1つの仕組みでまとめて判断しているという内容で、数兆の関係を持ち、毎秒数百万の判断を、95% が 10 ミリ秒未満で返していた。

### 考え方：関係の「タプル」と、その書き換え規則

Zanzibar は、許可をすべて**「対象 # 関係 @ 主体」**の3つ組（関係のタプル）で持つ。

```
doc:readme#owner@user:alice          alice は readme の持ち主
doc:readme#parent@folder:projects    readme は projects フォルダの中にある
folder:projects#viewer@group:eng#member   eng グループのメンバーは projects を見られる
group:eng#member@user:bob            bob は eng グループのメンバー
```

主体の側に「グループのメンバー全員」（`group:eng#member`）のような**集合**を書けるのが要。そのうえで、関係どうしの**書き換え規則**を、対象の種類ごとに1回だけ書く。

```
doc の viewer ＝ doc の editor ∪ 直接の viewer ∪ (parent の folder の viewer)
doc の editor ＝ doc の owner ∪ 直接の editor
```

「bob は readme を見られるか」と聞かれたら、Zanzibar はこのつながりをたどる：readme の viewer → parent の projects の viewer → eng#member → bob。たどり着いたので「許す」。

| 前のモデルの不満 | ReBAC の答え |
| --- | --- |
| ロールの爆発（RBAC） | 文書ごとのロールを作らない。「この文書の editor」という関係のタプルを1行足すだけ |
| 逆引きができない（ABAC） | 関係はデータ（タプル）なので、逆にたどれる。「alice が見られる文書」「この文書を見られる人」に答えられる（Zanzibar の Expand、後発の製品の ListObjects など） |
| 継承や共有が書きにくい | フォルダ → 文書、チーム → メンバー の継承を、書き換え規則の1行で表せる |
| サービスごとに作りがばらばら | 全サービスが同じ PDP（Zanzibar）に「Check（主体, 関係, 対象）」を聞く。共有の画面も、検索の絞り込みも、同じ答えになる |

RBAC は ReBAC で書ける（「ロール」を「組織 # admin @ 人」という関係にすればよい）ので、ReBAC は RBAC の置き換えではなく、**RBAC を含む、より一般の形**と見るのがよい。

### Zanzibar が解いた、もう1つの難題：一貫性

分散した仕組みで判断すると、**新しい敵の問題**（new enemy problem）が起きる。たとえば、alice が bob を文書の共有から外し、そのあとで文書に秘密を書き足したとする。判断のキャッシュが古いと、bob が「外される前の許可」で新しい秘密を読めてしまう。Zanzibar は、書き込みのたびに時刻の印（zookie）を返し、「少なくともこの時点より新しい関係で判断して」と指定できるようにして、これを防いだ。

## 7. 今の形：判断を専用の仕組みに出す（2016年〜）

Zanzibar は Google の中の仕組みだが、論文をもとに、誰でも使える実装が続いた。

| 系統 | 代表 | 中身 |
| --- | --- | --- |
| ReBAC（Zanzibar 系） | SpiceDB（AuthZed、2021年に公開）、OpenFGA（Auth0／Okta、2022年。CNCF のプロジェクト）、Ory Keto | 関係のタプルを持つ PDP。アプリは Check や ListObjects を API で聞く |
| ポリシー言語（ABAC 寄り） | OPA と Rego（2016年。2021年に CNCF の卒業プロジェクト。Kubernetes の受け入れの判断で広まった）、Cedar（AWS、2023年に公開） | 規則を言語で書き、PDP が評価する。関係を持たない代わりに、何でも条件にできる |

PEP と PDP の間の聞き方そのものを標準にする動きもある（OpenID Foundation の AuthZEN の作業部会。2023年ごろから）。OAuth が「トークンの出し方」を標準にしたように、「許すかどうかの聞き方」を標準にしようとしている。

### 紛らわしい言葉：「認可サーバー」は2つある

| 呼び名 | 何をするか | このリポジトリでは |
| --- | --- | --- |
| OAuth の**認可サーバー**（Authorization Server） | 利用者の同意をもとに、トークンを出す。「このアプリに、私の代わりに何をさせてよいか」（委譲） | auth の `/authorize` と `/token` |
| アクセス制御の **PDP**（SpiceDB、OpenFGA、OPA など） | 「この人は、この対象に、この操作をしてよいか」に、その都度答える | まだない（ステップ7で小さく作る） |

OAuth の認可サーバーは、**どのメモを誰が消してよいかを知らない**。scope は「このアプリはメモを書いてよい」までで、「alice のメモを bob が消してよいか」は、アプリ（か、アプリが聞く PDP）が決める。2つは役割がまったく違い、組み合わせて使う（トークンで「誰が、どのアプリ経由で」を知り、PDP で「この対象にしてよいか」を決める）。

## 8. なぜ広く使われるようになったか

- **RBAC が今も主流なのは、組織図と対応して、人が読めるから。**監査で「経理担当は何ができるか」に答えられる。多くの社内システムや IAM は、これで足りる。
- **ReBAC が広まったのは、共有の時代の許可の形に合ったから。**「共有された人」「フォルダの中身」「チームのメンバー」は、どれも関係。Google が規模と速さを論文で示し、オープンソースの実装が揃ったことで、Google 以外でも選べるようになった。
- **判断を外に出す形が広まったのは、マイクロサービスで同じ判断があちこちに要るから。**サービスごとに `if` を書くと、どこかで食い違う。PDP に集めれば、1か所で直せて、1か所で監査できる。

## 9. まとめ

| | |
| --- | --- |
| 生まれた理由 | 「誰が、何に、何をしてよいか」の表（アクセス行列）は、そのままでは大きすぎて持てない |
| 思想 | 表をどう畳むか。対象に付ける（ACL）、組織が強制する（MAC）、役割で束ねる（RBAC）、規則で計算する（ABAC）、関係をたどる（ReBAC） |
| 解消した不満 | 持ち主任せ（MAC）、人の出入りの手間（RBAC）、ロールの爆発（ABAC、ReBAC）、逆引きと共有と一貫性（ReBAC、Zanzibar） |
| 普及した理由 | RBAC は組織に合い、人が読める。ReBAC は共有の時代に合い、Google が規模を示した。PDP に出す形は、マイクロサービスで判断を1か所に集められる |
| 残った弱点 | ReBAC は関係のデータを PDP に同期し続ける手間がある（アプリの DB と二重に持つ）。ポリシー言語は、書いた規則の正しさを確かめにくい |
| 今の形 | アプリ（PEP）が、専用の PDP（SpiceDB、OpenFGA、OPA、Cedar）に「Check（主体, 操作, 対象）」を聞く。中身は RBAC か ReBAC、または両方 |

ステップ7では、この「今の形」を小さく作る。sample-auth-client を PEP にして、判断を担うモジュール（PDP）を切り出し、関係のタプルで答えさせる。RBAC（auth が渡すロール）は、その中の「組織 # admin」という関係の1つとして表す。

## 10. 筆者の理解

ここまでを読み、質問を重ねたうえで、自分の言葉でまとめたもの（細かい質問と答えは [勉強メモ](../notes/study-notes.md) の「認可」と「認可の来歴（ステップ7）」）。

- 認可処理は、「主体・対象・操作」の組み合わせに対して、特定の組み合わせのみ許可する、ということをいかに平易に整理するか、ということが主題になる。
- **ACL**（Unix の rwx など）
  - 対象の持ち主が、他の主体に対してなんの操作をしてよいか決める仕組み。
- **RBAC**
  - 主体と、権限（対象 × 操作の複合）の間に、ロールという概念を入れて、
  - ロールに権限を付与して、主体をロールに所属させる。
- **ABAC**
  - 主体・対象・操作の組み合わせを、各項目の属性で記述する。
    - 「許す if 主体.部署 == 対象.部署 and 操作 == "読む"」など。
- **ReBAC**
  - 「対象・関係・主体」を表すタプルと、書き換え規則の2種で構成される。
    - タプルの例：`doc:readme#owner@user:alice`（alice は readme の持ち主）
    - 書き換え規則の例：doc の viewer ＝ doc の editor ∪ 直接の viewer ∪（parent の folder の viewer）
      - 「操作」はタプルには持たない。関係（viewer、editor 等）の中で表現される。
  - タプルは、個別の事実を表す。日々の操作で増減する。「alice は readme の持ち主」など。
  - 書き換え規則は、一般の規則であり固定である。
  - この人がこの対象にこの操作を実行可能か？という検証したいステートメントに対して、規則（ここでは書き換え規則）に沿って式変形を行っていって、最終的に個別のタプルだけで言いつくされる状態にして、それでこのタプル群の事実を論拠にステートメントの真偽を判断する、という世界観。記号論理学の考え方に近い。
