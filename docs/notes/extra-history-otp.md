# 番外編：ワンタイムパスワードの来歴

最終更新：2026-11-12

段2（TOTP）の背景。パスワードの来歴は [番外編：パスワードとセッションの来歴](extra-history-password-session.md)。

## 1. 不満：ネットワークを流れるパスワードは盗める（1981年〜1994年）

パスワードの来歴で見た工夫（ハッシュ、ソルト）は、**サーバーに保存されたパスワード**を守るものだった。ところが計算機がネットワークでつながると、別の穴が問題になる。telnet や rlogin は、パスワードを平文のまま流していた。経路の途中で盗み見れば、そのまま使える。

1994年には、インターネットの各所のサーバーに盗聴のプログラムが仕掛けられ、大量のパスワードが集められていることが分かり、CERT が警告を出した。

ここで出てきた発想が、

> 一度流れたものは、二度と使えないようにすればよい。

盗み見られても、それはもう使い終わったパスワードなので、価値がない。これがワンタイムパスワード（OTP）の思想。

### Lamport のハッシュの鎖（1981年）

Leslie Lamport が1981年の論文で示した方法。秘密 `s` に一方向の関数を何度もかけて、鎖を作る。

```
h(s), h(h(s)), ..., h^99(s), h^100(s)
server stores h^100(s)
login 1: user sends h^99(s)  -> server checks h(sent) == stored, then stores h^99(s)
login 2: user sends h^98(s)  -> ...
```

サーバーは「次に来るはずのものを、一方向の関数にかけた値」だけを持つ。盗まれても、そこから次のパスワード（鎖の1つ手前）は計算できない。パスワードの「サーバーは秘密を持たない」という思想を、そのまま「使い捨て」に広げている。これが Bellcore の **S/KEY**（1995年に RFC 1760）になった。利用者は、使い捨てのパスワードを印刷した紙を持ち歩いた。

ただし S/KEY は普及しきらなかった。紙の一覧を持ち歩くのが面倒で、そもそも SSH（1995年）が通信路ごと暗号化して、盗聴の問題を別の方法で解いてしまったから。

## 2. 「持っているもの」としてのトークン（1980年代後半〜2011年）

OTP にはもう1つの系譜がある。RSA の **SecurID**（1980年代後半〜）は、6桁の数字が1分ごとに変わる小さな機械（ハードウェアトークン）で、企業の VPN や銀行で広く使われた。機械とサーバーが同じ秘密（シード）を持ち、現在の時刻から同じ数字を計算する。

ここで OTP の意味が変わる。盗聴の対策から、**「この機械を持っている」ことの証明**、つまり認証の要素の「所持」になった。パスワード（知識）と組み合わせれば、2要素認証になる。パスワードがリスト型攻撃で漏れても、機械がなければ入れない。

| 不満 | 中身 |
| --- | --- |
| 高い | 機械を1人1台配る。電池が切れたら交換 |
| 1社に縛られる | 計算の方法が非公開で、サーバーも RSA の製品でなければならなかった |
| サーバー（と製造元）が秘密を持つ | 2011年、RSA が侵入され、トークンのシードに関わる情報が盗まれた。直後に米国の防衛産業の Lockheed Martin が、それを使ったとみられる攻撃を受け、RSA は数千万個のトークンを交換した |

最後の点は、パスワードとの大きな違いを示している。パスワードは、サーバーがハッシュしか持たなくても照合できる。OTP は、**サーバーも同じ秘密から同じ数字を計算する**ので、秘密そのものを持っていなければならない（共有の秘密、shared secret）。サーバーが破られれば、全員分が漏れる。

## 3. 公開の規格へ：HOTP と TOTP（2004年〜2011年）

1社に縛られる不満から、2004年に業界団体 OATH（Initiative for Open Authentication）ができ、計算の方法を公開の規格にした。

| 年 | 規格 | 中身 |
| --- | --- | --- |
| 2005 | **HOTP**（RFC 4226） | `HMAC-SHA1(秘密, カウンタ)` から6桁を切り出す。ボタンを押すたびにカウンタが1つ進む |
| 2011 | **TOTP**（RFC 6238） | カウンタの代わりに「今の時刻 ÷ 30秒」を使う。HOTP そのものに、時刻を入れただけ |

計算は短い。

```
counter = floor(unix_time / 30)
mac     = HMAC-SHA1(secret, counter as 8-byte big-endian)   # 20 bytes
offset  = mac[19] & 0x0f                                     # last 4 bits choose where to cut
code    = (mac[offset..offset+3] as 31-bit integer) mod 10^6 # 6 digits
```

- **HMAC** は、鍵を知っている人だけが作れるハッシュ。秘密を知らない人には、次の6桁が予測できない。
- **最後の4ビットで切り出す位置を決める**（dynamic truncation）のは、20バイトのどこから取っても偏りが出ないようにするため。
- HOTP のカウンタは、機械とサーバーで数がずれる（ボタンを押しただけで使わなかった、など）。時刻にすると、ずれるのは時計だけになり、合わせやすい。前後1つ（±30秒）の幅を許すのが一般的。

規格が公開されたことで、誰でもサーバーと機械（アプリ）を作れるようになった。auth が自分で TOTP を実装できるのも、このおかげ。

## 4. 普及の決め手：スマートフォンと QR コード（2010年〜）

規格だけでは普及しない。機械を配る費用の壁が残っていた。これを壊したのが **Google Authenticator**（2010年）。Google は、中国からの大規模な侵入（Operation Aurora、2010年）が明らかになった年に、Gmail の2段階認証を一般に開放し、そのための無料のアプリを出した。

- 機械を配らなくてよい。**すでに誰もが持っているスマートフォン**がトークンになる。
- 登録は **QR コード**を読むだけ。中身は `otpauth://totp/発行者:ユーザー名?secret=BASE32の秘密&issuer=発行者` という URL で、Google が決めた書き方が事実上の標準になった。どの認証アプリも同じ QR を読める。
- 計算は公開の TOTP なので、どのサービスでも同じアプリが使える。

**「公開の規格」×「誰もが持つ端末」×「読むだけの登録」**がそろって、TOTP は消費者向けにも広がった。パスワードの来歴で見た「導入しやすさ」の壁を、所持の要素として初めて越えた例と言える。

## 5. 横道：SMS のワンタイムパスワード

同じ時期、銀行などは**SMS で6桁を送る**方式を広く使った。アプリを入れる必要すらなく、導入しやすさでは最強だった。しかし弱点が知られていく。

- **SIM スワップ**：携帯会社の窓口をだまして、被害者の電話番号を攻撃者の SIM に移す。以後の SMS は攻撃者に届く。
- **SS7 の悪用**：携帯の網どうしの古い制御の仕組みを悪用して、SMS を横取りする。2017年にドイツの銀行の口座から、この方法で預金が抜かれた。

NIST は2016年の案で SMS を「非推奨」とし、2017年の確定版では「制限付き」の扱いにした。今は「ないよりはまし」の位置づけ。

## 6. OTP の限界：フィッシングには弱い

TOTP でも防げないものがある。偽のログイン画面に、パスワードと6桁を入れさせ、**その場で**本物のサイトに中継する攻撃（リアルタイムのフィッシング）。6桁は30秒の間は有効なので、間に合ってしまう。2017年には、これを自動で行う道具（Evilginx）が公開された。

人間が数字を読み写す限り、「どのサイトに入力しているか」を確かめるのは人間の目になる。人間は偽のドメインを見分けられない。この限界を、**仕組みでサイトを見分ける**ことで越えたのが FIDO2・パスキー（段3）。

## 7. まとめ

| | |
| --- | --- |
| 生まれた理由 | ネットワークを平文のパスワードが流れ、盗聴で集められた |
| 思想 | 一度流れたものは、二度と使えないようにする。のちに「持っているものの証明」（所持の要素）へ |
| 解消した不満 | 盗聴とリプレイ。パスワードだけの認証の弱さ（リスト型攻撃）。のちに、1社に縛られた高価なトークン（→ 公開の HOTP・TOTP） |
| 普及した理由 | 公開の規格、誰もが持つスマートフォン、QR を読むだけの登録 |
| 残った弱点 | サーバーが秘密そのものを持つ（共有の秘密）。リアルタイムのフィッシングに弱い |
| 今の形 | TOTP（SHA-1、6桁、30秒）、前後1つの幅、同じコードの再利用を拒む、回数制限、秘密を暗号化して保存 |

段2の実装は、表の最後の行をなぞる。「サーバーが秘密を持つ」弱点にどう向き合うか（暗号化して保存するか）も、この段で決める。
