# 番外編：引換券を挟むという型

最終更新：2026-11-15

ステップ4の認可コード（[4-oidc.md](../steps/4-oidc.md)）から出てきた問い：「一時的な引換券を挟むのは冗長に感じる。どういうときに、この方式を思いつけばよいのか」。認証に限らず、IT にも限らず使える型として整理する。

## 1. 認可コードが引換券である理由

1回で済むはずの受け渡しを2回に分けるので、引換券はそれ自体がコスト（往復が1回増える、預かる側に記録が要る、期限の管理が要る）。それでも選ぶのは、**1つの道では満たせない条件が重なったとき**。認可コードの場合：

| 理由 | 中身 |
| --- | --- |
| 表の道は漏れやすい | リダイレクトの URL は、履歴、Referer、アクセスログ、拡張機能、スマホのほかのアプリに残る |
| 利用者を巻き込める道は、表しかない | ログインや同意の画面を見せられるのはブラウザだけ。裏の通信には利用者がいない。表は省けないが、表だけでは足りない |
| 2つの道をつなぐ札が要る | 表の通信と裏の通信は別の接続。「さっきブラウザで同意したのは、今 `/token` に来たこの要求のことだ」と結び付ける照合の番号が要る |
| 相手の確認を、受け取りの時まで遅らせる | リダイレクトでは、受け取る相手を確かめられない。確かめられるのは、裏の通信で client_secret を見せてもらう時だけ |
| 運べる大きさ | URL には長さの限りがある。ID トークン（JWT）は長くなりやすい |
| 中身を運び手に見せない | トークンがブラウザを通らないので、ページの JavaScript（XSS）や拡張機能に見られない |
| 一度きりで、異常に気づける | 同じコードが2回来たら、どこかで盗まれている。仕様は、そのとき出したトークンも取り消すよう勧めている |

## 2. いつ引換券を挟むか

品物（価値のあるもの、権限、データ）を渡そうとして、次のどれかに当てはまったら、引換券を考える。

1. **運ぶ道は信用できるか。**途中で見られる・残る・横取りされるなら、品物ではなく札を運ばせる。
2. **渡す時点で、受け取る相手を確かめられるか。**確かめられないなら、確かめられる時（窓口）まで渡すのを遅らせる。
3. **決める時と、渡す時が違うか。**今決めて、あとで（別の場所・別の道で）渡すなら、決めた内容を指す札を出す。
4. **運べる大きさに収まるか。**運び手（URL、QR、SMS、紙）が小さいなら、札だけを運ばせる。
5. **あとで取り消したいか。**札なら、手元の記録を消すだけで無効にできる。

逆に、道が信用でき、その場で相手を確かめられ、すぐ渡せるなら、引換券は要らない。冗長なだけになる。

引換券に付ける性質も、問いから決まる。

| 性質 | どの問いから | 認可コードでは |
| --- | --- | --- |
| 推測できない（長い乱数） | 1 | 32バイト |
| 短命 | 1・3 | 60秒 |
| 一度きり | 1・5 | 取り出したら消す |
| 受け取りに本人確認を求める | 2 | client_secret |
| 札を出した相手と、受け取りに来た相手が同じか | 1・2 | PKCE（code_verifier） |

## 3. 似た例

### IT の中

| 例 | 札 | 品物 | 当てはまる問い |
| --- | --- | --- | --- |
| ステップ1のセッション ID | Cookie の乱数 | サーバーの DB にある「誰がログイン中か」 | 1・5 |
| ステップ3の challenge の Cookie | `__Host-webauthn` の乱数 | DB の challenge | 2・3 |
| パスワード再設定のメール | メールのリンクの一度きりのトークン | 「パスワードを変えてよい」という権限 | 1・3（メールは漏れやすい） |
| ネットの決済（PayPal、Stripe Checkout など） | 決済画面から戻るときの ID | 決済の確定。店のサーバーが裏で決済会社に確定を頼む | 1・2（OAuth とほぼ同じ形） |
| 非同期の API（`202 Accepted`） | ジョブの ID | 時間のかかる処理の結果。あとで取りに行く | 3 |
| メッセージキューの Claim Check パターン | 置き場所への参照 | 大きなデータ。キューには参照だけを流す | 4 |
| OS のファイル記述子 | 小さな番号（3、4…） | カーネルの中のファイルの実体。プロセスは直接触れない | 1・5 |
| Kerberos のチケット | チケット | サービスへのアクセス | 2・3 |

### IT の外

| 例 | 札 | 品物 | OAuth との対応 |
| --- | --- | --- | --- |
| **宅配の不在票** | 郵便受けの不在票 | 荷物 | 一番近い。郵便受け（ブラウザ）は誰でも覗ける。窓口（`/token`）で身分証（client_secret）と照らして渡す。保管期限（60秒）、受け取ったら終わり（一度きり） |
| クローク、手荷物の預かり | 番号札 | コート、スーツケース | 預けた時点で中身が決まり、札と引き換え |
| 線引小切手 | 小切手 | お金 | 窓口で現金に換えられず、口座への入金しかできない。盗まれても使いにくい（client の認証が要るのと同じ） |
| 船荷証券 | 証券 | 船の積み荷 | 品物は船で運び、権利だけを書類で先に送る（道を分ける） |

## 4. 対になる型：参照か、値か

引換券は「**参照**を渡す」型。もう1つ、「**署名した値**を渡す」型がある（JWT、署名付きの証書）。

| | 参照（引換券） | 値（署名付きの証書） |
| --- | --- | --- |
| 例 | 認可コード、セッション ID | ID トークン、JWT のアクセストークン、パスポート |
| 預かる側の記録 | 要る | 要らない（署名を確かめるだけ） |
| 取り消し | 記録を消せば即座に | 難しい（期限まで有効） |
| 漏れたとき | 中身は漏れない | 中身が読める |

OAuth・OIDC は両方を使っている。表の道ではコード（参照）、裏で受け取るのは ID トークン（値）。ステップ5では、アクセストークンを参照にするか値にするかを比べる。
