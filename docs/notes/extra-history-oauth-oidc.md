# 番外編：OAuth 2.0 と OpenID Connect の来歴

最終更新：2026-11-15

段4（OIDC）と段5（アクセストークン）の背景。ここまでの段（パスワード、OTP、パスキー）は「auth の前にいるのは誰か」を確かめる話だった。この記事は、**確かめた結果を、ほかのアプリにどう渡すか**、そして**アプリに、利用者の代わりに何をさせてよいか**の話。用語は [番外編：OAuth・OIDC の用語](extra-auth-terms.md)、分野の地図は [番外編：認証・認可の全体像](extra-auth-overview.md)。

## 1. 不満：パスワードを渡していた時代

2000年代の半ば、Web のサービスが増えるにつれて、2つの不満が大きくなった。

**1つ目：サイトごとにアカウントを作る。**新しいサービスを試すたびに、ユーザー名とパスワードを作る。パスワードの来歴で見たとおり、人間は同じパスワードを使い回し、1つのサイトが漏れると、ほかのサイトも破られる。

**2つ目：ほかのサービスに、自分のパスワードを渡す。**SNS が「友だちを探す」機能を作ったとき、よく使われたのは次のやり方だった。

```
SNS: 「Gmail のアドレス帳から友だちを探します。Gmail のメールアドレスとパスワードを入れてください」
SNS のサーバーが、利用者のふりをして Gmail にログインし、アドレス帳を読む
```

これを **password anti-pattern** と呼ぶ。問題は明らかだった。

| 問題 | 中身 |
| --- | --- |
| 渡しすぎる | アドレス帳を読ませたいだけなのに、メールを読む・送る・パスワードを変える、まで全部できてしまう |
| 取り消せない | その SNS だけ止めたくても、パスワードを変えるしかない（ほかに渡したサービスも全部止まる） |
| 守り手が増える | パスワードを預かった SNS が漏らせば、Gmail が破られる |
| 利用者に悪い習慣を教える | 「よそのサイトに、メールのパスワードを入れてよい」と学ばせる。フィッシングと見分けがつかない |

> 1つのアカウントで、いろいろなサイトに入りたい（**連携・SSO**）。パスワードを渡さずに、必要な分だけをアプリに任せたい（**委譲**）。

この2つの願いが、別々の道を通って、最後に OpenID Connect で合流する。

## 2. 企業の SSO：SAML（2002年〜2005年）

最初に形になったのは、企業の中の SSO だった。社員が、社内のたくさんの業務システムに、1回のログインで入れるようにしたい。

OASIS という標準化団体が、2002年に **SAML**（Security Assertion Markup Language）1.0 を、2005年に **SAML 2.0** を決めた。

```
1. 社員が業務システム（SP：Service Provider）を開く
2. SP が、ブラウザを会社の IdP（Identity Provider）へリダイレクトする
3. IdP でログインする（社内のパスワードなど）
4. IdP が「この人は山田さん。いつ、どうやってログインした」という**アサーション**（XML）に署名し、
   ブラウザに持たせて SP へ POST させる
5. SP は、IdP の公開鍵で署名を確かめ、山田さんとして受け入れる
```

骨格は、段4で作る OIDC とほとんど同じ。**IdP がログインの結果に署名し、ブラウザ経由で届け、受け手が署名を確かめる。**

SAML は企業で広く使われ、今も現役（Microsoft 365、Google Workspace、Salesforce などの企業向けの SSO）。ただ、一般の Web には広がらなかった。

| 理由 | 中身 |
| --- | --- |
| XML が重い | XML の署名（XML Signature）は、正規化の規則が複雑で、実装を間違えやすい。2012年には、多くの SAML の実装が、署名を付け替える攻撃（XML Signature Wrapping）で破れると発表された |
| 事前の取り決めが要る | IdP と SP が、証明書やメタデータを事前に交換しておく。企業どうしの契約が前提 |
| ブラウザ前提 | スマートフォンのアプリや、API の呼び出しには合わない（SAML が決まった2005年には、スマホのアプリがまだない） |

## 3. 個人の Web の SSO：OpenID（2005年〜2015年）

一般の Web では、別の動きがあった。2005年、ブログサービス LiveJournal の Brad Fitzpatrick が **OpenID** を作った。思想は「**自分の URL が、自分の ID**」。

```
1. あるブログにコメントしたい。ログイン欄に、自分の URL（alice.livejournal.com）を入れる
2. ブログは、その URL のページを見て、Alice の OP（OpenID Provider）がどこかを知る
3. ブラウザが OP へ移り、Alice がそこでログインする
4. OP が「この人は alice.livejournal.com の持ち主だ」と答え、ブラウザ経由でブログに戻す
```

事前の取り決めが要らず、誰でも OP になれ、誰でも RP（Relying Party：OP の答えを信じる側）になれる。中央の管理者がいない分散型の設計で、2007年に **OpenID 2.0** と OpenID Foundation ができ、Yahoo!、Google、Microsoft なども OP になった。

それでも、OpenID は一般の利用者には広がらなかった。

| 理由 | 中身 |
| --- | --- |
| URL が ID だと分からない | 普通の人は、自分の URL を持っていない。「ログイン欄に URL を入れる」が理解されなかった |
| フィッシングに弱い | RP が、偽の OP のログイン画面にリダイレクトしても、利用者は見分けにくい |
| ログインしかできない | 「誰か」は分かるが、その人のデータ（アドレス帳、写真）をアプリが使う方法がない。サービスの側から見ると、導入する理由が弱い |

最後の点が決定的だった。サービスが欲しかったのは「ログイン」だけではなく、「**その人のデータを使わせてもらうこと**」だった。

## 4. 委譲の発明：OAuth 1.0（2006年〜2010年）

2006年、Twitter の Blaine Cook たちは、Twitter の API を OpenID と組み合わせて使う方法を探していた。しかし OpenID には、API へのアクセスを任せる仕組みがない。Twitter、Ma.gnolia（ブックマークのサービス）などの開発者が集まり、2007年12月に **OAuth Core 1.0** を公開した。

OAuth の思想は、よく**バレーキー**（ホテルの駐車係に渡す、運転はできてもトランクは開かない鍵）にたとえられる。

> パスワード（すべての鍵）を渡すのではなく、**用途と期限を限った鍵（トークン）**を、持ち主の同意のもとで渡す。

```
1. アプリが「Twitter に投稿したい」と、利用者を Twitter の同意画面へ送る
2. 利用者は Twitter にログインし、「このアプリに、ツイートの投稿を許しますか」に同意する
3. Twitter がアプリにアクセストークンを渡す
4. アプリはトークンで API を呼ぶ。利用者のパスワードは、アプリに一度も渡らない
```

password anti-pattern の不満が、ここで解ける。

| 不満 | OAuth の答え |
| --- | --- |
| 渡しすぎる | トークンに**範囲（scope）**がある。「投稿だけ」「読むだけ」 |
| 取り消せない | トークンは、アプリごとに取り消せる。パスワードは変えなくてよい |
| 守り手が増える | アプリはパスワードを持たない。漏れるのはトークンだけで、範囲も期限もある |

OAuth 1.0 の特徴は、**リクエストごとの署名**だった。アプリは、API を呼ぶたびに、URL やパラメータを決まった順に並べ、秘密の鍵で HMAC-SHA1 の署名を付ける。当時は HTTPS が今ほど当たり前ではなく、盗聴されてもトークンを使い回されないための工夫だった。

ただし、この署名が開発者を苦しめた。パラメータの並べ方、エンコードの細部を1つ間違えると「署名が合わない」とだけ言われ、どこが違うのか分からない。2009年にはセッション固定の脆弱性が見つかり、OAuth 1.0a に直された。2010年に RFC 5849 になり、同じ年の8月、Twitter は API でのパスワード認証（Basic 認証）を止め、OAuth だけにした。

## 5. 作り直し：OAuth 2.0（2012年）

OAuth 1.0 の不満は、大きく2つあった。

- **署名が難しい。**ライブラリがないと、まず正しく書けない。
- **Web のサーバーのアプリしか想定していない。**スマートフォンのアプリ、ブラウザの中だけで動く JavaScript、サーバーどうしの呼び出しには、うまく合わない。

Microsoft、Google、Yahoo! などが2009年に OAuth WRAP という簡略版を出し、それを土台に IETF で作り直したのが **OAuth 2.0**。2012年10月に RFC 6749（本体）と RFC 6750（Bearer トークンの使い方）になった。

| 変えたこと | 中身 |
| --- | --- |
| 署名をやめる | トークンは **Bearer**（持っている者が使える）。盗聴は HTTPS（TLS）に任せる |
| 役を分ける | 利用者（resource owner）、アプリ（client）、トークンを出す**認可サーバー**、API（resource server）。トークンを出す役と API を分けたので、大きなサービスで作りやすい |
| アプリの種類ごとの流れ（grant type） | 認可コード（サーバーのある Web アプリ）、implicit（ブラウザだけのアプリ）、パスワード（移行用）、client credentials（サーバーどうし） |
| 期限とリフレッシュ | アクセストークンは短命にし、**リフレッシュトークン**で取り直す。漏れたときの被害を短くする |

一方で、OAuth 2.0 は「**規格ではなく枠組み（framework）だ**」と批判された。決めていないことが多く、実装ごとに中身が違う。編集者の1人だった Eran Hammer は2012年に「OAuth 2.0 は地獄への道だ」と書いて編集を降りた。この緩さが、のちに PKCE などの補強を必要とすることになる（8 節）。

それでも、OAuth 2.0 は爆発的に広がった。HTTPS の上で、トークンを `Authorization: Bearer ...` のヘッダーに入れるだけで API が呼べる。どの言語でも、ライブラリなしで書けるほど単純になった。

## 6. ねじれ：OAuth で「ログイン」する

OAuth は**委譲**の仕組みで、「誰がログインしたか」を伝える仕組みではない。それでも、サービスはすぐに OAuth を「ログイン」に使い始めた。代表は「Facebook でログイン」で、2010年に Facebook は新しい API（Graph API）とともに、まだ草案だった OAuth 2.0 を採用し、外のサイトのログインをその上で提供した。

```
アプリ：Facebook に OAuth で「プロフィールを読む」権限をもらう
アプリ：そのトークンで /me を呼び、返ってきた ID を「ログインした人」とみなす
```

これは動くが、穴がある。**アクセストークンは「API を呼んでよい」という証明で、「このアプリのためにログインした」という証明ではない。**

- **トークンのすり替え**：悪いアプリ X が、自分のところに来た利用者のアクセストークンを手に入れる。それを別のアプリ Y の「ログイン」に差し出すと、Y は /me を呼んで「この人だ」と受け入れてしまう。トークンには「誰のために出したか（宛先）」が書いていないから。
- **流儀がばらばら**：「誰か」を取る API（/me、/userinfo、/account）も、返ってくる形も、サービスごとに違う。「Google でログイン」「Facebook でログイン」「Twitter でログイン」を全部作ると、全部別の実装になる。

> OAuth の委譲の仕組みの上に、**「ログインの結果」を、宛先付きで、署名して渡す**部分が要る。

SAML がアサーションでやっていたこと、OpenID がやろうとしたことを、OAuth 2.0 の上でやり直す。それが OpenID Connect。

## 7. 合流：OpenID Connect（2014年）と JWT

OpenID Foundation は、名前は OpenID のまま、中身を OAuth 2.0 の上に作り直した。2014年2月に **OpenID Connect Core 1.0** が最終版になった。

**OIDC と OAuth 2.0 の関係は、兄弟ではなく、上に乗る形**。

```
OpenID Connect   ＝ OAuth 2.0
                   ＋ ID トークン（ログインの結果。署名付き）
                   ＋ /userinfo（利用者の属性を返す API。決まった形）
                   ＋ Discovery（設定を /.well-known/openid-configuration で公開する）
                   ＋ scope の決まり（openid、profile、email）
```

**3つの先輩から、1つずつ借りている。**

| 先輩 | 何をしていたか | 足りなかったこと | OIDC が借りたもの |
| --- | --- | --- | --- |
| SAML | IdP が「誰が、いつ、どうやってログインし、どの SP 宛てか」を書いたアサーション（XML）に署名して渡す | XML の署名が重い。事前の契約が要る。スマホに合わない | **中身**：署名付きの「ログインの結果」。ID トークンは、アサーションを JSON（JWT）で書き直したもの |
| OpenID 2.0 | 事前の契約なしに、誰でも IdP・RP になれる、一般の Web の SSO を目指した | ログインしかできず、導入する理由が弱い。URL を ID にする使い勝手 | **開かれ方**：Discovery と、RP の動的な登録 |
| OAuth 2.0 | IdP に連れて行き、同意をもらい、コードを渡し、裏でトークンに引き換える。すでに広く実装されていた | ログインの結果を渡す決まりがない（6 節） | **運び方**：`/authorize` → 認可コード → `/token`、client_id と redirect_uri の登録 |

OIDC ＝ OAuth 2.0 の運び方 ＋ SAML の中身（を JSON で）＋ OpenID の開かれ方。すでに皆が実装していた OAuth 2.0 の上に乗ったので、OAuth 2.0 に対応したサービスは、少し足すだけで IdP になれた。

名前は OpenID を引き継いだが、OpenID 2.0 とは別物で、互換性もない。Google は2015年に OpenID 2.0 の提供を終え、OIDC に移った。

### ID トークン：6 節の穴をふさぐ

流れは OAuth 2.0 の認可コードの流れそのもので、`scope` に `openid` を入れると、`/token` の応答に、アクセストークンと一緒に **ID トークン**が付いてくる。

ID トークンは、6 節の穴をふさぐように作られている。

| 中身（claim） | 意味 | ふさぐ穴 |
| --- | --- | --- |
| `iss` | 誰が出したか（IdP） | 偽の IdP |
| `sub` | 誰がログインしたか（IdP の中で一意の ID） | 「誰か」の取り方がばらばら |
| `aud` | **誰に宛てたか**（RP の client_id） | トークンのすり替え（宛先が違えば RP が拒む） |
| `exp`、`iat` | いつまで有効か、いつ出したか | 古いトークンの使い回し |
| `nonce` | RP が最初に渡した乱数 | ログインの応答の使い回し |
| `amr`、`auth_time` | どうやって、いつログインしたか | RP が「多要素か」「最近か」を判断できない |

### JWT：ID トークンの形

ID トークンの形は **JWT**（JSON Web Token。「ジョット」と読む）。JSON を base64url にして、署名を付けたもの。

```
ヘッダー（署名の方式、鍵の ID）. 中身（claim の JSON）. 署名
eyJhbGciOiJFUzI1NiIsImtpZCI6IjEifQ.eyJpc3MiOiJodHRwczovL2F1dGguLi4ifQ.MEUCIQ...
```

JWT は、SAML のアサーションと同じ役（署名された「この人はこうだ」という主張）を、XML ではなく JSON でやる。XML 署名の複雑さ（2 節）がなく、URL やヘッダーにも入れやすい。署名の形（JWS）は RFC 7515、鍵の形（JWK）は RFC 7517、JWT そのものは RFC 7519（2015年）。RP は、IdP が公開する鍵の一覧（**JWKS**）で署名を確かめる。

### OAuth 2.0 と OIDC の使い分け：scope に openid を入れるか

「Google でログインしたことをもって、自社サイトのログインの代わりにする」（欲しいのは「誰か」）が OIDC、「自社サイトから Google カレンダーを読ませてもらう」（欲しいのは「データを使ってよい」）が OAuth 2.0。前者は、後者の運び方に、運ぶ荷物（ID トークン）を足して作る。

使い分けるのは「何を頼むか（scope）」で、窓口（`/authorize`、`/token`）も流れも同じ。**`scope` に `openid` が入っていれば OIDC の要求**で、`/token` の応答に ID トークンが付く。

| 頼み方（scope） | 呼び名 | 返ってくるもの | 用途 |
| --- | --- | --- | --- |
| `calendar.readonly` | OAuth 2.0 | アクセストークン（カレンダーの API 用） | カレンダーを読むだけ |
| `openid email` | OIDC | ID トークン ＋ アクセストークン（`/userinfo` 用） | ログインだけ |
| `openid email calendar.readonly` | OIDC | ID トークン ＋ アクセストークン（`/userinfo` とカレンダーの API 用） | 両方を1回の同意で |

ID トークンとアクセストークンは、受け取ったあとの使い道が違う。

| | アクセストークン | ID トークン |
| --- | --- | --- |
| たとえ | 合鍵（API の扉を開ける） | 宛名付きの紹介状（「この人は山田さん。あなた宛てに書いた」） |
| 誰が読むか | API。アプリは中身を読まずに渡すだけ | アプリ（RP）自身。API には送らない |
| 何を言うか | この範囲（scope）の操作をしてよい | 誰が、いつ、どうやってログインしたか。宛先は誰か |

## 8. 補強：PKCE と、セキュリティの最善の慣行（2015年〜）

OAuth 2.0 の緩さ（5 節）は、その後の RFC で少しずつ締められていった。

| 年 | 出来事 | 不満と答え |
| --- | --- | --- |
| 2015年 | **PKCE**（RFC 7636。「ピクシー」と読む） | スマホのアプリでは、認可コードを受け取る URL（カスタムスキーム）を、悪いアプリに横取りされうる。アプリが最初に乱数（code_verifier）のハッシュを渡し、コードを引き換えるときに元の乱数を見せる。横取りしたコードだけでは、トークンに引き換えられない |
| 2010年代後半 | implicit の流れの退場 | ブラウザだけのアプリに、URL の中で直接トークンを渡していた流れ（implicit）は、履歴やリファラーから漏れやすい。認可コード + PKCE に置き換える |
| 2025年1月 | **OAuth 2.0 Security Best Current Practice**（RFC 9700） | 10年分の攻撃と対策をまとめた。すべてのアプリで PKCE を使う、implicit とパスワードの流れは使わない、redirect_uri は完全一致で照らす、など |
| 策定中 | OAuth 2.1 | RFC 6749 と、その後の補強を1つにまとめ直す。認可コード + PKCE が基本の形になる |

PKCE は、もとはスマホのアプリのための仕組みだったが、今はサーバーのある Web アプリでも使うのが推奨。段4でも使う。

## 9. なぜ広がったか

- **大手が IdP になった。**Google、Microsoft、Apple（2019年の「Apple でサインイン」）、LINE などが OIDC の IdP を提供した。RP は、自分でパスワードを預からずに、ログインを任せられる。
- **作るのが簡単になった。**HTTPS の上のリダイレクトと、JSON と、JWT の署名の検証だけ。SAML の XML 署名や、OAuth 1.0 の署名の細部が要らない。Discovery で、IdP の URL を1つ渡せば、ライブラリが設定を全部読みに行く。
- **1つの仕組みで、ログインと委譲の両方ができる。**ID トークンで「誰か」、アクセストークンで「その人のデータを使ってよい範囲」。OpenID 2.0 に欠けていた「導入する理由」が、OAuth の側から来た。
- **スマホのアプリでも使える。**PKCE で、秘密を持てないアプリでも安全に使えるようになった。
- **企業も乗った。**Microsoft Entra ID（旧 Azure AD）、Okta、Keycloak などが、SAML と並べて OIDC を提供し、新しいシステムは OIDC を選ぶことが多くなった。

## 10. まとめ

| | |
| --- | --- |
| 生まれた理由 | サイトごとのアカウントと、パスワードの使い回し（連携の願い）。ほかのサービスにパスワードを渡す password anti-pattern（委譲の願い） |
| 思想 | パスワードを渡さず、用途と期限を限ったトークンを、持ち主の同意で渡す（OAuth）。ログインの結果を、宛先付きで署名して渡す（OIDC） |
| 解消した不満 | 渡しすぎ、取り消せない、守り手が増える（OAuth）。OAuth で無理にログインするときのすり替えと、流儀のばらつき（OIDC）。SAML の XML の重さ、OpenID の「ログインしかできない」 |
| 普及した理由 | 大手が IdP になった。HTTPS・JSON・JWT だけで作れる単純さ。ログインと委譲を1つの仕組みで。PKCE でスマホでも使える |
| 残った弱点 | OAuth 2.0 は枠組みで、選択肢が多く、間違えやすい（Security BCP と OAuth 2.1 で締めている途中）。Bearer トークンは、盗まれたら使える（送り手に結び付ける DPoP などが出てきている） |
| 今の形 | 認可コード + PKCE。ID トークン（JWT、署名、`aud`・`nonce`・`amr`）、JWKS、Discovery、`/userinfo` |

段4の実装は、表の最後の行をなぞる。auth が IdP（OP）として `/authorize` と `/token` を持ち、段1〜3のログインの結果を、ID トークンに署名して demo-app に渡す。
