# 勉強メモ：認証・認可

最終更新：2026-11-19

[ロードマップ](../roadmap.md) を進める中で出てきた疑問と、その答えを積み上げていくメモ。1つの問いに1つの見出しを立てる。答えは、会話の中で説明した内容を、圧縮せずにそのまま残す（あとから読み返して「当時何を理解したのか」が分かるように）。とくに長い話は番外編（`extra-*.md`）に分けて、答えからリンクする。インフラや開発環境の話は、infra リポジトリの [勉強メモ](https://github.com/alphajinsei/cf-infra-playbook/blob/main/docs/notes/study-notes.md)。

## 全体像

### Q. 認証・認可は、どんな小分野に分かれているのか。FIDO2・OAuth 2.0・LDAP はどこに当たるのか

認証・認可と呼ばれるものは、突き詰めると3つの問いに分かれる。

| 問い | 名前 | 例 |
| --- | --- | --- |
| あなたは誰か | 認証（Authentication） | パスワード、パスキー、「Google でログイン」 |
| あなたは何をしてよいか | 認可（Authorization） | 「管理者だけが削除できる」「このアプリに Google カレンダーの読み取りだけ許す」 |
| 誰がいるのか | ID 管理（Identity Management） | 社員の名簿、グループ、退職者の無効化 |

これに、認証の結果を覚えておく仕組み（セッション）が加わる。毎回パスキーを求めるわけにはいかないので、「さっき認証した人だ」という証明を持ち回る。実際の事故は、認証そのものより、このセッションやトークンの扱いで起きることが多い。

細かくは8つの小分野に分けられる（A. 本人確認、B. セッション、C. 連携・SSO、D. 委譲された認可、E. アプリの中のアクセス制御、F. ID 管理・ディレクトリ、G. 機械同士の認証、H. 横断するもの）。興味のある3つは、地図の上では別々の場所にある。

- **FIDO2** は A。本人だとどう示すか、の話。
- **OAuth 2.0** は D。アプリに権限を渡す話で、認証そのものではない。認証にあたるのは、その上に載る OIDC（C）。
- **LDAP** は F。Web のログインの仕組みではなく、名簿を引くプロトコル。

auth は、これらをつなぐ中心になる。名簿を持ち（F）、パスキーなどで本人を確かめ（A）、Cookie でログイン状態を覚え（B）、アプリにトークンを出し（C・D）、アプリはそれを見て権限を判断する（E）。

→ [番外編：認証・認可の全体像](extra-auth-overview.md)

### Q. パスキーと OIDC は組み合わせられるのか。画面はいくつ作ることになるのか

組み合わせられる。というより、担当している場所が違うので、ぶつからない。

- **OIDC** が決めているのは、「IdP がアプリに、ログインしたのは誰かをどう伝えるか」だけ。
- **IdP がその人をどう確かめるか**（パスワード、TOTP、パスキー）は、OIDC の範囲外で、IdP の中の事情。

「Google でログイン」を思い浮かべると分かりやすい。アプリから見えるのは OIDC だけで、Google の画面でパスワードを使ったかパスキーを使ったかは、アプリには関係ない（ID トークンの `amr` という項目で、使った方式を伝えることはできる）。

なので画面は2つの側に分かれる。

- アプリ側（demo-app）：「auth でログイン」のボタンがあるだけ
- IdP 側（auth）：ログイン画面（パスワード／パスキーを選ぶ）、TOTP の6桁の入力、同意画面など

### Q. 「一度人間が画面でログインして、機械用のトークンを払い出す」OAuth を体験するには、CLI を作る必要があるのか

作らなくてよい。これは OAuth の**デバイスコードのフロー**（RFC 8628。`gh auth login` がこれ）。流れは次のとおりで、

1. CLI が認可サーバーに「デバイスコードをください」と頼む
2. CLI が「このコードをブラウザで入れて」と表示する
3. 人間がブラウザでログインし、コードを入れて承認する
4. その間、CLI は認可サーバーに「もう承認された？」と問い合わせ続け（ポーリング）、承認されたらトークンを受け取る

人間がブラウザでログインして承認する部分（3）は、普通のブラウザの流れ（認可コード）とまったく同じ。違うのは最後のトークンの受け取り方だけで、リダイレクトでアプリに戻る代わりに、CLI がポーリングで受け取る。本質は同じなので、自作の CLI は作らず、ブラウザでの流れを深く理解する方を優先した。

### Q. パスキーも、パスワードのように DB に手で入れて作れるのか

できない。パスキーの登録は、ブラウザと認証器（スマホやセキュリティキー）が**鍵ペアを作る一連の手順**（ceremony）そのものだから。秘密鍵は認証器の中で生まれ、外に出ない。サーバーが受け取るのは公開鍵だけなので、サーバー側で勝手に作ることはできない。TOTP も、利用者の認証アプリが秘密を読み取る手順が要る。

ここで大事なのは、**アカウントを作ること**と、**そのアカウントに認証の手段を登録すること**は別、という点。

- アカウントとパスワード：管理用のコマンドで作る（`admin.js create-user`）
- TOTP とパスキー：ログインしたあと、アカウントの画面から利用者自身が登録する

新規登録の画面（誰でもアカウントを作れる経路）とアカウントの回復は、auth を自分のサービス全体の認証基盤にしていくときに必要になるので、[設計](../design.md) の「今後の発展」に残した。

### Q. IdP、OP、認可サーバー、RP、クライアント……用語が多すぎる。何がどう違うのか

分かりにくさの大半は、**同じものが規格ごとに別の名前で呼ばれている**こと。

| 実体 | OAuth 2.0 | OIDC | SAML・一般 | このリポジトリでは |
| --- | --- | --- | --- | --- |
| ログインさせたいアプリ | クライアント | RP（Relying Party） | SP（Service Provider） | demo-app |
| ログインを引き受け、トークンを出すサーバー | 認可サーバー | OP（OpenID Provider） | IdP（Identity Provider） | auth |
| トークンを見て応じる API | リソースサーバー | （UserInfo エンドポイント） | — | auth の `/userinfo` |

- IdP・OP・認可サーバーは、このリポジトリでは全部 auth のこと。言い方が違うのは見ている面が違うから。「ログインした人が誰かを証明する」面を見れば IdP・OP、「トークンを発行して権限を渡す」面を見れば認可サーバー。
- RP は「OP の言うことを信頼（rely）する側」という意味。まさに「IdP がログインしてよいと言っているから、うちにもログインさせよう」という立場。
- OAuth の「クライアント」は**ブラウザではなく、トークンを受け取って使うアプリ**のこと。ブラウザは「ユーザーエージェント」と呼ぶ。最初に一番混乱しやすい点。

→ [番外編：OAuth・OIDC の用語](extra-auth-terms.md)

### Q. ステップ1でデプロイした auth は、IdP と RP がひとまとまりになったアプリなのか

違う。コンテナで動いているのは **IdP（auth）だけ**で、RP（demo-app）はまだどこにも作っていない。

ただしステップ1の auth は、ほかのアプリにログインの結果を渡す機能（OIDC）をまだ持たず、**自分自身へのログイン**しかできない。だから外から見ると普通のアプリと区別がつかない。

Google で言えば、今の auth は accounts.google.com にあたる。Google のアカウントにログインして、自分のアカウントの画面が見られるところまで。「Google でログイン」でほかのサイトに入れる機能はまだない。

| | ステップ1の時点 | ステップ4で足すもの |
| --- | --- | --- |
| auth（IdP） | ログイン画面、auth 自身のセッション、アカウントの画面 | `/authorize`、`/token`、`/userinfo` などの OIDC の窓口 |
| demo-app（RP） | ない | 手元で作り、「auth でログイン」する。のちに別のリポジトリ・別のコンテナ |

ステップ1で作ったログイン画面は、そのまま **IdP のログイン画面**になる。ステップ4で demo-app の「auth でログイン」を押すと、ブラウザが auth のこの画面に飛ばされ、ログインすると demo-app に戻る。`/account` は IdP の中の「自分のアカウントの管理画面」で、ステップ2・3でここに TOTP やパスキーの登録を足す。

FIDO（パスキー）は「本人をどう確かめるか」（A）の方式で、フェデレーション（C）とは別の軸。ステップ2・3はログイン画面に確かめ方を足すステップ、ステップ4はほかのアプリに結果を渡す窓口を足すステップで、ステップ4で初めてフェデレーションになる。

### Q. ID/PW、ID/PW + OTP、FIDO をアカウントごとに自由に試せるようにしたい。アカウントの属性として「どの認証方式に対応しているか」を持つのか

属性（列）としては持たない。**アカウント**と、**そのアカウントに登録した認証の手段**を分け、どの方式でログインできるかは、登録されている手段から決める。Google や GitHub もこの形で、2段階認証を登録したアカウントには、ログインのたびに6桁を求める。

| 登録した手段 | ログインのしかた |
| --- | --- |
| パスワードだけ | パスワード |
| パスワード + 確認済みの TOTP | パスワードのあとに6桁を必ず求める |
| パスキー | パスキーだけで入れる（端末で指紋や PIN を確かめるので、1つで多要素になる） |

- 「対応している」という列を持つと、実際に登録されているものと食い違う心配がある。登録した手段から決めれば、食い違いようがない。
- 利用者は、アカウントの画面で手段を足したり外したりするだけで、方式を切り替えられる。
- デモ用には、方式ごとのアカウント（`demo-password`、`demo-totp`、`demo-passkey`）を管理用のコマンドで作っておけば、人にも見せられる。

「対応している方式は必ず1種類」でもない。1つのアカウントに複数の手段を登録でき、ログイン画面で利用者が選べる（パスワード + TOTP とパスキーの両方を登録した人は、どちらでも入れる）。強さの順は ID/PW < ID/PW + OTP < FIDO で、差を生むのはフィッシングへの強さ。パスキーだけが「偽のサイトでは鍵を使わない」を仕組みで保証する。

今の段階から仕込んだもの：

- TOTP を `users` の列にせず、別のテーブル（`totp_credentials`）にした。ステップ3のパスキーも同じ形の別テーブル（`webauthn_credentials`）になる。パスキーだけのアカウントのために、ステップ3でパスワードを空にできるようにする。
- セッションに、使った方式（`amr`）を記録し、アカウントの画面に出す。

### Q. TOTP 対応のアカウントは、users と totp_credentials の両方に登場するのか。方式の見分けは「totp_credentials にいれば TOTP、users にいれば ID/PW、どちらにもいなければ未登録」というロジックか

前半はそのとおり。アカウントは全員 `users` に1行あり（アカウントそのもの）、TOTP を登録した人だけが `totp_credentials` にも1行ある（そのアカウントに付けた手段）。

ただ、見分けるロジックは「どちらの表にいるかで方式を1つに決める」のではなく、**選ばれた入口ごとに、次に何を求めるかを決める**形になる。

```
「パスワードでログイン」が押された:
  users にいなければ → 失敗（未登録。画面には「どちらかが違う」とだけ出す）
  パスワードを照らす → 違えば失敗
  totp_credentials に確認済みの行があれば → 6桁を求める → 合えば amr = "pwd otp"
  なければ → そのまま完了 → amr = "pwd"

「パスキーでログイン」が押された（ステップ3）:
  パスキーの署名を確かめる → 合えば完了 → amr = パスキーを表す値
```

### Q. sessions の amr には、登録した認証方式を書いておくのか。上のロジックの解釈と一致するのか。amr は何の略か

amr は「登録した方式」ではなく、**「このログインで実際に使った方式」の記録**。

| | 意味 | どこにあるか |
| --- | --- | --- |
| 登録した手段 | このアカウントが**使える**方式 | `users.password_hash`、`totp_credentials`、ステップ3の `webauthn_credentials` |
| amr | このログインで**実際に使った**方式 | `sessions.amr`（ステップ4では ID トークン） |

多くの場合は結果として一致する。ただし、パスキーも登録している人がパスワードで入れば、amr は `pwd otp` になる。amr はロジックの入力ではなく、ロジックを通った結果の記録。

amr は **Authentication Methods References**（認証方式の参照）の略。OIDC の ID トークンの項目として定義され、入れる値は RFC 8176 が決めている（`pwd` パスワード、`otp` ワンタイムパスワード、`hwk` ハードウェアの鍵、`user` 本人の確認（指紋など）、`mfa` 多要素、など）。auth のセッションにも同じ名前・同じ値で記録しておけば、ステップ4で RP に「この人はパスワード + TOTP でログインした」とそのまま伝えられる。RP が「パスキーでログインした人だけ」と求める仕組み（`acr_values`）の土台にもなる。

### Q. sessions.amr が「実際に使った方式」なら、「登録した認証の手段」はどこに持つのか。個別の列は持たず、ロジック側で判断するのか

**認証に使うデータそのものが、登録の印**になっている。「方式の一覧」のような要約の列を別に持たない、という意味。

| 手段 | 「登録している」とは | 置き場所 |
| --- | --- | --- |
| パスワード | パスワードのハッシュがある | `users.password_hash`（ステップ3からは空にできる） |
| TOTP | 確認済みの行がある | `totp_credentials`（`confirmed_at` が空でない行） |
| パスキー（ステップ3） | 公開鍵の行が1つ以上ある | `webauthn_credentials`（1人で複数の端末を登録できる） |

ロジックは、この表を見て判断する。上の問いのロジックの「`totp_credentials` に確認済みの行があれば → 6桁を求める」が、まさに「TOTP が登録されているか」をデータそのもので見ている箇所。

おすすめしなかったのは、`users` に `methods = 'pwd,otp'` のような列を足して、そちらを見る形。TOTP を削除したのに列を直し忘れた、といった食い違いが起きうる。データそのものを見れば、食い違いようがない。

（経緯：「登録した手段から決める」と「sessions に amr を記録する」を同時に説明したので、登録した手段＝ `sessions.amr` と読めてしまった。amr はあくまで、そのログインで使った方式を、セッションと一緒に持っておくもの。）

### Q. （ステップ3を終えて）この先のステップ4（OIDC）は ID のフェデレーション、ステップ5（アクセストークンとリフレッシュトークン）は OAuth 2.0 の話という理解でよいか。OIDC・OAuth 2.0 と FIDO は両立するのか。FIDO は認証しかしていないが、OIDC・OAuth 2.0 で認可の話に移るのか。それとも権限の委譲で、認可とは別なのか。認可をここでやらないなら、これから作る別の Web アプリの側で実装するのか

ほぼその理解。ただし **OIDC は OAuth 2.0 の上に乗っている**ので、きれいには分かれない。

| | ステップ4（OIDC） | ステップ5（アクセストークンとリフレッシュトークン） |
| --- | --- | --- |
| 何をするか | demo-app が「auth でログイン」する | demo-app が、利用者の代わりに API を叩く |
| 受け取るもの | **ID トークン**（誰が、いつ、どうやってログインしたか） | **アクセストークン**（何をしてよいか＝scope）と、その更新用の**リフレッシュトークン** |
| 分野 | C：連携・SSO（ID のフェデレーション） | D：委譲認可 |
| 使う仕組み | OAuth 2.0 の認可コードフロー（`/authorize`、`/token`）＋ ID トークン | OAuth 2.0 そのもの |

OIDC は「OAuth 2.0 の仕組みを使って、ついでに ID トークンも渡す」規格。ステップ4で OAuth 2.0 の骨組みを作り、ステップ5でその「アクセストークンで API を叩く」側を本格的に使う。

**FIDO とは両立する。層が違うので重ねて使う。**

```
利用者 ──（パスワード / TOTP / パスキー）──> auth        A：本人確認（ステップ1〜3）
auth ──（ID トークン。OIDC）──────────────> demo-app    C：連携（ステップ4）
demo-app ──（アクセストークン。OAuth 2.0）──> API         D：委譲認可（ステップ5）
API・アプリの中 ──（この人はこの操作をしてよいか）        E：認可モデル
```

FIDO は「auth の前にいるのは誰か」、OIDC は「その結果をほかのアプリにどう渡すか」。渡す中身にはステップ3の `amr`（`hwk mfa` など）が入るので、demo-app はパスキーに触れずに「パスキーで多要素のログインをした」と分かる。ステップ1〜3は認証（A）だけで、認可はまだ何もしていない。

**「認可」は2つの別のことを指す。**

| | D：委譲認可（OAuth 2.0） | E：認可モデル（RBAC など） |
| --- | --- | --- |
| 問い | 利用者が、**アプリ**に、自分の代わりに何をさせてよいか | **利用者**が、アプリの中で何をしてよいか |
| 例 | 「このアプリに、Google カレンダーの読み取りだけ許す」 | 「この人は管理者なので、ほかの人の記事を消せる」 |
| 表し方 | scope。利用者が同意画面で許す | ロール、権限の表、ポリシー |
| 決める人 | 利用者 | アプリの持ち主（管理者） |

OAuth 2.0 は前者（権限の委譲）で、後者とは別物。scope `write` を委譲しても、「他人の記事まで書き換えてよいか」は scope では決まらない。

**認可モデル（E）は、最終的には各アプリ（API）の側で判断する。**守るデータと、「この記事は誰のものか」「この操作に何の権限が要るか」を知っているのはアプリだから。auth が手伝えるのは判断の材料を渡すところまで（`sub`、`amr`、`scope`、足すならロールやグループ）。判断の規則だけを専用のサービスに集める（ポリシーエンジン。OPA など）構成もあるが、その場合も問い合わせて従うのはアプリ。今のロードマップに E はないので、ステップ5で demo-app を独立させるときに「auth がロールを渡し、demo-app が見て判断する」を小さく足すかどうかを決める。

**理解の確認**：委譲認可（OAuth 2.0）と認可モデルは別物で、今回 auth で触るのは委譲認可。認可モデルは本来アプリの側、今回なら demo-app が決めること。demo-app を独立させるときに、認可モデルも入れる（ロードマップのステップ5に足した）。

「OIDC と OAuth 2.0 は兄弟のようなもの」と言い直したが、1点訂正すると、兄弟ではなく**上に乗る形**。OIDC は OAuth 2.0 の認可コードの流れをそのまま使い、その上に ID トークン、`/userinfo`、Discovery を足した規格（OIDC ＝ OAuth 2.0 ＋ ログインの結果を渡す部分）。→ [番外編：OAuth 2.0 と OpenID Connect の来歴](../history/4-oauth-oidc.md) の 7 節

### Q. 「Google でログインしたことをもって自社サイトのログインの代わりにする」ユースケースと、「自社サイトから Google カレンダーを参照したいので許可をもらう」ユースケースの2種類があるように読めた。OAuth や OpenID Connect は後者を想定しているように思うが合っているか。今回作ろうとしているのは前者だと思うが、前者は後者に内包される形で実装できるのか（「ログインする」ことだけを許可するトークンを払い出すなど）

半分逆。**OAuth 2.0 が後者（データを使わせてもらう）、OpenID Connect が前者（ログインの代わり）**のためのもの。そして推察のとおり、前者は後者の仕組みに乗せて作る。

| ユースケース | 欲しいもの | 規格 | このリポジトリ |
| --- | --- | --- | --- |
| Google でログインしたことをもって、自社サイトのログインの代わりにする | 「この人は誰か」 | OIDC（昔は SAML、OpenID 2.0） | ステップ4 |
| 自社サイトから Google カレンダーを読ませてもらう | 「この人のデータを使ってよい」 | OAuth 2.0 | ステップ5 |

OAuth 2.0 は委譲のために「IdP に連れて行き、同意をもらい、コードを渡し、裏でトークンに引き換える」運び方を作った。OIDC はその運び方をそのまま使い、運ぶ荷物に「ログインの結果（ID トークン）」を足した。

「ログインすることだけを許可するトークン」という発想はほぼ当たっている。`scope=openid` だけで頼むと、`/token` から **ID トークン**（本体）と、`/userinfo` しか呼べない最小の**アクセストークン**が返る。ただし ID トークンは「許可」ではなく、**宛名付きの紹介状**。

| | アクセストークン | ID トークン |
| --- | --- | --- |
| たとえ | 合鍵（API の扉を開ける） | 紹介状（「この人は山田さんです。あなた宛てに書きました」） |
| 誰が読むか | API。アプリは中身を読まずに渡すだけ | アプリ（RP）自身。API には送らない |
| 何を言うか | この範囲（scope）の操作をしてよい | 誰が、いつ、どうやってログインしたか。宛先は誰か |

1回の流れで両方をもらうこともできる。`scope=openid email https://www.googleapis.com/auth/calendar.readonly` と頼めば、ログインとカレンダーの読み取りが1回の同意で済む。

### Q. 「SAML がアサーションでやっていたこと、OpenID がやろうとしたことを、OAuth 2.0 の上でやり直す。それが OpenID Connect」が本質だと思うが、それぞれ何を表すのか

OIDC は、3つの先輩から一番よかったところを1つずつ借りている。

| 先輩 | 何をしていたか | 足りなかったこと | OIDC が借りたもの |
| --- | --- | --- | --- |
| **SAML** | IdP が「誰で、いつ、どうやってログインし、どの SP 宛てか」を書いた**アサーション**（XML）に署名して渡す | XML の署名が重い。事前の契約が要る。スマホに合わない | **中身**：署名付きの「ログインの結果」。ID トークンはアサーションを JSON（JWT）で書き直したもの（`iss`、`sub`、`aud`、`exp`、`amr` は、どれもアサーションにあった項目） |
| **OpenID 2.0** | 事前の契約なしに、誰でも IdP・RP になれる一般の Web の SSO を目指した | ログインしかできず、サービスが導入する理由が弱い。URL を ID にする使い勝手 | **開かれ方**：Discovery（`/.well-known/openid-configuration`）と RP の動的な登録。IdP の URL を1つ渡せば、ライブラリが設定を読みに行く |
| **OAuth 2.0** | IdP に連れて行き、同意をもらい、コードを渡し、裏でトークンに引き換える。どの言語でも書ける単純さで、すでに広く使われていた | ログインの結果を渡す決まりがない（トークンのすり替え） | **運び方**：`/authorize` → 認可コード → `/token`、client_id と redirect_uri の登録、スマホへの対応（PKCE） |

短く言うと **OIDC ＝ OAuth 2.0 の運び方 ＋ SAML の中身（を JSON で）＋ OpenID の開かれ方**。「やり直す」のは、3つとも狙いは正しかったのに単独では欠けていたから（SAML は中身はよいが重い、OpenID は狙いはよいが導入する理由がない、OAuth は広く使われていたがログインの結果を渡せない）。すでに皆が実装していた OAuth 2.0 の上に乗ったので、新しい仕組みを一から広める必要がなく、OAuth 2.0 に対応したサービスが少し足すだけで IdP になれた。これが普及の大きな理由。→ [番外編：OAuth 2.0 と OpenID Connect の来歴](../history/4-oauth-oidc.md) の 7 節

### Q. OIDC はログインの代わり、OAuth 2.0 はカレンダーを読ませてもらう、で使っている。ということは OIDC は OAuth 2.0 の上位互換ではなく、用途によって使い分けるものか。Google でいえば、ログインの代行だけなら Google と OIDC でやりとりし、カレンダーを読みたいときは OAuth 2.0 でやりとりする、ということか（本当か）。「1回の流れで両方」は、OIDC と OAuth 2.0 のどちらを使っているのか

半分合っている。「用途によって使い分ける」のは確かだが、**使い分けるのは「何を頼むか（scope）」で、窓口も流れも同じ**。OIDC は OAuth 2.0 と並ぶ別のやりとりではなく、OAuth 2.0 の頼み方の1つ。

Google の窓口は、ログインでもカレンダーでも同じ（認可 `https://accounts.google.com/o/oauth2/v2/auth`、トークン `https://oauth2.googleapis.com/token`）。違うのは `/authorize` に送る `scope` だけ。

| 頼み方（scope） | 呼び名 | 返ってくるもの | 用途 |
| --- | --- | --- | --- |
| `calendar.readonly` | OAuth 2.0 | アクセストークン（カレンダーの API 用） | カレンダーを読むだけ |
| `openid email` | OIDC | **ID トークン** ＋ アクセストークン（`/userinfo` 用） | ログインだけ |
| `openid email calendar.readonly` | OIDC | **ID トークン** ＋ アクセストークン（`/userinfo` とカレンダーの API 用） | 両方 |

**`scope` に `openid` が入っていれば OIDC の要求、なければ素の OAuth 2.0 の要求。**どちらも同じ流れ（`/authorize` → 認可コード → `/token`）を通り、OIDC のときだけ `/token` の応答に ID トークンが付く。

- **上位互換か**：規格の関係としては近い。OIDC の流れはすべて OAuth 2.0 の流れでもあり、OIDC の IdP（OP）は必ず OAuth 2.0 の認可サーバーでもある（Google も、ステップ4の auth も）。使う側から見ると「要るときだけ足す」もので、カレンダーを読むだけなら `openid` は要らない。ログインに使うなら `openid` を足して ID トークンをもらう（アクセストークンだけでログインの代わりにするのは、すり替えの穴があるので避ける）。
- **「1回の流れで両方」はどちらか**：`openid` が入っているので OIDC。同時に OAuth 2.0 でもある。ID トークンは自社サイトが読んでログインさせるのに、アクセストークンはカレンダーの API に渡して予定を読むのに使う。
- 実際には Google は、最初は `openid email` だけでログインさせ、カレンダーの機能を使うときに追加で `calendar.readonly` を頼むのを勧めている（incremental authorization）。最初から多くの権限を求めると、利用者が同意をためらうため。追加のときも窓口と流れは同じ。

## パスワードとセッション

### Q. パスワードの保存は、どういう思想で今の形になったのか

パスワードは、1台の計算機を大勢で共有した MIT の CTSS（1961年）で生まれた。最初はファイルに平文で置かれ、すぐに漏洩の事件が起きた（1962年の持ち出し、1966年の「今日のお知らせ」の取り違え）。

そこで出てきた思想が「**照合に、秘密そのものは要らない**」。パスワードを一方向の関数にかけた結果だけを保存し、照合のときは入力をもう一度同じ関数にかけて比べる。サーバーが秘密を持たなければ、ファイルが漏れても秘密は漏れない。

以後は、この思想は変えずに、攻撃者の計算のコストをどう上げるかの競争が続いた。

| 工夫 | 解消した不満 |
| --- | --- |
| わざと遅くする（1979年、crypt） | 辞書の単語を片っ端から試せた |
| ソルト | 辞書を一度ハッシュにしておけば、全員に使い回せた |
| bcrypt（1999年） | 計算機が速くなると遅さが効かなくなる → 遅さを数値で上げられる |
| scrypt（2009年） | GPU で並べて総当たりされる → メモリを大量に使わせる（GPU は演算器ごとのメモリが少ない） |
| Argon2（2015年） | 公開のコンペで選ばれた、メモリと時間の両方を調整できるもの。auth はこれ（Argon2id） |

→ [番外編：パスワードとセッションの来歴](../history/1-password-session.md)

### Q. フォームでのログイン + Cookie のセッションは、何かの規格なのか

規格ではない。Web の作り手が自然に行き着いた、事実上の標準。

HTTP は利用者を覚えない（ステートレス）。最初の解決は HTTP/1.0 の Basic 認証で、ブラウザがパスワードを覚えて**すべてのリクエストに**付けて送った。これには不満が多かった。

- 見た目を変えられない（ブラウザ標準のダイアログ）
- ログアウトできない（ブラウザが覚えている限り送り続ける）
- 期限がない
- パスワードが毎回流れる（base64 は暗号化ではない）

1994年に Netscape が Cookie を作った（もとは買い物かごのため）。これを使って、「フォームでパスワードを1回だけ受け取り、合っていれば乱数のセッション ID を Cookie で渡し、以後はその ID で判断する」と組み立てると、Basic 認証の不満が全部解ける。

Cookie の属性（`HttpOnly`・`Secure`・`SameSite`・`__Host-`）は、どれも過去の攻撃への答えとして、あとから足されたもの。

| 属性 | 答えた攻撃 |
| --- | --- |
| `HttpOnly`（2002年） | XSS で `document.cookie` を読まれて盗まれる |
| `Secure` | 平文の HTTP から Cookie を拾われる（2010年の Firesheep で、誰でもできるようになった） |
| `SameSite`（2016年〜） | CSRF：よそのサイトから、ログイン中のサイトへのリクエストを送らせる |
| `__Host-` | 別のサブドメインから Cookie を上書きされる |

### Q. ログインに失敗したとき、なぜ「どちらが違うか」を言わず、存在しない利用者でもハッシュを計算するのか

存在するユーザー名を探す手がかりを与えないため。

- メッセージ：「ユーザー名かパスワードが違います」とだけ言う。「そのユーザーはいません」と言うと、存在するユーザー名を一覧にできてしまう。
- 応答時間：メッセージをそろえても、**時間の差**が手がかりになる。利用者がいないときは Argon2id の計算（数十ミリ秒）を省けるので、速く返ってしまう。この差から「このユーザー名は存在する」と分かる（タイミング攻撃）。

そのため、利用者がいないときも、起動時に作っておいた捨てのハッシュで同じだけ照合してから断る。手元で測ると、存在する利用者でも、しない利用者でも、0.05〜0.08秒でほぼ同じになった（最初の1回だけ遅いのは、立ち上がりのため）。

同じ考え方で、止めている間（5回失敗したあと）も、画面には同じメッセージを出し、同じだけ時間をかける。「止まっています」と言うこと自体が、そのユーザー名が存在する手がかりになるから。

### Q. ログインの POST のあと、なぜ 303 でリダイレクトするのか

Post/Redirect/Get という定石。ログインのフォームの POST に、HTML を直接返すのではなく、「303 See Other → /account」を返して、ブラウザに `/account` を GET で開き直させる。

こうすると、ログイン後の画面でブラウザの再読み込みを押しても、フォームが再送されない（「フォームを再送信しますか？」のダイアログが出ない）。302 ではなく 303 を使うのは、「POST の結果として、別の URL を **GET で**開け」という意味がはっきりしているから。

### Q. ログアウトを GET ではなく POST にし、`Origin` を確かめるのはなぜか

GET だと、よそのサイトに `<img src="https://auth.alphajinsei.com/logout">` を置くだけで、そのページを見た人を勝手にログアウトさせられる。画像を読むつもりで、ブラウザが GET を送ってしまうから。

状態を変える操作は POST にし、さらに `Origin` ヘッダーで「自分の画面から送られたか」を確かめる（CSRF の対策）。ブラウザは POST に `Origin`（送信元のページのスキーム・ホスト・ポート）を必ず付け、JavaScript からは偽れない。Cookie の `SameSite=Lax` でも、よそのサイトからの POST には Cookie が付かないが、古いブラウザや例外に備えて二重にしている。

ログアウトで大事なのは、**サーバーの DB の行を消すこと**。Cookie を消すのは、ブラウザに後片付けを頼んでいるだけ。Cookie が残っていても、行がなければそのセッションは無効。

### Q. 自分の origin（`https://auth.alphajinsei.com`）を、なぜリクエストの URL から決めず、環境変数にするのか

経路は Cloudflare → OCI LB → app VM で、**LB で TLS が終わる**。アプリには HTTP で届くので、リクエストの URL から決めると `http://...:3000` のようになってしまう。

`Origin` の確認や、ステップ4の OIDC の issuer（発行者の URL）は、外から見た正しい origin でなければならない。そのため環境変数（`PUBLIC_ORIGIN`）で固定する。本番は `compose.yaml` に `https://auth.alphajinsei.com`、手元は `local.env` に `http://localhost:3000`。手元でポートを変えたときは `PUBLIC_ORIGIN` も変えないと、POST が 403 になる。

### Q. 失敗の回数は、どう数えれば数え漏れがないのか

1つの `UPDATE` で、数えるのと止めるのを同時に行う。

```sql
UPDATE users
SET failed_count = failed_count + 1,
    locked_until = IF(failed_count >= 5, <15分後>, locked_until)
WHERE id = ?
```

いったん `SELECT` で回数を読み、アプリで1足して `UPDATE` で書くと、同時に来た2つの失敗が同じ値を読み、1回分を数え漏らす。1つの `UPDATE` なら、DB が行をロックして順に処理するので漏れない。

MySQL の `SET` は左から順に評価され、右の式（`IF(failed_count >= 5, ...)`）は、**足したあとの** `failed_count` を見る。この性質を使っている（標準の SQL とは違う、MySQL の挙動）。

回数はログインに成功したときだけ0に戻す。15分が過ぎたあとも回数は5以上のままなので、また1回間違えるとすぐ止まる。総当たりの速さを、15分に1回まで落とすことになる。手で解くときは `admin.js unlock <ユーザー名>`。

### Q. 手元で試したら、止める期限が9時間ずれていた。なぜか

日時の扱いが2通り混ざっていた。

- Drizzle の通常の `insert`・`update` は、日時を **UTC** の文字列にして送り、読むときも UTC とみなす。
- 生の SQL（`` sql`...` ``）に `Date` を埋め込むと、ドライバー（mysql2）が既定で**プロセスの時刻**（手元なら JST）で文字列にする。

失敗の回数の `UPDATE` は生の SQL で書いたので、「15分後」が JST で書き込まれ、Drizzle がそれを UTC として読んだ。結果、9時間長く止まった。

接続の設定に `timezone: 'Z'` を付け、ドライバーも UTC にそろえて直した（[src/db/client.ts](../../src/db/client.ts)）。本番のコンテナは UTC なので、手元でしか出ない種類の不具合。

## ワンタイムパスワード

### Q. OTP は、どういう思想で生まれ、何が決め手で普及したのか

最初の思想は「**一度流れたものは、二度と使えないようにする**」。telnet などが平文でパスワードを流し、1994年には盗聴で大量に集められていた。盗み見られても、それがもう使い終わったパスワードなら価値がない。

その後、RSA の SecurID などのハードウェアトークン（6桁が1分ごとに変わる小さな機械）で、意味が変わった。盗聴の対策から、「**この機械を持っている**」ことの証明、つまり認証の要素の「所持」になった。パスワード（知識）と組み合わせれば2要素認証になり、パスワードがリスト型攻撃で漏れても、機械がなければ入れない。

ハードウェアトークンは、高い・1社に縛られる（計算の方法が非公開）という不満があった。そこで計算の方法が公開の規格になり（HOTP 2005年、TOTP 2011年）、さらに Google Authenticator（2010年）で、機械を配らずにスマートフォンがトークンになった。

普及の決め手は、次の3つがそろったこと。

- 公開の規格（誰でもサーバーとアプリを作れる）
- 誰もが持つスマートフォン（機械を配らなくてよい）
- QR を読むだけの登録（`otpauth://totp/...` の URL。どの認証アプリも同じ QR を読める）

残った弱点は、リアルタイムのフィッシング。偽の画面に入れさせた6桁を、30秒以内に本物のサイトへ中継されると防げない。人間が数字を読み写す限り、どのサイトに入力しているかを確かめるのは人間の目になる。この限界を、仕組みでサイトを見分けて越えたのがパスキー（ステップ3）。

→ [番外編：ワンタイムパスワードの来歴](../history/2-otp.md)

### Q. Lamport の鎖（100乗、99乗……）だと、OTP で認証できる回数に限りがあるのか。それとも十分大きいので実質無限なのか

**限りがある。**100回分の鎖を作ったら、使えるのは100回まで。使い切ったら、新しい秘密で鎖を作り直して、サーバーに登録し直す（S/KEY では `keyinit` というコマンド）。「十分大きいので実質無限」という位置づけではない。鎖を長くすると、1回のログインごとに最大その回数だけハッシュを計算することになるので、数百回程度が普通だった。

限りがある理由は、一方向の関数の性質。`h(x)` から `x` には戻れないので、使う順番は「鎖の後ろから前へ」しかない。サーバーが持つのは「次に来るはずの値を、もう一度ハッシュした値」だけで、盗まれても次のパスワード（鎖の1つ手前）は計算できない。

つまり Lamport の鎖は、**サーバーが秘密を持たないかわりに、回数に限りがある**という取引になっている。紙の一覧を持ち歩く面倒さもあり、SSH（1995年）が通信路ごと暗号化して盗聴の問題を別の方法で解いたこともあって、S/KEY は普及しきらなかった。

### Q. 回数に限りがあるのは原型の Lamport の鎖だけで、今の TOTP は時刻を使うので制限がない、ということか。HOTP と TOTP のどちらが主流か

そのとおり。HOTP も TOTP も、`HMAC(秘密, カウンタか時刻)` を毎回計算するので、何度でも使える。そのかわり、サーバーも秘密そのものを持つ（Lamport の鎖の逆の取引）。どちらが良いかではなく、トレードオフ。

主流は **TOTP**。認証アプリ（Google Authenticator、Microsoft Authenticator、1Password など）は、ほぼ TOTP を前提にしている。HOTP は、ボタンを押すたびにカウンタが進むので、押しただけで使わないと機械とサーバーでカウンタがずれ、サーバー側でずれを探し直す手間が要る。時刻なら、ずれるのは時計だけ。HOTP が残っているのは、ボタンを押すと数字が出るハードウェアトークンや、YubiKey の一部の機能くらい。

### Q. 秘密を共有して双方で OTP を導出するのは、共通鍵に近い気がする。何か違いはあるのか

**実体は同じで、共通鍵（対称鍵）そのもの**。TOTP の秘密は HMAC の鍵。違うのは使い方だけで、暗号化には使わず、「この鍵を持っていなければ作れない値」を作って見せるのに使う。

構造としては、チャレンジ・レスポンス（相手が出した問題に、鍵を使って答えを返す）の一種。チャレンジが「今の時刻」なので、サーバーが送らなくても双方が知っている。

共通鍵なので、サーバーも同じ鍵を持つ。パスワードはサーバーがハッシュしか持たなくても照合できるが、TOTP はサーバーが秘密そのものを持つ（共有の秘密）。サーバーが破られれば全員分が漏れる。2011年に RSA が侵入され、SecurID のシードに関わる情報が盗まれ、直後に Lockheed Martin が攻撃を受けたのは、この弱点が現実になった例。

ステップ3のパスキーは、ここを**公開鍵**に替えたもの。サーバーが持つのは公開鍵だけなので、DB が漏れても秘密は漏れない。

### Q. 共有する秘密は、登録時に QR で受け渡される。秘密がインターネットを流れるが、HTTPS で経路が暗号化される前提なのか

前提。経路は2区間に分かれる。

1. auth → ブラウザ：HTTPS で1回だけ流れる
2. 画面 → スマホ：カメラで読むので、ネットワークを通らない

これは共通鍵の宿命で、「最初に秘密を、安全に相手に渡す方法」が別に要る（**鍵配送の問題**）。TOTP では、その安全な経路として「HTTPS」と「パスワードでログイン済みのセッション」を使っている。そのため、登録の画面はログインした人にしか開けない。

逆に言えば、画面を覗かれたり、QR のスクリーンショットを撮られたりすれば、秘密は漏れる。QR の中身が画面に出るのは、登録のときの1回だけにしている。

### Q. 共有する秘密は、利用者ごとに新しく発行するのか。「DB が漏れたら全員分の2要素目が漏れる」とは、全ユーザーで何かを共有しているのか

利用者ごとに、登録のたびに乱数で新しく作る（20バイト）。全員で共有するものはない。

「全員分が漏れる」は、「DB にはそれぞれの利用者の秘密が並んでいるので、DB が漏れると全員の秘密が一度に漏れる」という意味。パスワードのハッシュなら漏れても元に戻すのに総当たりが要るが、TOTP の秘密はそのまま使えてしまう。だから暗号化して保存する（下の問い）。

### Q. OTP の前後1回のずれは許容する仕様なのか。登録のときだけか

**登録とログインの両方で許す。**RFC 6238 は、通信の遅れのために「少なくとも1つ前の枠を受け付けること」を推奨している。多くの実装は、時計のずれも考えて前後1つ（±30秒）にしている。クラウドのコンソールにログインするとき、入力している間に次の6桁が表示されてもログインできるのは、この仕様のおかげ。

その分、同じ6桁が最大90秒ほど計算上は合い続ける。盗み見られた6桁をすぐに使われないよう、**最後に使った時刻の枠を記録し、それ以前の枠を拒む**（RFC 6238 も、同じコードを2回受け付けてはならないと定めている）。

また、6桁は100万通りしかなく、前後1つの幅を許すと1回の試行で3つの値が当たりになる。回数制限がないと総当たりで破れるので、ステップ1の失敗の回数を、パスワードと6桁の両方で数える。

### Q. TOTP の秘密を暗号化して保存するとき、何がどこに置かれるのか

決めた形（B1）では、置き場所が3つに分かれる。

| もの | 置き場所 |
| --- | --- |
| 利用者ごとの TOTP の秘密 | **暗号文**として DB |
| それを暗号化する鍵（全利用者で共通の1つ） | 本体は **Vault**。**デプロイのとき**に、デプロイのスクリプトが app VM の上で Vault から取り出して `.env`（権限 600）に書き、コンテナはそれを環境変数として読む（DB のパスワードと同じ経路）。動いている間は、鍵はコンテナのメモリにある |
| 復号した秘密 | 6桁を照らすその場でだけメモリに置く。どこにも保存しない |

OTP の認証のリクエストが来たら、その利用者の暗号文を、環境変数の鍵で復号し、それを使って6桁を照らす。

これで、DB だけが漏れた場合（バックアップの流出、SQL インジェクションなど）は守れる。コンテナ（app VM）を乗っ取られると、鍵も取られる。

もう1つの形（B2）として、Vault の鍵管理の機能（KMS）で暗号化・復号する方法がある。鍵は Vault から一度も出ず、コンテナはログインのたびに Vault の API に「これを復号して」と頼む（AWS KMS などで実務によく使う形）。app VM を乗っ取られても鍵そのものは持ち出せない。そのかわり、OCI の SDK を入れる手間と、Vault が落ちるとログインできなくなる依存が増える。今回の学習の主題は TOTP なので、鍵の管理で回り道をしすぎないよう、B1 にした。

Claude は自分の内部で何語で考えているかを観察できないので、確かなことは言えない。ただ、コミットのメッセージでは英語で「Stage 4」と書いていて、ロードマップを作ったときに stage の訳として「段」を選んだ可能性が高い。日本語の「段」は「3段に分ける」「2段構え」のように層や段構えを表すことが多く、工程の意味では不自然だった。

## TOTP の実装（src/totp.ts）

### Q. `hotp()` を行ごとに解説してほしい（TypeScript 自体に詳しくない）

RFC 4226 の例（秘密 `12345678901234567890`、カウンタ 0）を、実際の数値でたどる。

```ts
export function hotp(secret: Buffer, counter: number, digits = DIGITS): string {
```

関数の宣言。

- `export`：ほかのファイルから使えるようにする印。
- 引数は3つ。`secret: Buffer` は「secret はバイト列（Buffer は Node.js のバイト列の型）」という意味で、`:` の右が型。`counter: number` は数値。`digits = DIGITS` は「省略されたら DIGITS（6）を使う」という既定値の書き方。
- 最後の `: string` は、戻り値が文字列だという宣言。

```ts
	const message = Buffer.alloc(8);
	message.writeBigUInt64BE(BigInt(counter));
```

カウンタを、HMAC に入れる**8バイトのバイト列**にする。HMAC は数値ではなくバイト列を受け取るので、変換が要る。

- `Buffer.alloc(8)`：0で埋めた8バイトを用意する。
- `writeBigUInt64BE`：そこに 64ビットの符号なし整数を、ビッグエンディアン（大きい桁が先）で書き込む。カウンタ 0 なら `00 00 00 00 00 00 00 00`。
- `BigInt(...)`：JavaScript の普通の数値は 64ビットの整数を正確に扱えないので、64ビットを書くときは BigInt（任意の大きさの整数）に変換して渡す決まり。

この形式（8バイト、ビッグエンディアン）は RFC 4226 が決めている。クライアントも同じ形にするので、同じ値になる。

```ts
	const mac = createHmac('sha1', secret).update(message).digest(); // 20バイト
```

HMAC-SHA1 を計算する。メソッドを順につなげる書き方で、「秘密を鍵に HMAC-SHA1 の計算器を作る → message を流し込む → 結果を取り出す」。結果は20バイト。例では次の値。

```
cc 93 cf 18 50 8d 94 93 4c 64 b6 5d 8b a7 66 7f b7 cd e4 b0
```

```ts
	const offset = mac[mac.length - 1] & 0x0f;
```

切り出す位置を決める。

- `mac[mac.length - 1]`：最後のバイト（例では `b0`）。
- `& 0x0f`：下位4ビットだけを残すビット演算。`0xb0` は 2進で `1011 0000` なので、下位4ビットは `0000` で、offset は 0。
- 4ビットなので、offset は 0〜15 のどれか。20バイトから4バイトを取るので、最大でも 15+4=19 で、はみ出さない。

```ts
	const binary = mac.readUInt32BE(offset) & 0x7fffffff;
```

offset の位置から4バイトを、32ビットの整数として読む。例では `cc 93 cf 18`。`& 0x7fffffff` で最上位の1ビットを0にし、31ビットの正の整数にする。`0xcc93cf18` の最上位ビットを落とすと `0x4c93cf18`、10進で **1284755224**。最上位ビットを捨てるのは、言語によって32ビット整数を符号付きで扱うものがあり、そこで結果が食い違わないようにするため（RFC の決まり）。

```ts
	return String(binary % 10 ** digits).padStart(digits, '0');
```

ここで**6桁にする**。

- `10 ** digits` は 10の6乗（100万）で、`%` は割った余り。1284755224 % 1000000 = **755224**。
- `String(...)` で文字列にし、`.padStart(6, '0')` で6桁に満たなければ前を0で埋める（余りが 42 なら `000042`）。

RFC 4226 の付録の、カウンタ 0 の答え `755224` と一致する。テストで確かめているのはこれ。

### Q. この「決まった桁数の数字を切り出す」処理は、クライアント側でも同じ処理を実行するのか。認証アプリに出るのは6桁だが、hotp の途中は31ビットの正の整数とある。この2つを直接比較するわけではないのか

比べない。31ビットの整数は**途中の値**で、`hotp()` が返すのは最後の行の6桁の文字列。

認証アプリ（クライアント）も、**まったく同じ計算**をしている。同じ秘密、同じカウンタ（時刻から求めた枠の番号）、同じ手順なので、同じ6桁になる。画面に出ているのは、この最後の6桁。サーバーは同じ計算で6桁を作り、`verifyTotp()` で、入力された6桁と文字列どうしで比べる。

### Q. TOTP は HOTP のカウンタに時刻を使ったもの、とのこと。ミリ秒とあるので、その瞬間のミリ秒が使われるのか。サーバーとクライアントで同じミリ秒の値は持てないと思う。プロトコルの中で「この時刻で計算しよう」と合意するのか

ミリ秒は一致しない。そして、一致させる必要もない。ミリ秒は入口で使うだけで、計算に使うのは**30秒ごとの枠の番号**だから。

```ts
export function stepAt(ms: number): number {
	return Math.floor(ms / 1000 / STEP_SECONDS);
}
```

- `Date.now()` は、1970年1月1日（UTC）からの経過ミリ秒。JavaScript の時刻はミリ秒で表すので、ミリ秒で受け取っている。
- 1000で割って秒にし、30で割って、`Math.floor` で小数を切り捨てる。たとえば 2026-11-12 の昼なら、ミリ秒は 1794000000000 前後で、枠の番号は 59800000 前後。この番号は **30秒の間ずっと同じ**。

合意しているのは「1970年からの秒数を30で割って切り捨てた番号」で、これは RFC 6238 が決めている。両者の時計が数秒ずれていても、同じ30秒の枠の中にいれば同じ番号になり、同じ6桁になる。

枠の境目をまたいだとき（スマホでは 59800000、サーバーに届いたときには 59800001 になった、など）や、時計のずれのために、`verifyTotp()` は前後1つの枠まで許している。スマホもサーバーも、時計はネットワーク（NTP や携帯の網）で数秒以内に合わせられているのが前提。

**理解の確認**：「30秒おきの枠で、サーバー・クライアントともに『共有の秘密 + 30秒おきの枠 → 6桁』を計算し、それが一致することを確かめる。これで、共有の秘密を『所持している』ことを示す、2要素目の認証ができる」で合っている。

### Q. totp.ts の残りの部分（generateSecret、totp、verifyTotp、base32、otpauthUri）は何をしているのか

**`generateSecret()`**：`randomBytes(20)` で、暗号論的に安全な乱数を20バイト作る。利用者ごとの秘密。

**`totp()`**：`hotp(secret, stepAt(ms), digits)` を呼ぶだけ。TOTP は「HOTP のカウンタに枠の番号を入れたもの」なので、関数の中身も1行。`ms = Date.now()` は既定値の書き方で、省略すると今の時刻を使う。テストでは過去の時刻を渡して、RFC の値と比べている。

**`verifyTotp()`**：入力された6桁を照らす。

```ts
export function verifyTotp(secret: Buffer, code: string, lastStep: number | null, ms = Date.now()): number | null {
```

- `lastStep: number | null` は「数値か null（まだ一度も使っていない）」。`|` は「どちらか」を表す型の書き方。
- 戻り値も `number | null` で、合えば合った枠の番号、合わなければ null を返す。

```ts
	if (!/^\d{6}$/.test(code)) return null;
```

`/^\d{6}$/` は正規表現で、「先頭から末尾まで、数字がちょうど6個」。それ以外（5桁、英字など）は計算せずに断る。

```ts
	const now = stepAt(ms);
	for (const step of [now - 1, now, now + 1]) {
		if (lastStep !== null && step <= lastStep) continue;
		if (timingSafeEqual(Buffer.from(hotp(secret, step)), Buffer.from(code))) return step;
	}
	return null;
```

- 前の枠、今の枠、次の枠の3つについて、順に試す。
- `continue` は「この回は飛ばして次へ」。最後に使った枠以前は試さないので、同じ6桁の再利用が拒まれる。
- `timingSafeEqual`：2つのバイト列を比べる。普通の `===` は、1文字目が違えばすぐ false を返すので、何文字目まで合っていたかが応答時間に出る。この関数は、どこで違っても同じ時間をかけて比べる。ステップ1の「存在しない利用者でもハッシュを計算する」と同じ考え方。
- 合えば、その枠の番号を返す。呼び出し側（2-c）が、それを「最後に使った枠」として DB に記録する。

**`base32()`**：秘密（20バイト）を、QR に入れる文字列にする。Base32 は、5ビットずつ区切って、32種類の文字（A〜Z と 2〜7）に置き換える方式。人が手で打つこともあるので、0と O、1と I のような紛らわしい文字が入っていない。中のビット演算は「8ビットずつ溜めて、5ビット以上溜まったら上から5ビット取り出す」をくり返している。20バイト＝160ビットは5で割り切れるので、32文字になる。

**`otpauthUri()`**：QR の中身の URL を作る。`otpauth://totp/auth.alphajinsei.com:alice?secret=...&issuer=...` の形で、Google が決めた書き方。どの認証アプリもこれを読める。

- `encodeURIComponent`：`:` や日本語などを URL で使える形にする。
- `URLSearchParams`：`?a=1&b=2` の部分を組み立てる。
- `` `...${...}...` ``（バッククォート）は、文字列の中に値を埋め込む書き方（テンプレートリテラル）。

### Q. TOTP の秘密の暗号化（src/secretbox.ts）は、どういう形で暗号化しているのか

AES-256-GCM で暗号化し、`base64url( nonce 12バイト | 暗号文 | 認証タグ 16バイト )` の形で DB に置く。20バイトの秘密が、64文字になる。

- **GCM は認証付き暗号**：暗号化と同時に「改ざんされていないか」を確かめるタグを作る。DB の値を書き換えられたら、復号のときにエラーになる。
- **nonce**（一度だけ使う乱数）は、暗号化のたびに作る。同じ鍵で nonce を使い回すと、GCM は安全でなくなる。
- **AAD（追加の認証データ）に利用者の ID を渡す**：AAD は暗号化はされないが、タグの計算に混ぜられる。別の利用者の行に暗号文をそのまま写しても、ID が違うのでタグが合わず、復号できない。
- 鍵は環境変数 `TOTP_KEY`（32バイトを base64 で）。起動時になければ、アプリは起動しない（設定漏れに早く気づくため）。手元は `local.env` の開発用の鍵、本番は Vault（2-d）。

### Q. 「AAD に利用者の ID を混ぜる」とは、6桁の導出に利用者 ID も入力として含まれるのか（ユーザー側でも ID を知って同じ計算をするのか）。それとも、サーバーが秘密を暗号化して保管するときの追加の安全策で、基本原理（共有の秘密と時刻からお互いに6桁を計算する）は変わっていないのか

**後者で合っている。**AAD は、サーバーが秘密を DB に保管するときの追加の安全策。基本原理は変わらない。6桁の計算に利用者の ID は入らず、ユーザー側（認証アプリ）は ID も暗号化も知らない。

層が2つに分かれている。

| 層 | 誰が関わるか | 中身 |
| --- | --- | --- |
| TOTP の層 | サーバーと認証アプリの両方 | 秘密（QR で渡した20バイトそのもの）+ 時刻の枠 → 6桁。RFC 6238 のとおり |
| 保管の層 | サーバーだけ | 秘密を DB に置く前に `TOTP_KEY` で暗号化する。ログインのときに復号して、平文の秘密に戻してから TOTP の層に渡す。AAD はここだけの話 |

認証アプリが持っているのは、QR から読んだ平文の秘密そのもので、サーバーの暗号化とは無関係。

言葉の補足：AAD は「ソルト」とは少し違い、**「暗号化はしないが、改ざんの検知（タグ）の対象には含めるデータ」**。タグは共通鍵で作る署名のようなもの（MAC）で、「暗号文」と「AAD」の両方をまとめて覆う。復号するときに同じ AAD（利用者の ID）を渡さないと、タグが合わずに失敗する。

**防いでいる攻撃**：攻撃者が DB に書き込めるようになった（SQL インジェクションなど）が、`TOTP_KEY` は持っていない、とする。

1. 攻撃者は、自分のアカウントで TOTP を登録する。自分の秘密（QR）は知っていて、DB にはその暗号文が入る。
2. その暗号文を、被害者の行にそのまま写す。
3. AAD がなければ、サーバーは被害者の行を「攻撃者の秘密」として復号してしまう。攻撃者は自分の認証アプリで、被害者の6桁を作れる。
4. AAD に利用者の ID を混ぜておけば、攻撃者の ID で作ったタグは被害者の ID では合わないので、復号が失敗し、6桁は通らない。

暗号化で「読めない」ことに加えて、AAD で「その暗号文は、その利用者のものだ」と結び付けている。

### Q. TOTP の利用者で、失敗の回数をいつ0に戻すのか

**ログインが最後まで済んだとき（6桁が通ったとき）だけ**。ステップ1では、パスワードが通った時点で0に戻していた。TOTP の利用者でも同じにすると、パスワードを知っている攻撃者は「パスワードを通す（回数が0に戻る）→ 6桁を4回試す」をくり返せて、6桁を無制限に試せてしまう。6桁は100万通りで、前後1つの幅を許すと1回の試行で3つが当たりになるので、回数制限が効かなくなると破られる。

手元で試すと、6桁を1回間違えると `failed_count` が1になり、正しい6桁が通ったところで0に戻った。

### Q. 同じ6桁が、同時に2つのリクエストで送られたらどうなるのか

「最後に使った枠」を、次の1つの `UPDATE` で記録している。

```sql
UPDATE totp_credentials SET last_step = <今回の枠>
WHERE user_id = ? AND (last_step IS NULL OR last_step < <今回の枠>)
```

書き換えに成功するのは、先に着いた1つだけ。もう1つは `affectedRows` が0になり、断られる。いったん `SELECT` で読んでから `UPDATE` で書くと、2つのリクエストが同じ古い値を読み、両方が通ってしまう（失敗の回数の数え方と同じ考え方）。

次のログインで同じ6桁を使い回した場合は、`verifyTotp()` が「最後に使った枠以前」を最初から試さないので、6桁の照合の段階で断られる（失敗として数えられる）。

## パスキー

### Q. FIDO2・パスキーは、どういう思想で生まれ、何が決め手で普及したのか

出発点は、パスワードも OTP も**人間が値を読み写す**ので、偽サイトに入力させてその場で中継されると防げないこと（人間はサイトを見分けられない）と、TOTP でもサーバーが秘密を持つこと。思想は「**人間ではなく、仕組みにサイトを見分けさせる。サーバーには公開鍵だけを置く**」。

公開鍵で本人を確かめる仕組み（TLS のクライアント証明書、IC カード、SSH の公開鍵）は昔からあったが、どれも「この鍵は誰のものか」を証明する CA や名簿を前提にしていて、一般の Web サイトには重かった。FIDO は逆に、鍵が誰のものかは証明せず、**サイトごとに新しい鍵ペアを作り、そのサイトに公開鍵を預けるだけ**にした。

フィッシングに強い理由は2つ。署名の対象に、ブラウザが見ている本当の origin が入る（偽サイトで操作すると偽サイトの origin が入り、本物のサイトが拒む）。鍵はサイト（RP ID）ごとに別で、認証器は偽サイトに本物の鍵を使わない。

流れは、U2F（2014年。Google と Yubico のセキュリティキーでの2要素目）→ FIDO2（WebAuthn が 2019年に W3C 勧告。全ブラウザで同じ API、端末に内蔵の認証器）→ パスキー（2022年に Apple・Google・Microsoft が発表。鍵を端末の間で同期する）。端末から鍵が出られず、機種変更や紛失で困る、という導入の壁を、同期で越えた。そのかわり、鍵の安全がクラウドのアカウントに依存し、最高水準（AAL3）からは一段譲った。

→ [番外編：FIDO2 とパスキーの来歴](../history/3-fido.md)

### Q. パスキーは、本質的には公開鍵認証によるクライアントの証明か。SSH の公開鍵認証に近いが、サーバー側で authorized_keys に公開鍵を置く作業がなくなっているのか。なぜ SSH は鍵の登録を自動化できないのか（登録する公開鍵が正当なユーザーのものだと判断するロジックが自動化できないのか）。FIDO は、事前に ID/PW で認証してから設定を入れるので、本当のユーザーの公開鍵だと示せるのか

その理解で合っている。FIDO では、`authorized_keys` に公開鍵を置く作業を、ブラウザと認証器が自動で行う。

自動化できる理由も推察のとおりで、**「この公開鍵は正当な本人のものだ」という信頼を、すでにある別の認証から借りている**から。登録はログイン済みの画面からしかできないので、「パスワード（+ TOTP）でログインした人が、今この鍵を出した」ことをもって、その鍵を本人のものと認める。新規登録の画面で最初のパスキーを作る場合は、「アカウントを作った人が持ち主」という、SSH の初回接続（known_hosts）と同じ「最初の1回は信じる」形になる。

SSH にも同じ仕組みはある。「一度 ID/PW でログインしてから鍵を送る」という発想は実在する。

| 仕組み | 信頼を借りる先 |
| --- | --- |
| `ssh-copy-id` | パスワードで1回ログインし、公開鍵を `authorized_keys` に書き足す |
| クラウドの VM の作成（OCI の `ssh_authorized_keys` など） | クラウドの API の認証（OCI の IAM）。VM を作る権限のある人が渡した鍵を、最初から置く |
| OCI Bastion のセッション | OCI の API の認証。公開鍵を API に渡すと、その鍵で3時間だけ入れる。FIDO の登録とほぼ同じ構図 |

ただ、インターネットに向けて SSH のパスワード認証を開けることはしない（感想のとおり）。そのため SSH の世界では、「SSH 自身の中で ID/PW から鍵へ段階的に上げる」形ではなく、「別の経路（クラウドの API）で認証して鍵を置く」形が広まった。

### Q. シーケンスにチャレンジ・レスポンスは含まれるのか。ID/PW で認証していても必要なのか。秘密鍵で署名する原文として challenge を送っているのか。チャレンジ・レスポンスは生のパスワードを送らないための仕組みだと理解していたが、ここでは秘密鍵を外に出さないために使っているのか

含まれる。FIDO の中心はチャレンジ・レスポンス。「秘密鍵で署名するときの原文として challenge を送っている」も合っている。署名の原文は「authenticatorData」と「clientDataJSON のハッシュ」をつなげたもので、clientDataJSON の中に challenge と origin が入っている。

ただし、使う目的は少し違う。

- パスワードのチャレンジ・レスポンス（CHAP、HTTP Digest など）の目的は2つだった。① 秘密（パスワード）を送らずに、知っていることを示す。② 使い回し（リプレイ）を防ぐ。
- **公開鍵の署名では、① は署名そのものが引き受ける。**署名から秘密鍵は計算できないので、challenge がなくても秘密鍵は外に出ない。
- そのため、ここでの **challenge の役目は ② の使い回しの防止**（新しさの保証）。毎回同じ原文に署名するなら、一度盗んだ署名を何度でも使えてしまう。サーバーが毎回新しい乱数を出し、一度使ったら消すので、盗んだ署名は二度と通らない。

ID/PW でログイン済みの登録のときにも challenge が要るのは、同じ理由。「この登録の応答は、今このサーバーが求めたものへの応答だ」と確かめ、古い登録の応答を流し込ませないため。

TOTP と並べると、TOTP は「今の時刻」が暗黙の challenge だった。FIDO は、サーバーが明示的に乱数を渡す。

### Q. FIDO のシーケンスは難解だが、技術の要素に還元すると数種類で、その組み合わせでこのシーケンスになる、という理解はできるか

できる。7つの要素の組み合わせ。

| # | 要素 | 何を保証するか | 由来 |
| --- | --- | --- | --- |
| ① | 公開鍵の署名 | 秘密鍵を持っていること（秘密を見せずに） | SSH、TLS のクライアント証明書 |
| ② | challenge | 署名が今回のための新しいもの（使い回しでない） | チャレンジ・レスポンス |
| ③ | origin を署名に入れる | どのサイトで操作したか（偽サイトの中継を見破る）。origin はブラウザが書き込むので、ページの JavaScript には偽れない | FIDO で新しく入った |
| ④ | 鍵をサイト（RP ID）ごとに分ける | 偽サイトには本物の鍵を使わない。サイトをまたいで同一人物だと追跡されない | FIDO で新しく入った |
| ⑤ | 端末の中でのユーザー検証 | 鍵を使ったのが端末の持ち主本人（指紋・PIN）。生体情報はサーバーに送られない | スマホのロック解除 |
| ⑥ | 登録の信頼を、既存のログインから借りる | 登録された公開鍵が本人のもの | `ssh-copy-id`、クラウドの鍵の登録 |
| ⑦ | カウンタ | 鍵が複製されていない（任意。同期されるパスキーでは 0） | ハードウェアトークン |

- **登録** ＝ ⑥ ログイン済みの画面から始める → ② challenge を渡す → ⑤ 本人を確かめて、④ この RP ID 用の鍵ペアを作る → ③ origin 入りの応答を返す → サーバーは ②③④ を確かめ、① の公開鍵を保存する
- **ログイン** ＝ ② challenge を渡す → ④ この RP ID の鍵を選び、⑤ 本人を確かめて、① 署名する（原文には ② と ③ が入っている）→ サーバーは ②③④ を確かめ、① を公開鍵で検証し、⑦ カウンタを見る

シーケンス図の Note の「〜を確かめる」は、どれもこの番号のどれかに当たる。どれも単独では昔からある考え方で、新しいのは組み合わせ方（特に ③④）。

### Q. RP、RP ID、RP サーバー、RP アプリケーションは、それぞれどう対応するのか。auth が両方を兼ねているのか。IdP 相当はどちらか。RP ID はどちらの持ち物か。そもそも RP とは何を意味する言葉か（relaying party なら、認証をお願いしたい側のアプリケーションか）

**RP は Relying Party（信頼する側）**で、relay（中継）ではなく rely（頼る・信頼する）。**誰かが出した認証の結果を信じて、利用者を受け入れる側**。

一番混乱しやすいのは、**同じ RP という言葉が、層によって違うものを指す**こと。

| 層 | 証明を出す側 | 証明 | RP（それを信じる側） |
| --- | --- | --- | --- |
| WebAuthn（ステップ3） | 認証器 | 署名（assertion） | **auth** |
| OIDC（ステップ4） | auth（OP） | ID トークン | **demo-app** |

auth は WebAuthn の層では RP で、OIDC の層では OP（IdP）。WebAuthn の世界での「RP」は「パスキーでログインさせるサイト」のことで、今回は IdP である auth 自身。用語の番外編で「RP ＝ demo-app」と書いたのは、OIDC の層の話。

- **RP サーバーと RP アプリケーション**：WebAuthn の RP は2つの部分からできている。**RP サーバー**は challenge を作り、署名を検証するところ（信頼できる側で、合否を決めるのはここだけ）。**RP アプリケーション**は利用者が操作する画面と、その中で `navigator.credentials` を呼ぶ JavaScript（スマホのアプリならアプリ本体）。今回は推察のとおり **auth が両方を兼ねている**。
- **IdP 相当はどちらか**：両方とも auth の中。IdP（auth）が、自分のログイン画面のために WebAuthn の RP になっている。
- **RP ID は誰の持ち物か**：RP 全体の持ち物で、**RP サーバーが決めて、守らせる**。サーバーが options で RP ID を渡し、検証のときに「authenticatorData の RP ID のハッシュが自分のものか」を確かめる。ブラウザは「その RP ID が、今のページの origin のドメインと合っているか」を確かめる（`auth.alphajinsei.com` のページから `google.com` の RP ID は使えない）。親のドメイン（`alphajinsei.com`）を指定すると、サブドメインの間で同じパスキーを使える。

**RP サーバーと RP アプリケーションを分離する予定はあるか**：分けない。企業では、検証専用の「FIDO サーバー」を置いて各業務アプリが API で呼ぶ構成をよく見かけるが、プロトコル上で大事なのは「challenge の発行と検証が、利用者の手の届かないサーバー側にあること」だけで、別のサービスに分けることは必須ではない。このリポジトリでは、より大事な分離がステップ4で入る。**パスキーを扱うのは IdP（auth）だけにし、各アプリ（demo-app）は WebAuthn に一切触れず、OIDC で結果だけを受け取る**形。今の一般的な構成で（「Google でログイン」の先でパスキーを扱うのは Google だけ）、アプリを増やしても、パスキーの登録や検証を各アプリに実装しなくて済む。分けた形を見たければ、ステップ4のあとの発展として検討する。

### Q. RP は「よそで認証されたことを信じる側、認証をよそに委託する側」ということか。「Google でログイン」の文脈では、RP はそのバナーを出す Web サイトのことが多い（OIDC の立場で議論することが多い）か

そのとおり。**何を「よそ」と見るかが、層によって変わる**だけ。

「Google でログイン」の話をするときは、ほとんどが OIDC の層の話で、RP はバナーを出すサイト。WebAuthn の層の RP（Google 自身。自分のログイン画面でパスキーを使わせる）は、外のサイトからはほとんど見えない。外のサイトはパスキーに一切触れず、Google から ID トークンを受け取るだけ。

**理解の確認**：WebAuthn と OIDC で RP に当たるものが違うのは驚きだったが、「証明を出す側と、それを信じる側」という原理を聞けば納得できた。

### Q. RP ID は RP サーバー（Google の例なら Google）が決めているのか。つまり Google は「本人であることは認証した。ただ、この認証でログインしてよいのは、事前に知っているこのドメインだけ」と言っているのか。Google の認証で OIDC を実装したいなら、自分のドメインでフェデレーションできるように Google に設定を入れてもらう必要があるのか

半分当たりで、**別の2つの制限が混ざっている**。

| | 何を縛るか | 誰が決める | 「Google でログイン」の例 |
| --- | --- | --- | --- |
| **RP ID**（WebAuthn の層） | **パスキーを使ってよいページのドメイン** | RP サーバー（Google） | `google.com`。パスキーは Google のログイン画面の中だけで使う。自分のアプリのドメインは関係しない |
| **クライアントの登録**（OIDC の層） | **ID トークンを渡してよい相手（client_id と redirect_uri）** | OP（Google） | 自分のアプリの `https://app.example.com/callback` を事前に登録する |

「本人であることは認証した。ただ、結果を渡してよいのは事前に知っているこのドメインだけ」は、**OIDC のクライアント登録**の方に当たる。

- 連絡は要らない。Google Cloud Console で「OAuth クライアント ID」を自分で作り、許可する redirect URI を書き込む（セルフサービス）。
- Google は、登録にない redirect URI には結果を返さない。そうしないと、偽サイトが「結果を自分に送って」と頼めてしまう。
- ステップ4で、auth にもこの仕組み（クライアントの表と redirect_uri の照合）を作る。

RP ID の方は「Google の鍵は Google のページでしか使わせない」という縛りで、パスキーに触れない自分のアプリが関わることはない。

**理解の確認**：OIDC の層では、結果を受け取る側（RP）ごとに OP への登録が要る。WebAuthn（を含む FIDO）の層は、Google の認証ページとその裏の認証サーバーの中で完結するので、どこからフェデレーションされても同じで、アプリごとに設定が発生する箇所ではない。

### Q. ブラウザの実装を信じていることが前提になっている箇所がいくつかある。ブラウザを独自に実装したら破れる穴はないのか

前提は実際にある。ただ、**破るには被害者の端末そのものを乗っ取る必要がある**。

ブラウザを信じているのは3か所。

- clientDataJSON に本当の origin を書く
- RP ID がページのドメインと合っているかを確かめてから、認証器に渡す
- 認証器には「どの RP ID 用か」をブラウザが伝える（認証器はそれを信じる）

| 誰のブラウザが細工されているか | 何が起きるか |
| --- | --- |
| **攻撃者が、自分の端末で独自のブラウザを作る** | 何も得られない。origin を好きに書けても、**被害者の秘密鍵は被害者の認証器の中**にあり、署名できない。サーバーは署名を公開鍵で検証するので、ここはブラウザを信じていない |
| **偽サイト（普通のフィッシング）** | ページの JavaScript には origin を書き換えられない。FIDO が守るのはこの場面 |
| **被害者のブラウザ自体が悪意のもの**（マルウェア、悪い拡張機能） | 破れる。偽の origin を書き、本物の RP ID で認証器に署名させれば、中継が通る |

最後の行は、FIDO が守らないと決めている範囲（仕様もクライアントを信頼するものとして扱っている）。そこまで乗っ取られた端末では、どの方式も守れない。入力したパスワードはそのまま盗めるし、ログイン後のセッションの Cookie も盗める（今いちばん多い攻撃は、この Cookie を盗むマルウェア＝インフォスティーラー）。**パスキーが消したのは、その手前の「偽サイトに入力させる」攻撃**。

それでも、OS は「誰でもブラウザを名乗れる」状態にはしていない。

- **Windows**：USB のセキュリティキーに直接話しかけるには管理者の権限が要る。普通のアプリは Windows の WebAuthn API を通すしかない。
- **iOS・Android**：任意のサイトの RP ID でパスキーを使えるのは、OS がブラウザと認めたアプリだけ（Apple は専用の権限、Android は許可されたブラウザの一覧）。普通のアプリは、自分と結び付いたドメイン（そのドメインが `/.well-known/` のファイルで「このアプリは自分のもの」と宣言している）でしか使えない。

Cookie を盗まれる問題への次の手として、セッションも端末の鍵に結び付ける仕組み（DBSC：Device Bound Session Credentials）が Chrome で進んでいる。パスキーの考え方をセッションにも広げるもの。

**理解の確認**：被害者のブラウザに細工できた時点で、こんな高級な仕組みを考えなくても悪用の方法はいくらでもある。なので、そのパターンは守る範囲の外と仕様でも決めている。

### Q. RP ID は今回は auth.alphajinsei.com で、Google の例でも google.com なのか。直観では「relying party ＝ 認証サーバーへ遷移する元の Web アプリの FQDN」だと思ってしまうが、そうではなく認証サーバーの方の ID なのか。WebAuthn の文脈では RP は認証サーバーの側（端末の認証器を信じる側）なので、RP ID は認証サーバーの FQDN を指す、ということか。RP という言葉が多義的なことによる分かりにくさか

そのとおり。**RP ID は「WebAuthn の RP の ID」**で、WebAuthn の RP は「認証器の署名を信じる側」＝ 署名を検証するサーバー。だから RP ID は、パスキーでログインさせる画面とその裏のサーバーのドメインになる。

| | 直観で思い浮かべるもの | 実際の RP ID |
| --- | --- | --- |
| 「Google でログイン」 | バナーを出した元のアプリのドメイン | `google.com`（Google のログイン画面のドメイン） |
| このリポジトリ（ステップ4以降） | demo-app のドメイン | `auth.alphajinsei.com`（手元は `localhost`） |

直観の「元のアプリ」は、**OIDC の層の RP**。そちらには RP ID という言葉はなく、OP が持つ識別子は client_id（と redirect_uri）。つまり、

- **WebAuthn の RP ID**：認証サーバー（OP）のドメイン。パスキーの鍵を、どのサイトの画面で使ってよいかを縛る
- **OIDC の client_id**：元のアプリの識別子。ID トークンを誰に渡してよいかを縛る

と、名前も層も違う。分かりにくさの原因は推察のとおり、**「RP」という言葉が層によって別のものを指す**こと。元のアプリから見ると、パスキーは「認証サーバーの中の出来事」で、アプリのドメインは一切登場しない。

**理解の確認**：RP は「証明を信じる側」。WebAuthn では認証サーバーが認証器を信じる側なので、RP ID は認証サーバーの FQDN。元の Web アプリは OIDC の層の RP で、そちらは client_id で識別される。

**裏付け**：WebAuthn の仕様（W3C、Level 3）の用語の節に、この点そのものの注記がある。

> Note: While the term Relying Party is also often used in other contexts (e.g., X.509 and OAuth), an entity acting as a Relying Party in one context is not necessarily a Relying Party in other contexts. … Note that in any concrete instantiation a WebAuthn context may be embedded in a broader overall context, e.g., one based on OAuth.

（ある文脈で RP である者が、ほかの文脈でも RP とは限らない。WebAuthn の文脈は、OAuth のような大きな文脈の中に埋め込まれることがある。）また RP ID の定義には「既定では、WebAuthn を呼び出したページの origin のドメイン」とある。「Google でログイン」で `navigator.credentials` を呼ぶのは Google のログイン画面なので、RP ID は Google のドメインになる。出典：[Web Authentication Level 3 の Terminology](https://www.w3.org/TR/webauthn-3/#webauthn-relying-party)

### Q. 「既定では、RP ID は WebAuthn を呼び出したページの origin のドメイン」とあるが、呼び出したページと聞くと、Google に認証を頼む元の Web アプリを思い浮かべてしまう。そうではなく、Google の認証ページが、裏にある Google の認証ロジック（これが WebAuthn？）を呼んでいる、という見方をすればよいのか

少し違う。**WebAuthn は Google の裏のロジックではなく、ブラウザが持つ JavaScript の API**（`navigator.credentials.create()` / `get()`）。「呼び出したページ」は、**その API を自分の JavaScript で呼んだページ**で、「Google でログイン」なら Google のログイン画面。

```
1. app.example.com のページで「Google でログイン」を押す
2. リダイレクトで、ブラウザが accounts.google.com のページに移る   ← 元のアプリのページは、もう画面にない
3. accounts.google.com のページの JavaScript が navigator.credentials.get() を呼ぶ   ← 「WebAuthn を呼び出したページ」
   → ブラウザが origin = https://accounts.google.com を記録し、認証器が署名する
4. その署名を、Google のサーバーが検証する（RP サーバー）
5. リダイレクトで app.example.com に戻る（認可コードを持って）
```

元のアプリのページは、3 の時点で画面から消えているので、API を呼べない。だから RP ID も origin も Google のものになる。「RP ID は認証サーバーのドメイン」と「呼び出したページのドメイン」は、同じことを言っている。

### Q. `/account/passkey/options` は ID/PW でログイン済みかを確かめる処理だと理解した。それならステップ1・ステップ2のテーブルのログイン状況を見るはずだが、新しい webauthnCredentials を見ているように読める。正しいのか。ID/PW が通ったら webauthnCredentials にもログイン状態を書く処理が、別に足される予定なのか

ログインの確認は1行目の `currentUser(c)`（`src/session.ts`）。Cookie から `sessions` テーブルを引き、本物のセッション（stage = full）かを見る。ステップ1・ステップ2のものをそのまま使っている。

`webauthnCredentials` を引いているのは別の目的で、**この利用者が登録済みの鍵の一覧**を取るため。options の `excludeCredentials` に入れ、同じ認証器での二重の登録を防ぐ。ログインの状態は書き込まないし、その予定もない。

### Q. `issueChallenge` の「challenge を作る」の実体は、`const id = randomBytes(32).toString('base64url')` のランダムなバイト列のことか

違う。乱数を**2つ**作っている。

| 変数 | 作る関数 | 何か | どこへ行くか |
| --- | --- | --- | --- |
| `challenge` | `newChallenge()`（`src/webauthn.ts`） | **challenge の本体**（32バイトの乱数） | options でブラウザへ渡り、clientDataJSON に入って戻る。DB にはそのまま置く |
| `id` | `randomBytes(32)` | **引換券**。DB の challenge の行を指す | Cookie（HttpOnly）。DB にはその SHA-256 だけ |

`id` はステップ1のセッション ID と同じ形の引換券。応答が戻ったとき、Cookie の `id` から「このブラウザに出した challenge」を引き、clientDataJSON の challenge と一致するかを確かめる。challenge の本体はページの JavaScript から見えるが、`id` は見えない。引換券を分けておくと、3-b のログイン（まだセッションがない）でも、「challenge を要求したブラウザ」と「応答を送ってきたブラウザ」が同じだと確かめられる。

### Q. `navigator.credentials.create` は、図では「ブラウザ → 認証器」で、auth には通信が来ない。なぜ await するのか。そもそも await できるものなのか

`await` は通信のためだけのものではなく、**すぐに結果が返らない処理なら何でも**対象になる（Promise を返す関数なら何でも待てる）。`navigator.credentials.create()` は Promise を返す。中で起きているのは「登録 4〜6」で、利用者が指紋を当てるまで、数秒から数分かかる。JavaScript はその間止まって待てない（止まると画面が固まる）ので、「終わったら結果を渡す」という Promise を返し、`await` で受け取る。

待つ相手は、ネットワークの先ではなく、ブラウザ・OS・認証器とその前の利用者。

| 行 | 待つ相手 | 図 |
| --- | --- | --- |
| `await post('/account/passkey/options')` | auth | 登録 2 → 3 |
| `await navigator.credentials.create(...)` | 認証器と利用者 | 登録 4 → 5 → 6 |
| `await post('/account/passkey/verify', ...)` | auth | 登録 7 → 9 |

### Q. `src/routes/passkey.ts` は、登録 2 と登録 7 の手順が順不同に並んでいるように見える。意図はあるのか

「**先に部品、あとで部品を使うルート**」の順。前半が部品（`issueChallenge` は登録 2、`takeChallenge` は登録 7 で使う）、後半がルート（`POST /account/passkey/options` ＝ 登録 2 → `POST /account/passkey/verify` ＝ 登録 7）で、後半は図の順。関数を使う場所より上に書く、プログラムでよくある書き方。図と照らして読むときは、後半のルートから読み、出てきた関数を前半で引く。

### Q. `src/webauthn.ts`、`src/routes/passkey.ts`、`public/passkey.js` はどう使い分けているのか。routes がどんなリクエストを受けて何を返すかの入口、webauthn.ts がその奥のロジック、で合っているか。public は初めて出てきたが、auth が画面も持っているので画面だけ分けているのか（画面はほかにもあるので、それだけでは説明できない気がする）

前半は合っている。ただし routes と webauthn.ts は**どちらもサーバーで動く**。違いは HTTP と DB に触れるかどうか。public は**動く場所そのものが違う**。

| ファイル | 動く場所 | 中身 | 触れるもの |
| --- | --- | --- | --- |
| `src/webauthn.ts` | サーバー | WebAuthn の仕様が決める確認。**RP サーバーのロジック** | 入力のデータだけ。HTTP も DB も知らない |
| `src/routes/passkey.ts` | サーバー | リクエストを受け、セッションを確かめ、challenge を DB に置き、webauthn.ts に確かめさせ、保存し、応答する。**入口と手続き** | HTTP（Hono）、DB、Cookie |
| `public/passkey.js` | **利用者のブラウザ** | `navigator.credentials.create` を呼ぶ。**RP アプリケーション** | ブラウザの API |

- **webauthn.ts を分けた理由**：3-b のログインでも同じ確認を使うため。HTTP も DB も要らないので、単体テストで直接試せるため（偽サイトの origin を拒むテストは DB なしで動く）。
- **public/ の意味**：画面かどうかではなく、**ブラウザにそのまま渡すファイルかどうか**。ほかの画面の HTML は、`src/views.ts` がサーバーで組み立てて送っている。`public/` のファイル（`style.css`、`passkey.js`）は組み立てずにそのまま渡す（`index.ts` の `serveStatic`）。`src/` の TypeScript はサーバーの Node.js で動き、`passkey.js` はブラウザで動く。素の JavaScript なのも、変換せずに渡すため。
- **JavaScript が初めて出てきた理由**：WebAuthn の API は JavaScript からしか呼べないから。これまでの画面は HTML のフォームだけで済んでいた（フォームを送るのはブラウザの標準の動き）。パスキーは HTML のフォームでは書けないので、ブラウザ側のコードが初めて必要になった。「2. 登場人物」の RP アプリケーションに当たる。

### Q. 「WebAuthn を呼び出す」とは、ブラウザの JavaScript が認証器に鍵の作成を頼む処理のことか。それとも、ブラウザの JavaScript に `navigator.credentials.get()` を実行させるよう指示した auth のことか。後者だから「呼び出したページ」は auth で、ID は auth の FQDN、という理解か。呼び出しというとクライアントからサーバーへの方向を想像するが、この場合は逆で、サーバーからクライアントへの依頼なのか

**前者が近い。**「呼び出す」は、ページの JavaScript がブラウザの API（`navigator.credentials.get()`）を呼ぶこと。その先でブラウザが認証器に頼む。どちらも端末の中の関数の呼び出しで、ネットワークの通信ではない。

**「ページ」は auth のサーバーではなく、ブラウザで開いている auth のページ。**ページの身元（origin）は、どこから読み込んだか（アドレスバーの URL）で決まる。`https://auth.alphajinsei.com/account` を開くと、HTML も `passkey.js` もそこから読み込まれるので、その中の JavaScript が呼べば、呼び出し元は `https://auth.alphajinsei.com`。偽サイトは自分のページの URL を偽れないので、origin も偽れない。

auth は、呼び出すコード（`passkey.js`）と材料（options）を配るだけで、遠隔で命令しているわけではない。ID が auth の FQDN になるのは、「auth が指示したから」ではなく、**呼んだのが auth から読み込んだページだから**。

### Q. challenge も id もクライアントに渡し、認証器は challenge に秘密鍵で署名し、公開鍵と id をサーバーに返す。サーバーは id でどの challenge への応答かを知り、公開鍵で署名を復号し、送った challenge と一致するかを確かめる、という理解でよいか。challenge は署名して返す前提なので元の値が保存されておらず、見分けるために id を括り付けるのか。複数の通信の間で同期したい情報はセッションで持つイメージだが、それはできないのか。元の challenge も署名と一緒に送り返してもらえば紐づけられそうだが、その案はとらなかったのか

いくつか違う。

- **id は認証器にも JavaScript にも渡らない。**HttpOnly の Cookie なので、ブラウザが次のリクエスト（登録 7）に自動で付けて返すだけ。認証器に渡るのは challenge だけ（options の中）。
- **送り返すのは challenge そのもの。**ブラウザが作る clientDataJSON に入って戻ってくる。
- **公開鍵を送るのは登録のときだけ。**ログインでは鍵の ID を送り、サーバーは登録のときに保存した公開鍵を引く（毎回送られてくる公開鍵を信じたら、攻撃者が自分の鍵で署名して自分の公開鍵を添えれば通ってしまう）。
- **署名の検証は「復号」ではない。**原文・署名・公開鍵を入れて、真か偽かが返る計算（ES256 には復号に当たる操作がない）。サーバーは、送られてきた authenticatorData と clientDataJSON から原文（`authenticatorData ‖ SHA-256(clientDataJSON)`）を組み立て、保存した公開鍵で署名を確かめる。それとは別に、clientDataJSON の challenge が、Cookie の id から引いた「出した challenge」と一致するかを確かめる。
- **登録では challenge に署名はかからない**（attestation を `none` にしたため）。登録の challenge の確認は、clientDataJSON の一致だけ。署名で守られるのはログイン（3-b）。
- **元の challenge はサーバーが保存している**（`webauthn_challenges.challenge`）。送り返された値は利用者側が自由に作れるので、サーバーが「自分が出した、まだ使っていない challenge」と照らさないと、昔の応答の送り直しを見分けられない。
- **やっていることはセッションそのもの。**challenge 用の5分だけの小さなセッションで、Cookie に引換券、サーバーに中身、というステップ1と同じ形。`sessions` テーブルに入れなかったのは、3-b のログインがセッションのない状態から始まるため。登録とログインで同じ仕組みを使えるように分けた。
- **送り返してもらう案**も実在する。サーバーが challenge に HMAC をかけて渡し、改ざんがないかを確かめれば、何も保存しなくて済む。ただ、期限内なら何度でも送れるので、「一度しか使えない」を守るには「使った」という記録が結局要る。それなら最初から保存する方が単純。

### Q. （理解の確認）`navigator.credentials.create()` を await できるのはなぜか

**理解の確認**：`public/` 配下のコードも auth のサーバーの一部だと誤解していたので、「登録 4 はブラウザと認証器の間の処理なのに、なぜ auth が待てるのか（通信がないのに）」と疑問に思った。実際は、`public/` は auth が配る、ブラウザで動く JavaScript。`create()` を呼ぶのはブラウザの中の `passkey.js` なので、それが待つのは正当。auth のサーバーは、次のリクエスト（登録 7）が来るまで何もしていない。

### Q. JavaScript はサーバーから配信して、クライアント側で実行する。つまり、`navigator.credentials.get()` をローカルのブラウザで実行するように JS を配信した配信元が origin で、それが auth、という理解でよいか

ほぼそのとおり。正確には、origin は **JS のファイルの配信元ではなく、JS を載せたページ（HTML）の URL** で決まる。ブラウザの中では、読み込んだスクリプトはすべて、それを読み込んだページの一部として動く。auth のページが外部の CDN から JS を読み込み、その JS が `navigator.credentials.get()` を呼んでも、origin は `https://auth.alphajinsei.com` のまま。今回はページも `passkey.js` も auth から来ているので、結論は同じ。

origin は「スキーム + ホスト + ポート」（`https://auth.alphajinsei.com`）。RP ID は、そのうちのドメイン（`auth.alphajinsei.com`）だけ。

**理解の確認**：「呼び出し」をクライアントからサーバーへの方向で考えていたのが誤りだった。JS はサーバーから配られてブラウザで動き、そのページの URL がブラウザの API に対する身元（origin）になる。

### Q. HttpOnly の Cookie は、なぜ JavaScript から読めないのか。「JS ではなく HTTP」という意味の名前なのか。一見、HTTP と HTTPS のうち HTTP しか処理しない、と読めて脆弱そうに見える

名前の意図は「**HTTP のやりとりにだけ使う**（JavaScript には見せない）」。ブラウザはこの Cookie をリクエストのヘッダーに付けて送るが、ページの JavaScript の `document.cookie` には出さない。ここでの HTTP はプロトコル全般のことで、HTTPS も含む。「HTTPS のときだけ送る」は、別の **`Secure`** 属性の役目。auth の Cookie には両方を付けている。

| 属性 | 意味 | 防ぐもの |
| --- | --- | --- |
| `HttpOnly` | JavaScript から読めない | XSS（ページに紛れ込んだ悪いスクリプト）に Cookie を盗まれること |
| `Secure` | HTTPS の通信にだけ付ける | 暗号化されていない HTTP での盗み見 |

### Q. ログインのときの options と、登録のときの options は別なのか

別。登録は「新しい鍵を作る」ための材料が全部要るが、ログインは「どのサイトの鍵で、この challenge に署名して」だけでよい。

| | 登録（`registrationOptions`） | ログイン（`authenticationOptions`） |
| --- | --- | --- |
| RP | `rp: { id, name }` | `rpId` だけ |
| challenge | ある | ある |
| 利用者 | `user: { id, name, displayName }`（認証器に覚えさせる） | なし（まだ誰か分からない。認証器が返してくる） |
| 署名の方式 | `pubKeyCredParams`（ES256、RS256） | なし（鍵はもうある） |
| 登録済みの鍵 | `excludeCredentials`（二重の登録を防ぐ） | `allowCredentials` は渡さない（discoverable なので認証器が探す） |
| その他 | `attestation`、`authenticatorSelection` | `userVerification` |

### Q. RP ID は誰が指定し、誰が検証するのか。登録のとき、クライアントが「この RP ID で鍵を作って」と言うのか、サーバーが決めるのか。認証器が特定の RP ID で鍵を作り、auth がそれを検証する、という流れか。ログインで、鍵の RP ID が自分のものと一致するかを確かめるのが動作 8 か

**決めるのはサーバー（RP サーバー）、確かめるのはブラウザ・認証器・サーバーの3者。**

| 誰が | 何をするか | どこで |
| --- | --- | --- |
| **サーバー** | RP ID を決めて、options に入れる | 登録 3（`rp.id`）、ログイン 3（`rpId`） |
| JavaScript | options をそのままブラウザの API に渡す（中継するだけ） | `navigator.credentials.create` / `get` |
| **ブラウザ** | RP ID が今のページのドメイン（かその親）か確かめる。違えば、認証器に頼まずに断る | 登録 3 / ログイン 3 のあとの Note |
| **認証器** | 登録では鍵をその RP ID に結び付けて覚える。ログインでは、その RP ID の鍵だけを探す。どちらも authenticatorData に RP ID のハッシュを入れる | 登録 4〜6 / ログイン 4〜6 |
| **サーバー** | authenticatorData の RP ID のハッシュが、自分の RP ID のハッシュと一致するか確かめる | 登録 7 のあとの 3つ目の Note、ログイン 8 のあとの 2つ目の Note（`checkAuthData`） |

クライアントが自分で RP ID を言い出すのではなく、サーバーが決めた値を、ブラウザが「このページで使ってよい値か」と確かめてから認証器に渡す。ログインの動作 8 は「鍵の ID から公開鍵を引く」で、RP ID の確認はその次の 2つ目の Note。

### Q. 認証器から送られてくるのは、鍵の情報（challenge への署名など）だけでなく、RP ID などもまとめて来るはず。ざっくり何が来るのか。RP ID と、challenge を秘密鍵で署名したものが本体（authenticatorData）かと思ったが、clientDataJSON も来ている

送られてくるものは、**作った者が2人いる**。ブラウザが作る clientDataJSON と、認証器が作る authenticatorData・署名。

ログイン（`credential.toJSON()`）の中身：

```
id               鍵の ID                                    認証器
response
  clientDataJSON   { type: "webauthn.get", challenge, origin }   ブラウザ
  authenticatorData  RP ID のハッシュ(32) | フラグ(1) | カウンタ(4)   認証器
  signature        authenticatorData ‖ SHA-256(clientDataJSON) への署名   認証器
  userHandle       利用者の ID（登録のときに覚えさせたもの）         認証器
```

登録では、authenticatorData のうしろに「鍵の ID と公開鍵」が付き、それが attestationObject（`{ fmt, attStmt, authData }`）に包まれて来る。attestation を `none` にしたので、登録には署名がない。

推察と違うのは、**challenge は authenticatorData に入らない**こと。challenge と origin は、Web の世界の情報で、ブラウザが知っている。RP ID、本人を確かめたか、カウンタは、端末の側の情報で、認証器が知っている。

- ブラウザは、clientDataJSON を作ってから、その**ハッシュだけ**を認証器に渡す（認証器は origin も challenge も直接は見ない）。
- 認証器は「authenticatorData ‖ そのハッシュ」に署名する。

こうして、2人が別々に作ったものが、1つの署名で結び付けられる。サーバーは、届いた2つから同じ原文を組み立てて検証するので、clientDataJSON の challenge と origin も、authenticatorData の RP ID も、まとめて署名で守られる。

（この問いのおかげで、図の誤りが見つかった。clientDataJSON は、認証器が応答したあとではなく、認証器に頼む前に作られる。そのハッシュを認証器に渡す必要があるため。図を直した。）

### Q. ログインの `const row = await takeChallenge(c, 'login')` は何か。図のどこに当たるのか。`/login/passkey/options` を受けてから「鍵の ID から、公開鍵・カウンタ・利用者を引く」の間にいるように見える

**ログイン 7（POST /login/passkey/verify）を受けて、最初にすること**。ログイン 2 のあとの Note で覚えておいた challenge を、Cookie の引換券で取り出し、同時に消す（一度しか使えない）。取り出した challenge は、ログイン 8 のあとの 1つ目の Note で、clientDataJSON の challenge と比べる。

時間の順では、`/login/passkey/options` のルートはログイン 3 で終わっている。そのあとログイン 4〜6 はブラウザと認証器の中の出来事で、サーバーは何もしていない。ログイン 7 で `/login/passkey/verify` のルートが始まり、その最初が `takeChallenge`、次がログイン 8。

元の図には、この「取り出して消す」が描かれていなかった。DB の別の表（`webauthn_challenges`）への操作で、図に載せていなかったため。「ログイン 7 のあとの Note」「登録 7 のあとの 1つ目の Note」として足した。

### Q. サーバーから送っていたのは options だけだが、それも届くものの中に含まれているのか。auth が options をブラウザに渡し、ブラウザが challenge などを clientDataJSON に埋め込んで認証器に渡し、認証器が clientDataJSON をもとに鍵を選ぶか作り、authenticatorData を作り、clientDataJSON のハッシュと authenticatorData に秘密鍵で署名して送り返す、という構図か

ほぼそのとおり。違うのは1点で、**ブラウザが認証器に渡すのは clientDataJSON そのものではなく、そのハッシュ**。認証器は challenge も origin も読めない。鍵を選ぶ・作る手がかりは、ブラウザが別に渡す RP ID。

options の中身は、形を変えて戻ってくる。

| options の項目 | 誰が使うか | 応答のどこに現れるか |
| --- | --- | --- |
| `challenge` | ブラウザ | clientDataJSON の中に、そのまま |
| `rp.id` / `rpId` | ブラウザ（照合）、認証器（鍵の選択） | authenticatorData の先頭に、ハッシュで |
| `userVerification` | 認証器（指紋・PIN） | authenticatorData のフラグ（UV） |
| `user.id`（登録） | 認証器が鍵と一緒に覚える | ログインのときの userHandle |
| `pubKeyCredParams`（登録） | 認証器が方式を選ぶ | 公開鍵（COSE）の中の `alg` |
| `excludeCredentials`、`rp.name`、`user.name`、`timeout` | 認証器・ブラウザ | 現れない（使われるだけ） |

auth が出した値は、ブラウザか認証器を通って戻ってきて、どれも署名の原文に入っている。サーバーは、自分が出した値と照らすだけでよい。誰が何を順に処理するかの文章は、`docs/steps/3-passkey.md` の「4. 流れ」の冒頭にある。

**理解の確認**：届くものは「ブラウザが作る clientDataJSON」と「認証器が作る authenticatorData・署名」に分かれていて、認証器が clientDataJSON のハッシュに署名することで、両者が1つの署名で結び付く。

### Q. ブラウザが認証器に渡すのが、clientDataJSON 本体ではなくハッシュなのはなぜか。認証器はあくまで認証器で、Web の細かい話（何が origin か）には立ち入らないようにしている世界観なのか。challenge そのものも認証器には渡っていないのか

その世界観で合っている。**認証器は、Web の中身に立ち入らない汎用の署名係**として作られている。理由は3つ。

1. **認証器は Web 専用ではない。**ブラウザと認証器の間の規格（CTAP）は、スマホのアプリ、OS のログイン、SSH からも使われる。OpenSSH は FIDO のセキュリティキーを鍵にでき（`ssh-keygen -t ed25519-sk`）、そのときは clientDataJSON ではなく、SSH の流儀で作った自分のデータのハッシュを渡す。認証器にとっては「32バイトの値に署名して」と頼まれるだけで、中身の形を知らずに済むので、使い道を選ばない。
2. **認証器は origin を確かめようがない。**認証器にはページが見えないので、clientDataJSON の中身を受け取っても、ブラウザが書いたものを信じるしかない。origin の確認はブラウザ（正しく書く）とサーバー（照らす）の仕事にし、認証器はそれに署名して改ざんできなくするだけ。反対に RP ID は、認証器が**自分で使う**（鍵を選ぶ、サイトごとに鍵を分ける）ので、ハッシュではなくそのまま渡される。
3. **小さな機械に合わせる。**セキュリティキーはメモリも通信（USB・NFC・BLE）も小さい。長さがまちまちの JSON より、必ず32バイトのハッシュの方が単純。

この形は U2F のときから同じ。U2F でもブラウザは「クライアントのデータのハッシュ」と「appId のハッシュ」を32バイトずつ認証器に渡していた。

**challenge も認証器には直接届かない。**届くのは challenge を含んだ clientDataJSON のハッシュだけ。それでも使い回しは防げる。challenge が毎回違えば clientDataJSON もそのハッシュも毎回違い、署名の原文が毎回変わるので、昔の署名は今回の原文に合わない。認証器は challenge を「見る」必要はなく、「署名に含める」だけでよい。

## OIDC（ステップ4）

### Q. 「client_id が登録済みか、redirect_uri が登録と完全一致するか」とあるが、auth（OP）は demo-app の情報を事前に知っておく必要があるのか。demo-app を開発するとき、auth に「今後 OIDC でリクエストを飛ばすので登録しておいてください」という申請が本来必要になるのか

はい、事前の登録（client の登録）が必要。登録で決めるのは3つ。

| 登録するもの | なぜ要るか |
| --- | --- |
| client_id（名前） | どのアプリからの要求かを見分ける。同意画面に「demo-app があなたの〜を求めています」と出す |
| redirect_uri（結果を返す先） | 一番大事。登録がないと、攻撃者が redirect_uri に自分のサイトを書いて `/authorize` に利用者を送り込める。利用者が正規に同意すると、認可コードが攻撃者のサイトに届いてしまう |
| client_secret（合言葉） | 裏の通信（`/token`）で「引き換えに来たのは本当に demo-app か」を確かめる |

「申請」の形は IdP によって違う。

- **Google など**：開発者が Google Cloud Console で自分で登録する（セルフサービス）。client_id と client_secret が発行され、許可する redirect URI を書き込む。Gmail の中身のような重い scope を求めるときは、Google の審査がある。
- **企業の IdP**（Entra ID、Okta など）：IdP の管理者が登録する。社内では、まさに「登録しておいてください」という申請になる。
- **自動の登録**：アプリが API で自分を登録する仕組みもある（Dynamic Client Registration、RFC 7591）。
- **このリポジトリ**：管理用のコマンド（`admin create-client demo-app http://localhost:4000/callback`）で登録する。利用者を作るのと同じ方針。

### Q. 一度認可コードを作り、その後のやりとりを経て ID トークン・アクセストークンに引き換えるのはどんな意図か。直接 ID トークン・アクセストークンを発行するのはダメなのか。認可コードは「利用者の同意を得られた」ことを表し、実際に何を許可するかのトークンはその後に別に発行する、という2段階なのか

結論：**ブラウザを通る道（表の通信）は漏れやすいので、そこには単独では使えない引換券だけを通し、本物は直接の道（裏の通信）で渡す**ため。

- **表の通信は漏れやすい。**リダイレクトの URL に載ったものは、ブラウザの履歴、次のページへの Referer ヘッダー、サーバーやプロキシのアクセスログ、ブラウザの拡張機能、スマホなら URL を横取りしたほかのアプリ、に残る。
- **表の通信では、受け取る相手を確かめられない。**auth はブラウザに「この URL へ行け」と言うだけで、行った先で誰が受け取ったかは分からない。裏の通信なら、client_secret で demo-app だと確かめてから渡せる。

認可コードは、表を通っても、60秒で切れる・一度しか使えない・引き換えに client_secret と code_verifier（PKCE）が要る、ので、盗まれても単独では使えない。**直接トークンを渡す方式は実際にあった**（implicit の流れ。URL に直接アクセストークンを載せた）が、漏れやすいので今は使わない（来歴の記事の 8 節）。

「認可コードは同意を得たことの証明か」は少し違う。**何を許すかは `/authorize` の時点で全部決まっていて、認可コードはその決定に結び付いた引換券**。

- `/authorize` で決まること：誰がログインしたか、どうログインしたか（amr）、どの client か、どの redirect_uri か、同意した scope、code_challenge、nonce
- 認可コード：それらを DB で指す引換券
- `/token`：コードと引き換えに、その内容をトークンにして渡す

2段階は「同意 → 許可の中身を別に決める」ではなく、「表で全部決めて、品物は裏で安全に渡す」。クロークの番号札と同じで、預けた中身は預けた時点で決まっていて、番号札だけを持ち歩き、受け取るときに本人確認をして引き換える。

### Q. ID トークンとアクセストークンは同時に発行するものか。片方がもう片方を兼ねられないのか。それとも、ログインしたいだけなら ID トークン、OP 側のリソースを触りたいならアクセストークン、と、何がしたいかで渡るトークンが異なるのか

**OIDC の要求（scope に `openid`）なら、`/token` から同時に出る。ただし片方で片方を兼ねることはできない。**宛先と読む人が違う。

| | ID トークン | アクセストークン |
| --- | --- | --- |
| 宛先 | RP（demo-app）。`aud` に client_id が入る | API（resource server） |
| 読む人 | demo-app 自身。中身を確かめて「誰か」を知る | API。demo-app は中身を読まずに渡すだけ |
| 言うこと | 誰が、いつ、どうやってログインしたか | この範囲（scope）の操作をしてよい |

- アクセストークンでログインの代わりをすると、「すり替え」の穴が開く（どのアプリのためのログインかが書いてない。来歴の記事の 6 節）。
- ID トークンで API を叩くと、API は「何を許されたか」が分からない。ID トークンは API 宛てでもない。

「何がしたいかで渡るトークンが変わる」は、おおむね合っている。素の OAuth 2.0（`openid` なし）ならアクセストークンだけ、OIDC（`openid` あり）なら ID トークン ＋ アクセストークン（少なくとも `/userinfo` を呼べるもの）。demo-app でいうと、ログインに使うのは ID トークンだけで、アクセストークンはステップ4では `/userinfo`、ステップ5では API に使う。

### Q. ブラウザを通る通信（ID/PW を入れたり、同意の画面を挟んだり）は漏れやすいので、その時点では認可コードという引換券の発行にとどめ、裏の通信（demo-app のサーバーと auth のサーバーの間）で引き換える、という世界観か。それでわざわざ一時的な引換券を挟む発想になるのか。非常に冗長な設計に感じ、自分では思いつけなかった。ほかにも理由はあるのか。次に自力で思いつけるよう、どういうときにこの方式にすればよいかを、認証に限らず（IT にも限らず）似た例とともに整理してほしい

世界観はそのとおり。「冗長に感じる」のも正しい感覚で、引換券は1回で済む受け渡しを2回に分けるコスト（往復が1回増える、預かる側に記録が要る、期限の管理が要る）。それでも選ぶのは、**1つの道では満たせない条件が重なったとき**。

漏れやすさ以外の理由：

- **利用者を巻き込める道は表しかない。**ログインや同意の画面を見せられるのはブラウザだけで、裏の通信には利用者がいない。表は省けないが、表だけでは足りない。両方の道が要る。
- **2つの道をつなぐ札が要る。**表と裏は別の接続。「さっきブラウザで同意したのは、今 `/token` に来たこの要求のことだ」と結び付ける照合の番号がコード。
- **相手の確認を、受け取りの時まで遅らせる。**リダイレクトでは受け取る相手を確かめられず、確かめられるのは裏で client_secret を見せてもらう時だけ。
- **運べる大きさ。**URL には長さの限りがあり、JWT は長くなりやすい。
- **中身を運び手に見せない。**トークンがブラウザを通らないので、XSS や拡張機能に見られない。
- **一度きりで異常に気づける。**同じコードが2回来たら盗まれている。そのとき出したトークンも取り消せる。

**引換券を挟むかの問い**（品物を渡そうとして、どれかに当てはまったら考える）：

1. 運ぶ道は信用できるか（見られる・残る・横取りされるなら、札を運ばせる）
2. 渡す時点で、受け取る相手を確かめられるか（できないなら、確かめられる時まで遅らせる）
3. 決める時と渡す時が違うか（今決めて、あとで別の道で渡すなら、決めた内容を指す札を出す）
4. 運べる大きさに収まるか（URL、QR、SMS、紙が小さいなら、札だけ）
5. あとで取り消したいか（札なら記録を消せば無効）

道が信用でき、その場で相手を確かめられ、すぐ渡せるなら、引換券は冗長なだけ。

似た例：ステップ1のセッション ID、ステップ3の challenge の Cookie、パスワード再設定のメールのリンク、ネットの決済（PayPal、Stripe Checkout。OAuth とほぼ同じ形）、非同期の API のジョブ ID（`202 Accepted`）、メッセージキューの Claim Check パターン、OS のファイル記述子、Kerberos のチケット。IT の外では、**宅配の不在票**（一番近い。誰でも覗ける郵便受け＝ブラウザ、窓口で身分証と照らす＝`/token` と client_secret、保管期限、受け取ったら終わり）、クローク、線引小切手（口座への入金しかできない＝client の認証）、船荷証券。

対になる型は「参照（引換券）を渡す」か「署名した値（JWT、証書）を渡す」か。参照は記録が要るが即座に取り消せ、値は記録が要らないが取り消しにくい。OAuth・OIDC は両方を使う（表ではコード＝参照、裏で受け取る ID トークン＝値）。→ [番外編：引換券を挟むという型](extra-pattern-claim-ticket.md)

**理解の確認**：細部を理解しようとしているのは（AI に任せれば理解していなくても動くものは作れるが）、アイデアの手札を増やしたいから。仕組みの理由を、使い回せる型として、分野をまたいだ例と一緒に整理しておく。

### Q. Cookie に戻り先の URL を入れて覚えておく技（`rememberReturnTo`、`takeReturnTo`）が出てきた。`rememberReturnTo` は、ログインがまだの利用者に戻り先の Cookie を仕込んでから `/login` にリダイレクトさせるものだった。`takeReturnTo` はどこで使うのか。見つけられなかった。ID・パスワードの認証が済んだところで使うのか

そのとおり、ログインが最後まで済んで、本物のセッション（`full`）を作った直後に使う。ログインの終わり方は3通りあるので、呼び出しも3か所ある。

| 終わり方 | 場所 | 返し方 |
| --- | --- | --- |
| パスワードだけ（TOTP を設定していない） | [src/routes/login.ts](../../src/routes/login.ts) の `POST /login` の最後 | `c.redirect(takeReturnTo(c), 303)` |
| パスワード + TOTP | 同じファイルの `POST /login/totp` の最後 | `c.redirect(takeReturnTo(c), 303)` |
| パスキー | [src/routes/passkey.ts](../../src/routes/passkey.ts) の `POST /login/passkey/verify` の最後 | `c.json({ ok: true, redirect: takeReturnTo(c) })`。パスキーは JavaScript の `fetch` で送るので、リダイレクトではなく JSON で行き先を返し、[public/passkey-login.js](../../public/passkey-login.js) が `location.href` で移る |

パスワードは正しいが TOTP がまだ、というとき（`partial` のセッション）は呼ばない。ここで戻してしまうと、`/authorize` に戻っても `currentUser` が空なので、また `/login` に飛ばされるだけになる。Cookie は TOTP の画面を通っている間も残っていて、6桁が通ったところで取り出される。

`takeReturnTo` がしていること：Cookie を読む → Cookie を消す（一度きり）→ 中身が `/authorize?` で始まるときだけそれを返し、それ以外（Cookie がない、別の URL が入っている）なら `/account`。`/authorize` に寄り道していない普通のログインでは Cookie がないので、これまでどおり `/account` へ行く。

`/authorize?` に限っているのは、オープンリダイレクトを防ぐため。任意の URL に戻せると、攻撃者が「auth のログイン画面を通ったあと、偽のサイトへ飛ぶ」リンクを作れてしまう（利用者は本物の auth でログインしたので、飛んだ先も信じやすい）。

### Q. 戻り先の URL を覚えておいて、あとで戻ってくることを実現するのに、Cookie に戻り先を入れておいてあとで見直す方法は一般的なのか。決済で、商品ページから決済のボタンを押すと決済のサイト（クレジットカード、PayPay など）に飛び、決済が済んだら元のページに戻ってくる動きがよくあるが、これも同じような実装なのか

「同じサイトの中で、寄り道のあとに戻る」なら、Cookie（またはサーバーのセッション）に覚えるのはよくある方法の1つ。ただ、決済の戻りは仕組みが違い、**OIDC の redirect_uri と同じ形**になっている。今回の流れには、実はこの2種類が両方入っている。

| | 同じサイトの中の寄り道 | サイトをまたぐ往復 |
| --- | --- | --- |
| 今回の例 | auth の中：`/authorize` → `/login` → `/authorize` | demo-app → auth → demo-app |
| 戻り先を覚えるのは | 自分（auth）。Cookie に入れる | 呼んだ側（demo-app）が、行き先（auth）に戻り先を教える。`redirect_uri` |
| 決済では | — | 店 → 決済会社 → 店 |

**同じサイトの中で戻り先を覚える方法**は、主に3つある。

| 方法 | 例 | 向き不向き |
| --- | --- | --- |
| URL の query で持ち回る | Django の `?next=/...`、多くのサイトの `?returnTo=` / `?redirect=` | 一番よく見る。分かりやすいが、ログインのフォームにも隠し項目で持ち回る必要があり、オープンリダイレクトの穴の定番の場所でもある |
| サーバーのセッションに入れる | Spring Security の SavedRequest（ログイン前のセッションに元の要求を保存）、Rails の Devise の `stored_location`（Rails のセッションは既定で署名付きの Cookie なので、実質 Cookie） | ログイン前から使えるセッションの仕組みがあれば自然 |
| 戻り先だけを入れた短い Cookie | 今回の auth | セッションを作る前に使え、画面をいくつ通っても持ち回りが要らない |

今回 Cookie にしたのは、ログインの道が3通り（パスワード → TOTP の画面、パスキーは JavaScript の `fetch`）あり、query で持ち回ると、どの画面・どのフォーム・どの JS にも戻り先を通す必要があるため。Cookie なら、置いた場所と取り出す場所の2か所だけで済む。代わりに、`__Host-` で auth にしか送られないようにし、10分で切れるようにし、中身を `/authorize?` に限っている。なお、Keycloak のような OP 製品は、`/authorize` の要求そのものをサーバー側に「認証の途中のセッション」として保存し、ログイン画面の URL にはその参照（番号）だけを付ける、という作りが多い。

**決済の戻り**は、次のように動く（Stripe Checkout、PayPal、PayPay の Web 決済などは、細部は違ってもこの形）。

1. 店のサーバーが、裏の通信で決済会社の API を呼び、「決済の画面」を作ってもらう。このとき金額と一緒に、**戻り先の URL**（Stripe なら `success_url` と `cancel_url`、PayPay なら `redirectUrl`）を渡す。戻り先には、注文の番号や決済の ID を埋め込める（Stripe は `{CHECKOUT_SESSION_ID}` と書くと、戻るときに本物の ID に置き換えてくれる）。
2. 決済会社は、決済の画面の URL を返す。店は、利用者のブラウザをそこへリダイレクトする。
3. 利用者が決済会社の画面でカードの番号を入れる、PayPay のアプリで承認する、など。
4. 決済会社が、ブラウザを手順1の戻り先へリダイレクトする（決済の ID 付き）。
5. 店のサーバーは、戻ってきた ID を使って、**裏の通信で**決済会社に「この決済は本当に済んだか」を問い合わせ、済んでいれば注文を確定する。

OIDC と並べると、ほぼ同じ形になる。

| 決済 | OIDC |
| --- | --- |
| 店 | demo-app（RP） |
| 決済会社 | auth（OP） |
| `success_url` / `redirectUrl` | `redirect_uri` |
| 戻るときに付いてくる決済の ID | 認可コード |
| 裏の通信で「本当に済んだか」を問い合わせる | `/token` で引き換える |

違いは、戻り先を伝える方法。OIDC は、戻り先をあらかじめ登録しておき、毎回 URL の query で送って完全一致で照らす（表の道で送るので、登録で縛る）。決済は、戻り先を裏の通信（API）で直接渡すことが多い（裏の道なので、改ざんされない）。どちらも「戻ってきた URL の中身だけを信じない」のは同じで、ブラウザが運んだ値は、偽物や作り話かもしれない（「決済が済んだ」というパラメーターを手で付けて店の URL を開くだけで、注文が確定してしまっては困る）。だから必ず、裏の通信で確かめ直す。

決済に特有の点が2つある。

- **ブラウザが戻ってくるとは限らない。**決済が済んだ直後にタブを閉じる人、電波が切れる人がいる。そのため決済会社は、ブラウザとは別に、店のサーバーへ直接「決済が済んだ」と知らせる仕組み（Webhook）を用意していて、注文の確定は Webhook を正とするのが勧められている。ブラウザの戻りは「完了の画面を見せるため」と割り切る。
- **戻ってきたとき、店のログインの Cookie が送られないことがある。**カードの本人確認（3-D セキュア）では、カード会社の画面から店へ、フォームの POST で戻ることが多い。別サイトからの POST には、`SameSite=Lax` の Cookie が付かない。2020年に Chrome が Cookie の既定を `Lax` に変えたとき、「決済から戻るとログインが切れている」という不具合があちこちで起きた。auth の戻り先の Cookie はリダイレクト（GET）で戻るので `Lax` で足りるが、demo-app のステップ（4-d）で `/callback` を作るときにも同じ話が出てくる。

→ 引換券としての見方は [番外編：引換券を挟むという型](extra-pattern-claim-ticket.md) の「似た例」の表（ネットの決済）

### Q. これまでの実装では、routes には概要を書いて、src に細かい関数を実装することが多かったが、今回（`/authorize`）は routes の方に関数（`checkRequest`、`issueCode`、`hasConsent`）まで実装している。何か理由があるのか

分け方の基準は「HTTP や DB に触るか」。これまでも同じ基準で分けていて、今回はたまたま、src に出す種類の関数がほとんどなかった。

| 置き場所 | 中身 | 例 |
| --- | --- | --- |
| `src/*.ts`（routes の外） | HTTP の要求・応答にも DB にも触らない計算。入力を渡せば答えが返る | `password.ts`（ハッシュ）、`totp.ts`（6桁の計算）、`webauthn.ts`（バイト列の検証、署名の確認）、`jwt.ts`（JWT の署名） |
| `src/routes/*.ts` | 要求を読み、DB を読み書きし、応答（画面、リダイレクト、JSON）を返すもの。その道（URL）のためだけにあるもの | `passkey.ts` の `issueChallenge` / `takeChallenge` / `withUserLocked`、`oidc.ts` の `checkRequest` / `issueCode` / `hasConsent` |

routes の中の関数は、ステップ3の `passkey.ts` にもあった（challenge を DB に入れる・取り出す、利用者の行をロックする）。今回の3つも、この種類に当たる。

- `checkRequest`：結果がエラーの画面か、`error=` 付きのリダイレクト。つまり**応答そのもの**を返す。Hono の `Context`（`c`）がないと書けない。
- `issueCode`：DB に認可コードを入れて、302 で redirect_uri へ返す。
- `hasConsent`：DB の同意の表を引く。

どれも `/authorize` の GET と POST からしか使わず、ほかの道から使う予定もない。

逆に、OIDC の中で「HTTP にも DB にも触らない計算」は JWT の署名で、これは 4-a で [src/jwt.ts](../../src/jwt.ts) に分けた。4-c の `/token` で出てくる PKCE の確認（`SHA-256(code_verifier)` を base64url にして、code_challenge と比べる）も同じ種類の計算だが、1行で済むので、`/token` の中に書くつもり。

src に分けておく利点は、HTTP のサーバーを立てずにテストできること（`test/webauthn.test.ts`、`test/jwt.test.ts` は関数を直接呼んでいる）。routes の関数は、確かめるにはサーバーを立てて要求を送ることになる（4-b は curl とブラウザで確かめた）。

**理解の確認**：「外部のもの（DB や HTTP の要求・応答）に触るかどうかで分けている」という理解で合っている。1点だけ補足すると、HTTP の要求・応答も「外のもの」に含めて考えている（`checkRequest` は DB に触らないが、応答を返すので routes の中に置いている）。

### Q. 戻り先を POST のパラメーターで持ち回る方法もあるのか。毎回詰め直すことになるので微妙か。また「同じサイトの中で寄り道して戻るなら」という表現が引っかかった。Cookie は送られるドメインに範囲があるので、より気軽に使うには URL の query の方が簡便、ということか

POST で持ち回る方法もあり、実は auth の中でもう使っている。同意の画面のフォームは、`/authorize` の要求（client_id、redirect_uri、state、nonce、code_challenge など）を隠し項目（`<input type="hidden">`）に入れていて、「許可」を押すとそれが POST で戻ってくる（[src/views.ts](../../src/views.ts) の `consentPage`）。ほかにも、SAML はアサーションを POST で送り、戻り先を `RelayState` という項目で一緒に持ち回る。OIDC にも、結果をリダイレクトの query ではなく、自動で送信されるフォームの POST で返す `response_mode=form_post` がある。

微妙な点は推測どおり、毎回詰め直すこと。

- 画面が1枚（同意の画面のように「見せて、押してもらう」だけ）なら、隠し項目で十分。
- 画面を何枚も通る（パスワード → TOTP、パスキーの JavaScript）と、どのフォームにも入れ直す必要がある。query と同じ手間がかかる。
- リダイレクトをはさむと消える。POST の結果を 303 でリダイレクトすると、ブラウザは GET で開き直すので、本文（POST のパラメーター）は付いていかない。

「同じサイトの中で」の引っかかりは、半分そのとおり。ただ、「Cookie はドメインに範囲があるので query の方が気軽」というより、**サイトをまたぐときは、そもそも Cookie が使えない**、という話。

- auth が置いた Cookie は、auth にしか送られない。demo-app は読めない。
- auth は、demo-app のドメインに Cookie を置けない（ブラウザが許さない）。
- だから、demo-app が auth に「終わったらここへ戻して」と伝えるには、ブラウザが運ぶ URL（query）か POST に戻り先を書くしかない。それが redirect_uri。決済の `success_url` は、裏の通信（API）で直接渡している。

同じサイトの中なら、Cookie、query、POST、サーバーのセッションのどれも使える。そこで、持ち回りの手間（query、POST）と、Cookie の範囲・期限の管理を比べて選ぶ。サイトをまたぐなら、選べるのは URL か POST（または裏の通信）だけで、Cookie は候補にならない。

| | 同じサイトの中 | サイトをまたぐ |
| --- | --- | --- |
| Cookie | 使える（今回の `__Host-return-to`） | 使えない（相手のドメインには送られず、置けない） |
| URL の query | 使える（`?next=`） | 使える（`redirect_uri`）。値を盗み見・改ざんされうるので、登録で縛る |
| POST の隠し項目 | 使える（同意の画面） | 使える（SAML の `RelayState`、`form_post`） |
| 裏の通信 | — | 使える（決済の `success_url`） |

### Q. `/callback` の callback は、電話の折り返しのような言葉を想像した。なぜ callback と呼ぶのか。きっと意味があるはず

想像どおり、電話の「折り返し」が元になっている。プログラミングの用語の **コールバック**（callback）から来ていて、意味は「こちらの連絡先を先に渡しておき、相手の用が済んだら、相手のほうから呼んでもらう」。

- 電話：「今は分からないので、分かったら折り返します」と言われ、こちらの番号を伝えて切る。相手の用が済んだら、相手からかけてくる。
- プログラミング：関数を呼ぶとき、「終わったらこれを呼んで」と自分の関数を渡す。JavaScript の `addEventListener('click', f)` や `setTimeout(f, 1000)` の `f` が、コールバックの関数。呼ぶ側と呼ばれる側が入れ替わるので、「ハリウッドの原則」（Don't call us, we'll call you。こちらから連絡するので、そちらからはかけてこないで）とも言われる。
- OAuth・OIDC：demo-app は「終わったらここへ戻して」と、自分の URL（redirect_uri）を auth に渡す。auth はログインと同意が済んだら、ブラウザをその URL へ送り、demo-app の `/callback` が呼ばれる。demo-app から見ると、auth に任せていた仕事の結果を、auth の側から知らせてもらう。

名前が `/callback` になっているのは、OAuth 1.0（RFC 5849）で、戻り先の URL を `oauth_callback` というパラメーターで渡していた名残。OAuth 2.0 の仕様の正式な呼び名は「redirection endpoint」（パラメーターは `redirect_uri`）だが、URL のパスは `/callback`、`/auth/callback`、`/oauth2/callback` などと付けるのが今も慣習になっている。

同じ考え方は Webhook にもある。決済会社に「決済が済んだらこの URL を叩いて」と、店のサーバーの URL を登録しておく。Webhook は「HTTP のコールバック」と呼ばれることもある。違いは、`/callback` は**ブラウザ**を経由して呼ばれ（表の道）、Webhook は相手の**サーバー**から直接呼ばれる（裏の道）こと。

**理解の確認**：「demo-app が指定した宛先（redirect_uri）に、auth がリダイレクトでアクセスさせるよう仕向けてくれることを、callback と呼んでいる」という理解で合っている。1点だけ補足すると、`/callback` に実際に要求を送るのはブラウザで、auth のサーバーは demo-app に直接つながない。auth は「この URL へ行って」という 302 を返すだけで、それをブラウザが開く（だから表の道）。auth のサーバーが自分から demo-app を呼ぶのが Webhook の形で、OIDC のログインの流れには出てこない。

### Q. `/userinfo` は、何か処理を実装するものではなく、OIDC をサポートする認証サーバー（OP）は必ずこのエンドポイントを実装しないといけない、ということで実装しているのか

半分そのとおりで、半分違う。

**必須かどうか**：OIDC の仕様（OpenID Connect Core 1.0）では、OP の誰もが必ず作るもの（15.1 Mandatory to Implement Features for All OpenID Providers）には入っていない。必須になるのは、知らない RP が自分で登録してくる「動的な OP」（15.2）。Discovery の `userinfo_endpoint` も「推奨」（RECOMMENDED）。ただ、Google、Microsoft、Keycloak など、実際の OP はほぼすべてが持っていて、RP のライブラリも「あるもの」として使うので、事実上の標準になっている。auth で作ったのは、それと、ステップ5への足がかりにするため。

（ついでに分かったこと：同じ 15.1 には「ID トークンの署名に RS256 を使えること」が必須として入っていて、Discovery の `id_token_signing_alg_values_supported` にも RS256 を必ず含める決まりがある。auth は ES256 しか出さないので、厳密には仕様に沿っていない。RP が自分の demo-app だけなので困らないが、他人の RP やライブラリをつなぐときには、RS256 も出せるようにする必要が出てくるかもしれない。）

**処理があるかどうか**：中身は小さいが、処理はある。「アクセストークンを見せてもらい、正しければ利用者の情報を返す API」で、やっていることは次のとおり。

1. `Authorization: Bearer` からトークンを取り出す
2. SHA-256 を `access_tokens` で引き、利用者と scope を得る
3. 期限内か、scope に openid があるかを確かめる
4. scope に応じて、返す項目（`preferred_username` など）を選ぶ

**ID トークンに同じ情報が入っているのに、なぜ別にあるのか**：

| | ID トークン | /userinfo |
| --- | --- | --- |
| 何を表すか | 「この人が、この時刻に、この方法でログインした」というログインの出来事 | 今の利用者の情報（プロフィール） |
| いつ作られるか | ログインのときに1回 | 呼ぶたびに、その時点の DB から |
| 誰が確かめるか | RP（署名、iss、aud、nonce） | OP（アクセストークン） |
| 向いているもの | ログインの証明。小さく保つ | 項目の多い情報、あとから変わる情報（メールアドレス、表示名など） |

ID トークンはログインの瞬間の写真のようなもので、あとでユーザー名を変えても、写真の中は古いまま。/userinfo は、そのとき聞けばそのときの値が返る。

**ステップ5への足がかり**：/userinfo は、OAuth 2.0 の側（委譲認可）の「アクセストークンで守られた API」の、一番小さな見本でもある。ID トークンは OIDC が足したもの、アクセストークンと、それで API を呼ぶのは OAuth 2.0 そのもの。ステップ5では、この形を一般の API に広げ、アクセストークンを「DB で引く乱数」のままにするか、JWT にして API が自分で確かめる形にするかを比べる。

4-d の demo-app では、ID トークンを確かめたあとに /userinfo も呼び、「ID トークンの sub と、/userinfo の sub が一致するか」を確かめる（OIDC Core 5.3.2 の決まり。別の利用者のトークンにすり替えられていないことの確認）。

### Q. 4-a、4-b、4-c、4-d といった工程は、どこで定義したものだったか。ロードマップのステップ4の最後か

ロードマップ（[docs/roadmap.md](../roadmap.md)）ではなく、ステップ4の文書（[docs/steps/4-oidc.md](../steps/4-oidc.md)）の「5. 実装」→「実装の小分け」の表で決めたもの。ロードマップにはステップごとのチェック項目だけを置き、1つのステップを何回に分けて書くかは、そのステップの文書に置いている（ステップ3の 3-a〜3-c も同じで、[docs/steps/3-passkey.md](../steps/3-passkey.md) の「実装」の節）。

| | 中身 |

| 4-b | client の登録（管理用のコマンド）、`/authorize`（照合、ログイン画面への寄り道と戻り、同意画面）、認可コード |
| 4-c | `/token`（client の認証、コード、PKCE、ID トークン、アクセストークン）、`/userinfo` |

### Q. 「署名の鍵を作る（共通基盤の Vault を変える）」は、auth が署名に使う鍵を Terraform で作り、その鍵を Vault に登録する、という立ち位置か。Vault は各アプリ（auth も認証の機能を持つ1つのアプリとして）で作ってよい、という整理だった記憶だが合っているか

前半はそのとおり。後半は少し違い、**Vault（金庫そのもの）は共通基盤に1つだけで、各アプリが作ってよいのは、その中に入れるシークレット（金庫の中の1件1件）**。

| もの | 誰が作るか | どこに書くか |
| --- | --- | --- |
| Vault（金庫）と、暗号化の鍵（マスターキー） | 共通基盤 | `oci-platform/terraform/vault.tf` |
| VM が Vault を読める権限（動的グループとポリシー） | 共通基盤 | 同じ `vault.tf` |
| シークレット（DB のパスワード、TOTP の鍵、ID トークンの署名の鍵など） | 各アプリ | `<アプリ>/infra/terraform/main.tf`（共通基盤の出力 `vault_id`、`vault_key_id` を使う） |

oci-platform の README の役割分担の表にも、「Terraform（アプリ）：そのアプリの LB のリスナー・バックエンド・セット、Vault のシークレット、DNS レコード」とある。

ID トークンの署名の鍵の流れ（DB のパスワード、TOTP の鍵と同じ経路）：

1. auth の Terraform が `tls_private_key`（ECDSA P-256）で鍵を作る。値は Terraform の state（OCI の Object Storage）に残る
2. 同じ Terraform が、それを共通基盤の Vault に `auth-oidc-signing-key` というシークレットとして入れる
3. `npm run deploy` のとき、app VM の上で `platform-secret auth-oidc-signing-key` が Vault から取り出し、`.env` の `OIDC_SIGNING_KEY` に書く（VM 自身の権限で読むので、取り出すための鍵は要らない）
4. コンテナが環境変数として読み、`src/jwt.ts` が署名に使う

見出しの「共通基盤の Vault を変える」は、金庫に1件足すという意味。金庫そのものは変えない。

### Q. demo-app をコンテナ化しない（手元で動かす）のは、何か意図があったのか。コンテナを浮かべてもよいと思った。demo-app だけ手元で動くと、処理が余計わかりづらくならないか

意図はあった。ステップ4の文書で「ステップ5で独立したリポジトリにするまでの仮住まい」と決めていて、共通基盤に載せるのはステップ5の項目（「demo-app を独立したリポジトリにし、共通基盤に載せる（今後のサービスのひな形）」）にしている。理由は2つ。

1. **共通基盤に載せると、OIDC と関係のない作業が増える。**LB のリスナー、DNS のレコード、ポートの台帳、client_secret を Vault に置く、デプロイのスクリプト。どれもステップ5でひな形を作るときに1回やれば済み、ステップ4のうちにやると、ステップ5で独立させるときにもう一度やり直すことになる。
2. **RP がどこにあっても、流れは同じだと見られる。**表の通信（リダイレクト）はブラウザが運ぶので、demo-app が手元でも本番の auth と話せる。裏の通信（`/token`、`/userinfo`）は、手元の demo-app から本番の auth へ、インターネット越しに届く。これは、別の場所で動く本物のサービスが auth を使うときと同じ形。

「分かりづらくならないか」について：流れ（図「ログイン」の 1〜14）は、demo-app が手元でも本番でも1つも変わらない。変わるのは demo-app の URL（`http://localhost:4000` か `https://demo.alphajinsei.com` か）と、それに合わせた redirect_uri の登録だけ。一方で、手元だと demo-app のログ（標準出力）をそのまま見られるので、`/callback` で何が起きたかは追いやすい。

### Q. 本番で実行した `ssh oci-app 'cd /opt/apps/auth && docker compose exec -T app node dist/admin.js create-client demo-app http://localhost:4000/callback "デモのアプリ"'` は、何をやっていたのか

本番の auth に「demo-app という RP がいて、戻り先はこの URL」と登録していた。先の問い（「demo-app を作るとき、auth に事前の登録（申請）が必要か」）の、その登録に当たる。Google なら、Google Cloud Console で OAuth クライアントを作る操作。

| 部分 | 意味 |
| --- | --- |
| `ssh oci-app '…'` | app VM の上で実行する |
| `cd /opt/apps/auth` | auth の `compose.yaml` がある場所へ |
| `docker compose exec -T app` | 動いている auth のコンテナの中で実行する。`-T` は端末をつながない（ssh にコマンドを渡す形では端末がないため） |
| `node dist/admin.js create-client` | 管理用のコマンド（`src/admin.ts` をビルドしたもの）の、client の登録 |
| `demo-app` | client_id |
| `http://localhost:4000/callback` | 登録する redirect_uri。`/authorize` と `/token` で、これと完全一致するかを照らす |
| `"デモのアプリ"` | 同意の画面に出す名前 |

中でしていること：

1. 32バイトの乱数で client_secret を作る
2. 本番の DB の `oauth_clients` に、client_id、secret の SHA-256、名前、redirect_uri を入れる
3. secret そのものは画面に1回だけ出す。DB にはハッシュしかないので、二度と表示できない

コンテナの中で実行するのは、本番の DB（HeatWave）が private subnet にあって VM からしかつながらず、DB の接続情報（Vault から取り出したパスワード）もコンテナの環境変数にしかないため。手元の DB と本番の DB は別なので、client の登録もそれぞれ要る（secret も別の値になる）。

redirect_uri が `http://localhost` なので、本番の auth（https）から、手元の PC で動く demo-app に戻せる。`admin create-client` は、https 以外では localhost だけを許している。

**理解の確認**：「新しく自分のアプリから auth に OIDC でログインする線を足すときに、事前に auth へ『自分のアプリから OIDC で接続できるようにしてほしい。client_id はこれ、redirect_uri（callback してほしいリダイレクト先）はこれ』と伝えるもの」という理解で合っている。auth の側から見ると、伝えられた内容を記録し、引き換えに client_secret（合言葉）を1回だけ渡す手続き。以後、`/authorize` ではその client_id と redirect_uri の組で照らし、`/token` では合言葉で相手を確かめる。

### （つまずき）本番の auth でログインしたつもりが、ID トークンの iss が `http://localhost:3001` だった

`npm run demo` が `EADDRINUSE: address already in use :::4000` で起動できていなかった。前に Claude が手元の通しの確認で起動した demo-app（手元の auth に向けたもの）が、4000番で動いたまま残っていて、ブラウザはそちらと、手元の auth（3001番）を通っていた。`iss` を見れば、どの OP が出した ID トークンかが分かる（RP が iss を確かめる理由そのもの）。古いほうを止めて、起動し直した。

## アクセストークンとリフレッシュトークン（ステップ5）

### Q. アクセストークン・リフレッシュトークンの概念は OIDC に内包されるものだと思っていたが、OIDC とステップを分けたのは、そうではなく、独立に一分野として存在するということなのか

包含の向きが逆で、**アクセストークンとリフレッシュトークンは OAuth 2.0 の概念**で、OIDC はそれを土台として借りている。OIDC が足したのは、ID トークン、/userinfo、Discovery など、「誰がログインしたか」を伝える部分。

| | 決めている仕様 | 何のためか |
| --- | --- | --- |
| 認可コード、アクセストークン、リフレッシュトークン、scope | OAuth 2.0（RFC 6749、6750） | アプリに、利用者の代わりに API を呼ぶ許可を渡す（委譲認可） |
| ID トークン、nonce、/userinfo、Discovery | OIDC（OAuth 2.0 の上に足したもの） | アプリに、誰がログインしたかを伝える（認証の結果の受け渡し） |

だから、OIDC を使えばアクセストークンも付いてくる（ステップ4の `/token` も、ID トークンと一緒にアクセストークンを返した）が、逆は成り立たない。OIDC なしで OAuth 2.0 だけを使う場面は多い。

- GitHub や Slack の API を、ボットや CI が呼ぶ（ログインは関係ない。「このリポジトリに書き込んでよい」という許可だけが要る）
- サーバー同士が、利用者なしでトークンをもらう（client credentials の流れ）
- スマホのアプリが、自社の API を呼ぶ

そしてトークンの扱いには、OIDC が何も言っていない広い領域がある。アクセストークンの形（参照か JWT か。RFC 9068）、API が確かめる方法（Introspection、RFC 7662）、取り消し（RFC 7009）、リフレッシュトークンの取り替えと盗難の検知（RFC 9700）、盗まれても使えないようにする仕組み（DPoP、RFC 9449）。どれも OAuth 2.0 の側の仕様で、OIDC とは独立に積み上がってきた。

ステップを分けたのはこのため。

- ステップ4：**認証の受け渡し**。ID トークンを作り、RP が確かめる。アクセストークンは「/userinfo を呼べる乱数」として最小限だけ出した。
- ステップ5：**API の認可**。アクセストークンで API を守る、期限を切る、リフレッシュする、取り消す。ログインの瞬間ではなく、そのあと何時間・何日も続く「API を呼び続ける」側の話。

→ [番外編：アクセストークンとリフレッシュトークンの来歴](../history/5-tokens.md)、OAuth と OIDC の関係は [番外編：OAuth 2.0 と OpenID Connect の来歴](../history/4-oauth-oidc.md) の 7 節「OAuth 2.0 と OIDC の使い分け」

**理解の確認**：「含まれる向きが逆」は言い過ぎだった。ユーザーの整理のとおり、アクセストークンは OAuth 2.0 に含まれ、OAuth 2.0 は OIDC におおむね含まれる（OIDC の流れは OAuth 2.0 の流れそのものを使う）ので、結果としてアクセストークンは OIDC の世界にも含まれる。言いたかったのは、ユーザーの言い直しの「OAuth 2.0 の時点でアクセストークンの概念は定義されており、OIDC が独自に定義した領域にはアクセストークンは含まれない」のほう。加えて、OAuth 2.0 は OIDC の外でも単独で使われる（GitHub の API をボットが呼ぶ、など）。ステップの分け方は「ステップ4（OIDC）で扱いきれなかった OAuth 2.0 の領域を、ステップ5で回収する」という理解で合っている。

### Q. API キーを発行する方式はよくある（Claude の API もこのタイプ）。最近はコンソールで期限を付けたり即時に失効させたりできる。来歴の「API キー」は、発行したらそれきりで無期限に使える、ゆるい設計を指しているのか。「安く確かめるか、毎回内部に問い合わせるか」のトレードオフで言えば、昔の API キーは問い合わせ不要で簡単な側、失効や期限の付いた最近の API キーは問い合わせが要る側、ということか。単純に API キーを機能拡充する方向性もあったのか

前半（来歴の「API キー」は、範囲も期限もなく、取り消しの管理も弱かった昔のものを指している）はそのとおり。ただ、トークンの形で分けると、**昔の API キーも今の API キーも、どちらも「毎回記録を引く」側**にいる。

API キーは意味のない長い乱数なので、文字列を見ただけでは、本物か、誰のキーかが分からない。サーバーは要求のたびに、キーの一覧（DB）を引いて「どのアカウントのキーか」を知る必要がある（そうしないと、課金も利用の上限も数えられない）。昔のキーも、ここは同じだった。昔のキーで「簡単」だったのは、使う側（キーを1つヘッダーに入れるだけ）の話で、サーバーの確かめ方は安くなかった。

| | 昔の API キー | 今の API キー（Claude の API、Stripe、GitHub の Personal Access Token など） |
| --- | --- | --- |
| 中身 | 乱数 | 乱数 |
| サーバーの確かめ方 | 毎回、記録を引く | 毎回、記録を引く（キャッシュで速くはする） |
| 足りなかったもの | 範囲、期限、取り消しの管理 | 足された（範囲を絞る、期限、管理画面ですぐ取り消す） |

つまり、毎回記録を引いているので、取り消しは「記録を消す」だけで即座に効く。今の API キーの即時の失効は、その性質を管理画面から使えるようにしたもの。

**API キーを育てる方向性**は実際にあって、今も主流の1つ。GitHub の Personal Access Token は、2022年に、範囲をリポジトリ単位まで絞れて期限も付けられる「fine-grained」版が出た。Stripe には、操作を絞った「restricted key」がある。

それでも OAuth が要った理由は、**誰の権限を、誰が持つか**が違うから。

| | API キー | OAuth のアクセストークン |
| --- | --- | --- |
| 誰の権限か | 開発者自身のアカウント | 利用者のアカウント |
| 誰が使うか | 開発者自身のプログラム | よそのアプリ |
| どう渡すか | 管理画面から、開発者が手で写す | 利用者が同意の画面で許し、自動で発行される |
| 例 | Claude の API を、自分のスクリプトから呼ぶ | 写真の印刷サービスが、利用者の Google フォトを読む |

自分のアカウントを自分で使うなら API キーで足りる。他人（利用者）のアカウントを代わりに使うのに、「管理画面で API キーを作って、このアプリに貼ってください」と頼むのは、パスワードを渡させるのに近い（実際、昔はそうしていたサービスもある）。OAuth は、この「貸す」手続きを、同意の画面と自動の発行で安全にしたもの。

### Q. 来歴の OAuth 1.0 の節を読むと、「失効や期限の付いた最近の API キー」と言ったのは、このアクセストークンのことか。Claude のコンソールでは API キーと表示されるが、言葉の問題か

半分は言葉の問題で、半分は違う。

- **仕組みは似ている。**どちらも、意味のない乱数をヘッダーに入れて送り、サーバーが記録を引いて確かめる。取り消しは記録を消すだけ。ここだけを見れば、今の API キーは「手で発行する、長生きのアクセストークン」と言える。GitHub が Personal Access Token（個人用のアクセストークン）と名付けているのも、その見方。
- **発行のされ方と、表す権限が違う。**Claude のコンソールの API キーは、開発者が自分に発行する（同意の画面も、第三者のアプリもない）。OAuth 1.0 のアクセストークンは、利用者がよそのアプリに、同意の画面を通して発行させる。そのため OAuth 1.0 のトークンには、「どのアプリに」「どの利用者が」許したかの2つが結び付いている。

なので、前の問いの「最近の潮流としての API キー」は OAuth 1.0 のアクセストークンのことではなく、API キーの系統が育ったもの。OAuth 1.0 のアクセストークンは「他人の権限を貸す」ための、別の系統の始まり。2つの系統は、仕組み（乱数と記録）では近づいている。

### Q. OAuth 1.0 の「毎回の署名」が分からない。秘密を保持する主体、署名が行われるタイミングと場所、検証されるタイミングと場所は。クライアント側で署名、サーバー側で検証か。サーバー側で毎回検証する負荷が嫌われたのか。それが「API は、毎回トークンを記録と照らす必要があった」のことか

クライアント（アプリ）側で署名し、サーバー（Twitter など）側で検証する、で合っている。嫌われたのは、検証の計算の重さではなく、主に2つ：**クライアントの開発者にとって署名が難しかったこと**と、**API が毎回、認可サーバーの DB にある秘密を引かなければならなかったこと**。後者が「毎回トークンを記録と照らす必要があった」の意味。

**秘密を持つのは誰か**：秘密は2つあり、どちらも**アプリとサーバーの両方が持つ**（共通の秘密。ステップ3の公開鍵の署名と違い、検証する側も同じ秘密を持つ）。

| 秘密 | いつもらうか | 何に結び付くか |
| --- | --- | --- |
| consumer secret | アプリをサービスに登録したとき（ステップ4の client_secret に当たる） | アプリ |
| token secret | 利用者が同意したあと、アクセストークンと一緒に | アプリ × 利用者 |

**署名のタイミングと場所**：アプリが、API を呼ぶ**要求のたびに**、アプリの中で。

1. 署名の対象の文字列を作る。HTTP のメソッド（`POST`）、URL、パラメーターを全部（ツイートの本文、`oauth_consumer_key`、`oauth_token`、`oauth_timestamp`（今の時刻）、`oauth_nonce`（使い捨ての乱数））を名前の順に並べ、決まった方法でエンコードしてつなぐ
2. 鍵 ＝ consumer secret と token secret を `&` でつないだもの
3. HMAC-SHA1 を計算して、`oauth_signature` として `Authorization` ヘッダーに入れる。秘密そのものは送らない

**検証のタイミングと場所**：サーバーが、要求を**受けるたびに**、API の側で。

1. ヘッダーの `oauth_consumer_key` と `oauth_token` から、2つの秘密を DB で引く
2. 届いた要求から、同じ手順で署名の対象の文字列を作り直し、HMAC を計算する
3. 届いた `oauth_signature` と一致するかを見る
4. `oauth_timestamp` が今に近いか、`oauth_nonce` が前に使われていないか（使った nonce も記録しておく必要がある）

**なぜ署名したか**：2007年当時、HTTPS は今ほど当たり前ではなかった（証明書が有料で、暗号の処理も重いとされていた）。平文の HTTP で要求を盗み見られても、秘密は流れないので、トークンを盗んだだけでは新しい要求を作れない。要求の中身（ツイートの本文）を途中で書き換えても、署名が合わなくなる。nonce と時刻で、同じ要求の使い回し（リプレイ）も防ぐ。

**何が嫌われたか**：

- **難しい。**並べ方、エンコード（スペースを `%20` にするか `+` にするか、など）を1つ間違えると「署名が合わない」とだけ返り、どこが違うか分からない。開発者の一番の不満はこれだった。
- **API が認可サーバーの DB から離れられない。**検証には秘密が要り、秘密は認可サーバーの DB にある。Yahoo!、Google、Microsoft のように、API のサービスが何十とある会社では、すべての API が要求のたびに、トークンの DB を引ける必要があった。WRAP（2009年）は、ここを解くために、Bearer トークン（署名なし、HTTPS 任せ）と、短命のアクセストークンを持ち込んだ。WRAP と同じ時期に Microsoft は、認可サーバーが署名して中身を書いた小さなトークンの形（Simple Web Token）も出していて、API が DB を引かずに確かめられる方向へ進んでいた。

同じ「要求ごとの署名」は今も AWS の API で使われている（アクセスキー ID とシークレットアクセスキーで、要求のたびに署名する Signature Version 4）。SDK が署名を肩代わりするので、開発者が難しさに触れずに済んでいる。

### Q. そもそも内部の通信（DB の参照や、認可サーバーへの問い合わせ）は、何を処理するときに発生するのか。失効の確認に DB 参照が要るのか。素朴には、API キーが有効であることを確認するのにも DB 参照が要る気がして、であればコストは変わらないように思ったが、そういうわけではないのか

素朴な感覚は、**乱数のトークンについては正しい**。乱数なら、有効かを確かめるのにもどのみち DB を引くので、失効の確認は追加の費用なしで付いてくる。コストが変わるのは、トークンを「中身を書いて署名したもの」（JWT）にしたとき。肝はこの1点：**内部の通信が要るのは、要求を受けた API が、手元のトークンだけでは分からないことを知りたいとき**。

API が要求のたびに知りたいことは4つある。

1. 本物か（自分たちが発行したもので、偽造ではないか）
2. 誰の、どの範囲の許可か
3. 期限内か
4. 取り消されていないか

トークンの形によって、手元で分かるものが変わる。

| トークンの形 | 手元で分かる | 記録を引かないと分からない |
| --- | --- | --- |
| 意味のない乱数（API キー、ステップ4の auth のアクセストークン） | なし | 1〜4 の全部 |
| 中身を書いて署名したもの（JWT） | 1（公開鍵で署名を確かめる）、2・3（中身に書いてある） | 4 だけ |

- **乱数**：文字列そのものに意味がないので、何を知るにも記録を引く。だから取り消しは「行を消す」だけで、次の要求から即座に効く。追加の費用はない。ユーザーの感覚どおり。
- **署名したもの**：1〜3 は手元で分かるので、記録を引かずに済む。ただし 4 だけは分からない。取り消しは**発行したあとに起きた出来事**で、発行のときに書いて署名した中身には入りようがないから。4 も確かめたければ、結局は記録（取り消しの一覧）を引くことになり、署名した意味が薄れる。そこで、4 を確かめるのはあきらめて、期限を短く（5分〜1時間）して、取り消しの遅れをその範囲に収める。

身近な例で言うと、乱数は「会員番号」（受付で名簿を引かないと何も分からない。名簿から消せば即座に入れない）、署名したものは「透かし入りの入場券」（係員は券を見るだけで、本物か、どの席か、いつの公演かが分かる。ただ、券を出したあとに『この券は取り消し』と決めても、券を見るだけでは分からない）。

**コストの違いは、計算よりも「つながり」**。DB を1回引く手間そのものは小さい（ミリ秒）。問題になるのは、API が増えたとき。

- すべての API が、認可サーバーの DB（または問い合わせの口）にネットワークでつながっている必要がある
- 認可サーバーが遅い・落ちると、すべての API が遅い・落ちる
- 要求の数だけ、認可サーバーに負荷がかかる

API が1つ（ステップ4の `/userinfo` のように、auth 自身の中にある）なら、DB を引くのは何の問題もない。API が別のサーバー、別のサービスに散らばると、署名したトークンの「記録を引かずに済む」が効いてくる。間を取る方法もあって、問い合わせの結果を数十秒キャッシュする（取り消しの遅れは、その数十秒になる）。

### Q. （理解の確認）開発者が自分で使うのが API キー、利用者が同意を通じて払い出させるのがアクセストークン、という感じか。OAuth 1.0 の「共有する秘密」は、共通鍵的な概念と理解した

どちらもその理解で合っている。

- **API キーとアクセストークン**：違いは仕組みではなく、出どころ（誰の権限を、誰に渡すか）。開発者が自分のアカウントの権限を自分のプログラムに持たせるのが API キー、利用者が自分のアカウントの権限を、同意の画面を通してよそのアプリに貸すのがアクセストークン。
- **共有する秘密**：共通鍵そのもの。HMAC は、同じ鍵を持つ者どうしでだけ計算が合う仕組みで、署名する側（アプリ）と確かめる側（サーバー）が同じ鍵を持つ。ステップ3のパスキー、ステップ4の ID トークンは公開鍵の署名（秘密鍵を持つのは署名する側だけ、確かめる側は公開鍵）なので、そこが違う。共通鍵なので、確かめる側（サーバー）も署名を作れてしまう。だから「誰が作ったか」を第三者に示すことはできず、「この2者の間で、相手が作った」ことしか言えない。

### Q. （理解の確認）乱数で発行される API キーやアクセストークンは毎回確認する必要があるが、JWT は何を許可されているかの中身まで書かれているので、ユーザーが「以前この操作をしてよいと言われています」とサーバーに自己申告するような形ということか。サーバーはその内容を全部確かめるまでする必要はなく、署名の検証だけで確認できる

大筋で合っている。2点だけ言い直すと、より正確になる。

1. **自己申告ではなく、「auth が書いて判を押した許可証」を見せている。**中身を書いたのは持ち主（アプリや利用者）ではなく auth で、auth の秘密鍵で署名してある。持ち主は中身を1文字でも書き換えると署名が合わなくなるので、言い値を足すことはできない。「自己申告」と言うと持ち主が書いたように聞こえるが、実際は「発行者のお墨付きの書類を、持参している」。前の項目のたとえで言う「透かし入りの入場券」。
2. **確かめるのは署名「だけ」ではない。**署名で「auth が書いたもので、書き換えられていない」が分かったあと、API は中身を自分の基準と照らす：期限（exp）が切れていないか、自分宛て（aud）か、要求された操作に scope が足りているか。どれも手元の計算で済み、記録を引かないのがポイント。demo-app の `verifyIdToken`（[demo-app/src/rp.ts](../../demo-app/src/rp.ts)）が ID トークンに対してやっている、署名 → iss → aud → exp → … の順番と同じ形。

確かめないのは「4. 取り消されていないか」だけで、これは券を見ても分からないので、短い期限で補う。

### Q. 「署名したもの ＝ JWT」と読めたが、ほぼイコールととらえて問題ないか。承認された内容を署名したもの、というのは任意のフォーマットを取りうるが、デファクトスタンダードとして JWT が主流、ということか

その理解で合っている。「中身を書いて署名したトークン」という考え方の、今の主流の形が JWT で、ほかの形もある。

| 形 | いつ | 中身の書き方 | 今の位置 |
| --- | --- | --- | --- |
| SAML のアサーション | 2005年（SAML 2.0） | XML に XML 署名 | 企業のシングルサインオンで今も現役。JWT の先輩にあたる |
| SWT（Simple Web Token） | 2009年ごろ | `key=value&...` に HMAC | Microsoft が OAuth WRAP の時代に使った。JWT に置き換わった |
| **JWT** | 2015年（RFC 7519） | JSON を base64url にして、JWS で署名 | OIDC の ID トークン、OAuth のアクセストークン（RFC 9068）の標準 |
| CWT | 2018年（RFC 8392） | JSON の代わりに CBOR（バイナリ）。中身の考え方は JWT と同じ | 小さい機器（IoT）向け |
| PASETO | 2018年ごろ | JWT の「alg を選べる」ことを危険と見て、版ごとに方式を固定 | JWT への批判から生まれた代替。使う所はあるが少数 |
| Macaroons | 2014年（Google の論文） | 持ち主が、受け取ったトークンに「さらに狭める条件」を足して他人に渡せる | 考え方は面白いが、一般には広まっていない |

JWT が主流になったのは、形が優れているからというより、OIDC が ID トークンに採用し、主要な製品とライブラリがそろったから。署名の仕組み（JWS）と鍵の配り方（JWKS）が決まっていて、ID トークンのために用意したものを、アクセストークンにもそのまま使えた。

なお、Web アプリの「署名付きの Cookie」（Rails などのセッションを Cookie に入れる方式）も、「中身を書いて署名し、サーバーは記録を引かない」という同じ考え方で、こちらは JWT ではない独自の形が多い。

### Q. 来歴 4 節（OAuth WRAP）の違いがよく分からない。リフレッシュトークンは、アクセストークンの期限が切れたら新しいアクセストークンと取り換える操作を許すトークンか。アクセストークンは多数利用される前提で数時間の期限を持たせ、切れたらリフレッシュトークンで更新させる仕組みか。参照を渡す型なら（アクセストークンもリフレッシュトークンもこれに含まれる理解）、どのみち認可 DB への確認の内部通信が走るので、2つに分けてもあまりメリットがないように思った。実はアクセストークンとリフレッシュトークンで中身に差があるのか（アクセストークンは Bearer で、リフレッシュトークンはもっとリッチな JWT など）

前半の理解（リフレッシュトークン＝切れたアクセストークンを取り換えるための券）は合っている。期限は、アクセストークンが数分〜1時間（Google は1時間）、リフレッシュトークンが数日〜数か月が多い。

疑問の後半も鋭く、**「両方とも乱数で、API が毎回 DB を引く」なら、コストの面のメリットはほぼ消える。**4 節の「アクセストークンは安く確かめる」は、API が記録を引かずに済む形（または、問い合わせの結果をしばらくキャッシュする）を前提にしている。実際、WRAP を早くから使った Microsoft の Azure ACS は、アクセストークンを SWT（HMAC で署名した、中身入りのトークン）にしていた。記事の 6 節で「WRAP の2本立てが、ここで本来の力を出す」と書いたのは、この意味。

それでも、両方とも乱数のままでも残るメリットがある。コストではなく、**漏れたときの被害の大きさ**の違い。

| | アクセストークン | リフレッシュトークン |
| --- | --- | --- |
| 見せる相手 | API（いくつもあるかもしれない）に、要求のたびに | auth の `/token` にだけ、たまに |
| 漏れやすさ | 高い。送る回数も先も多い。API のログ、途中の中継、ブラウザの中など | 低い。アプリのサーバーの中に置いたまま、auth にしか送らない |
| 漏れたら | 期限（〜1時間）まで使われる | client_secret がないと使えない（client_secret を持つアプリの場合。持てないアプリの話が 7 節） |
| 使うときに確かめること | 期限、scope | 取り消されていないか、利用者がまだいるか、同意が残っているか。ここで初めて、新しいアクセストークンを出すかを判断し直す |

つまり、**よく持ち歩くもの（アクセストークン）は寿命を短くし、長生きするもの（リフレッシュトークン）は持ち歩かない**、という分け方。家の合鍵を毎日持ち歩くのではなく、その日限りの入館証を毎朝窓口で受け取るのに近い。入館証を落としても翌日には使えず、窓口は「この人をまだ入れてよいか」を毎朝判断し直せる。

**中身の差について**：推測とは逆で、リフレッシュトークンのほうが乱数（opaque）であることがほとんど。

- リフレッシュトークンを読むのは、出した auth 自身だけ。中身を書いておく必要がない（auth は自分の DB を引けばよい）。
- リフレッシュトークンは取り消しを必ず確かめたいもの。どのみち記録を引くので、署名して中身を書いても得がない（1つ前の項目の4つのうち、4 を毎回確かめるなら乱数で十分）。
- 中身を JWT にする意味があるのは、auth 以外（API）が読むアクセストークンのほう。

一部の製品（Keycloak など）はリフレッシュトークンも JWT の形で出すが、使うときはやはりサーバー側の記録を引く。「Bearer」は RFC 6750 でアクセストークンの使い方として決めた言葉で、client_secret を持つアプリのリフレッシュトークンは、持っているだけでは使えないので、厳密には Bearer ではない。

### Q. （理解の確認）来歴 5 節の「参照」は本当に UUID 的な乱数を渡しているだけのトークン、「値」は実際に何を認可しているかなどの情報も書かれたトークン、ということか

その理解で合っている。補足すると、「値」は情報を書いただけでなく**署名してある**ことが本質。署名がなければ、持ち主が中身を書き換えられるので、API は信じられない。

- 参照：乱数そのものに意味はなく、「auth の DB のこの行を見て」という合札。ステップ4の auth のアクセストークン（32バイトの乱数。DB には SHA-256 だけ）。
- 値：誰の、どの scope、いつまで、を書いて署名したもの。auth の ID トークンがこの形（アクセストークンではないが、形は同じ）。

### Q. 来歴 6 節を読むと、結局リフレッシュトークン・アクセストークンのどちらも JWT にするのが流行った、ということか。以前は仕様が難解なので敬遠された、という趣旨の記載があったが、仕様が統一されたのと、インターネットの発展で情報収集が容易になったこともあって、開発者の労力が下がってハードル低く実装できるようになった、ということか。また、これまで参照・値と呼んできたが、opaque 方式・JWT 方式とそれぞれ呼ばれているのか

1点目は訂正がある。**JWT が広がったのはアクセストークンで、リフレッシュトークンは今も乱数がほとんど**（理由は1つ前の項目）。

2点目：敬遠された「難解さ」は、OAuth 1.0 の**アプリが要求のたびに署名する**ことだった（3 節）。JWT はそれが易しくなったのではなく、**難しい所を、別の人に移した**。

| | OAuth 1.0 の署名 | JWT のアクセストークン |
| --- | --- | --- |
| 署名するのは | アプリ（何千もいる、よそのアプリの開発者） | auth（1か所。発行のときに1回だけ） |
| アプリがすること | 要求のたびに、パラメーターを並べて HMAC を計算 | 受け取った文字列を、ヘッダーに入れて送るだけ |
| 確かめるのは | API（記録から共通の秘密を引いて、計算し直す） | API（公開鍵で。ライブラリが数行でやる） |
| 難しさを負うのは | すべてのアプリの開発者 | auth とライブラリの作者（少数の専門家） |

アプリの開発者から見ると、JWT のアクセストークンは「意味の分からない文字列をそのまま送る」だけで、乱数のトークンと何も変わらない。中身が JWT かどうかを気にするのは、auth と API だけ。そして API の側も、`jose` などのライブラリと JWKS（鍵の配り方の決まり）がそろったので、自分で暗号を書かずに済む。情報が集めやすくなったことも助けにはなったが、大きいのはこの「難しさの置き場所」の変化。

3点目の呼び方：**「opaque トークン」と「JWT」**が、いちばんよく見る呼び方。ほかに次の言い方もある。

| 記事の言い方 | よく見る呼び方 |
| --- | --- |
| 参照 | opaque token、reference token（参照トークン。Duende IdentityServer などの製品の用語）、by-reference |
| 値 | JWT access token、self-contained token（自己完結トークン）、structured token、by-value |

「値」の形はほぼ JWT なので、実際の会話では「opaque か JWT か」と言うことが多い。

### Q. 来歴 7 節のリフレッシュトークンの取り替え（rotation）がよく分からない。リフレッシュトークンはアクセストークンの取り換え用途という理解だった。それに加えて、リフレッシュトークンを使うと、新しいアクセストークンと、新しいリフレッシュトークンが払い出される仕組みになるということか

その理解で合っている。リフレッシュの返事に、新しいアクセストークンと**新しいリフレッシュトークンの両方**が入り、使った古いリフレッシュトークンはその場で無効になる。

取り替えない場合と比べると：

| | 取り替えない | 取り替える（rotation） |
| --- | --- | --- |
| リフレッシュの返事 | 新しいアクセストークンだけ | 新しいアクセストークン ＋ 新しいリフレッシュトークン |
| リフレッシュトークン | 同じものを、期限（数か月）まで何度でも使う | 1回使うと無効。毎回、新しいものに替わる |
| 盗まれたら | 期限まで、持ち主と盗んだ人の両方が使い続けられる。気づけない | 持ち主と盗んだ人のどちらかが先に使うと、もう片方が使ったときに「無効にしたはずの古いトークン」が来る → 盗難と分かる |
| 盗難に気づいたら | ― | その系統（同じログインから続いたリフレッシュトークン全部）を取り消す。持ち主ももう一度ログインし直すことになるが、盗んだ人も締め出せる |

流れで書くと（RT ＝ リフレッシュトークン、AT ＝ アクセストークン）：

1. ログイン：auth が AT1 と RT1 を出す
2. AT1 が切れた：アプリが RT1 を出す → auth は RT1 を無効にし、AT2 と RT2 を出す
3. AT2 が切れた：アプリが RT2 を出す → AT3 と RT3
4. もし攻撃者が RT1 を盗んでいて、今ごろ使うと：RT1 はもう無効 → 「使い終わった RT が来た」→ RT1〜RT3 の系統を全部取り消す

ステップ4の認可コードで、「使用済みのコードが来たら異常」と同じ考え（ステップ4ではそこまで作らず、断るだけにした。ステップ5では系統ごと取り消すところまで作る）。仕様の上では、RFC 6749 の 6 節が最初から「新しいリフレッシュトークンを出してもよい（MAY）」と書いていて、それを「public client では取り替える（か、送り手に結び付ける）べき」と強めたのが 2025年の RFC 9700。

→ [番外編：アクセストークンとリフレッシュトークンの来歴](../history/5-tokens.md) の 7 節

### Q. （理解の確認）現代的なトークンの配り方は、次の整理で合っているか。アクセストークン：JWT 形式が主で、署名付きの値が入っている（サーバーが発行した印鑑付きの許可証を、クライアントが提示するイメージ）。サーバーは認可サーバーに問い合わせず、署名の検証さえすれば何が実行できるかを判定できる。たいてい短命にする（取り消しの確認を不要にして取り回しを良くすることとのトレードオフ）。リフレッシュトークン：opaque 形式が主で、参照が入っている。短命なアクセストークンの再発行を担う。取り消しの確認を毎回挟むので、JWT にする意味が薄く、opaque が主流

その整理で合っている。3点だけ補足する。

1. **「サーバー」は2つに分けて言うと正確になる。**トークンを発行するのは認可サーバー（auth）、提示されて確かめるのは API（リソースサーバー）。整理の「サーバー側は、いちいち認可サーバーに問い合わせることなく」の「サーバー」は API のこと。
2. **確かめるのは「署名さえ」より少し多い。**署名のあとに、期限（exp）、自分宛てか（aud）、scope が足りているか、を見る。ただ、どれも手元の計算なので、「問い合わせが要らない」という整理の要点はそのまま。
3. **「アクセストークンは JWT が主」は、「JWT が広く使われる」くらいに弱めておくのが正確。**認可サーバーの製品やクラウドの ID の基盤（Auth0、Okta、Microsoft Entra ID、Amazon Cognito など）は JWT を出すことが多い。一方で、opaque のアクセストークンも今も普通にある（GitHub のトークンや、ステップ4の auth）。API が自分の中に1つだけなら、opaque で DB を引くほうが簡単で、取り消しも即座に効くから。「API が多い・散らばっているなら JWT、少ない・同じ場所なら opaque でもよい」が実際の選び方。

リフレッシュトークンの整理（opaque が主。読むのは auth だけで、取り消しを必ず確かめたいので、中身を書いても得がない）は、そのとおり。

### Q. リフレッシュトークンの取り替えを見て思ったが、結局リフレッシュトークンもアクセストークンも、同じ頻度のライフサイクルをたどることになった、という理解で合っているか。形式上は、アクセストークンは短命、リフレッシュトークンは一定期間有効という位置づけだが、アクセストークンの再発行のタイミングでリフレッシュトークンも再発行されるので、「一定期間有効」の猶予を活かさずに、アクセストークンの発行のタイミングでリフレッシュトークンも再発行される、ということか

**文字列が替わる頻度**については、その理解で合っている。取り替えをすると、リフレッシュトークンの文字列は、アクセストークンを出し直すたびに替わる。

ただし、**「一定期間有効」の猶予は、なくなっていない。**取り替えで変わったのは「同じ文字列が長生きする」ことで、「ログインし直さずに続けられる期間が長い」ことは残っている。分けて考えると分かりやすい。

| | アクセストークン | リフレッシュトークン（取り替えあり） |
| --- | --- | --- |
| 文字列が替わるのは | 期限が切れて、出し直すとき | 使うたび（＝アクセストークンを出し直すとき） |
| 1本の期限 | 短い（〜1時間） | 長い（例：発行から14日） |
| 期限が効いてくる場面 | 使っている最中でも、1時間で切れる | **アプリを使っていない間**。使わなければリフレッシュも起きないので、最後に受け取った RT が期限まで待っている |

猶予が生きるのは、アプリを使っていない間。たとえば、夜にアプリを閉じて、3日後に開いたとする。

- アクセストークンは、とっくに切れている
- 最後に受け取ったリフレッシュトークン（14日もつ）は、まだ有効 → これを出すと、新しい AT と RT が返り、ログインし直さずに使える
- 14日以上開かなければ、リフレッシュトークンも切れて、ログインし直し

つまり、使っている間は AT と同じ周期で入れ替わり、使っていない間は長い期限で待つ。リフレッシュトークンの長い期限は「使わずにいても、ここまでは続けられる」という猶予として効いている。

製品によっては、期限を2つに分ける。

- **使わずにいられる期限**（inactivity / idle）：1本ごとの期限。取り替えるたびに、新しい RT はそこから数え直す（例：14日）。使い続ける限り延びていく
- **系統全体の期限**（absolute）：最初のログインから数える上限（例：90日）。取り替えても延びない。これを過ぎると、使い続けていてもログインし直し

取り替えなしなら、1本の RT を数か月使い回すので、この2つは同じものになる。取り替えありでは、「1本の文字列の寿命」と「系統（ログインの続き）の寿命」が分かれる、と言える。ステップ5の実装では、この2つの期限をどうするかも決める。

### Q. （理解の確認）トークンの整理を自分の言葉でまとめ直した。違和感がなければ、来歴の記事に「筆者の理解」として書いておいてほしい。また、取り替えをしてもリフレッシュトークンの長い期限が効くのは、しばらく使わない利用者にとって利がある、ということか

まとめは、1か所を除いてそのまま合っている。来歴の記事の 11 節「筆者の理解」に、ほぼ原文のまま載せた。

直した1か所：最初の版は、リフレッシュトークンについて「**API サーバーから**認可サーバーへのトークンの取り消しの確認を毎回挟む」と書いていた。リフレッシュトークンは API サーバーには一度も見せない。**クライアント（アプリ）が認可サーバーの `/token` に直接出す**もので、認可サーバーが受け取るたびに自分の記録で取り消しを確認する。API サーバーが見るのはアクセストークンだけ。これを「クライアントが認可サーバーに直接出すもので、認可サーバーは受け取るたびに取り消しを確認することになる」と直した。

| トークン | 誰が出す | 誰が受け取って確かめる |
| --- | --- | --- |
| アクセストークン | クライアント | API サーバー（JWT なら手元で、opaque なら記録を引いて） |
| リフレッシュトークン | クライアント | 認可サーバーだけ（記録を引いて、取り消しを確かめる） |

取り替えと長い期限の件は、その理解で合っている。しばらく使わない利用者が、ログインし直さずに続けられるのが利点。これも 11 節の最後に1行足した。

### Q. 図「期限切れとリフレッシュ」では、GET /userinfo の先も POST /token の先も同じ auth になっているが、前者は API サーバーとしての auth、後者は認可サーバーとしての auth、という異なる位置づけであるという理解で合っているか

その理解で合っている。auth は1つのプログラムだが、2つの役を兼ねている。

| 口 | 役 | 受け取るもの | 確かめ方 |
| --- | --- | --- | --- |
| `/userinfo` | API（リソースサーバー） | アクセストークン | 署名と中身を手元で（ステップ5の JWT）。トークンの表は引かない |
| `/token`、`/revoke` | 認可サーバー | リフレッシュトークン（と client_secret） | 自分の記録を引いて、取り消し・使用済み・期限を確かめる |

OIDC では、`/userinfo` は OP（認可サーバー）が持つ API と決まっているので、同じ auth の中にある。ふつうの API（たとえば demo-app が自分のデータを返す API）は、認可サーバーとは別のサーバーにあり、その場合も流れは同じで、`/userinfo` を呼んでいた矢印の宛先が、その API のサーバーになるだけ。

この区別が分かりにくかったので、設計の文書（[docs/steps/5-tokens.md](../steps/5-tokens.md)）の図では、auth を「auth の /userinfo（API）」と「auth の /token（認可サーバー）」の2本の線に分けた。

### （つまずき）壊れたアクセストークンで `/userinfo` が 500 になった

5-a で `/userinfo` を JWT の検証に替えたあと、`Authorization: Bearer abc.def.ghi` を送ると 500 になった。原因は、検証の関数が投げた例外の文面を、そのまま `WWW-Authenticate` ヘッダーに入れていたこと。`abc` を base64url として読むと意味のないバイト列になり、`JSON.parse` の例外の文面にそれが混ざる。制御文字や引用符を含む値はヘッダーに入れられないので、Hono が返事を作るところで落ちた。

直し方：投げる文面を決まった言葉（`not a JWT`、`unexpected typ`、`unexpected alg` など）だけにし、相手が送った値（typ や alg の中身）を混ぜない。ヘッダーに引用符を入れられると、ヘッダーの形を壊したり、別の項目を書き足したりできる（ヘッダーの注入）ので、500 で済んでいたのはむしろ運がよかった。**相手が送った値を、そのまま返事のヘッダーに写さない**、が教訓。

### Q. これが OAuth 2.0・OIDC の実装の定番なのか。たとえば `/token` で、リフレッシュトークンの依頼と、認可コードの引き換えの両方を受けるなど

定番で、OAuth 2.0 の本体（RFC 6749）がそう決めている。OAuth 2.0 の口は、大きく2つしかない。

| 口 | 通り道 | 誰が呼ぶ | 役目 |
| --- | --- | --- | --- |
| 認可エンドポイント（`/authorize`） | 表（ブラウザがリダイレクトで運ぶ） | 利用者のブラウザ | 利用者にログインと同意をしてもらう |
| トークンエンドポイント（`/token`） | 裏（client のサーバーから直接） | client | 「許可の証拠」と引き換えに、トークンを出す |

`/token` に来る要求は、どれも「client を認証して、許可の証拠を確かめて、同じ形の返事（access_token、token_type、expires_in…）を返す」で共通している。違うのは**何を許可の証拠として出すか**だけなので、それを `grant_type`（grant ＝ 許可）で分けて、1つの口で受ける。

| grant_type | 許可の証拠 | 決めた仕様 |
| --- | --- | --- |
| `authorization_code` | 認可コード（＋ PKCE の verifier） | RFC 6749 4.1（ステップ4） |
| `refresh_token` | リフレッシュトークン | RFC 6749 6（ステップ5） |
| `client_credentials` | なし（client 自身の権限。利用者がいない、サーバー同士の通信） | RFC 6749 4.4 |
| `password` | 利用者のパスワードそのもの | RFC 6749 4.3。今は使うなとされている（RFC 9700） |
| `urn:ietf:params:oauth:grant-type:device_code` | テレビなどの機器に出したコード | RFC 8628 |
| `urn:ietf:params:oauth:grant-type:jwt-bearer` | 別の発行者が署名した JWT | RFC 7523 |
| `urn:ietf:params:oauth:grant-type:token-exchange` | 別のトークン | RFC 8693 |

実際の製品も同じ形で、URL の名前が違うだけ（Google は `https://oauth2.googleapis.com/token`、Keycloak は `…/protocol/openid-connect/token`、GitHub は `/login/oauth/access_token`）。名前が製品ごとに違うので、Discovery（`token_endpoint`）で知らせる。

一方、トークンを出す以外の仕事は、別の口に分かれる：`/revoke`（RFC 7009）、`/introspect`（RFC 7662）、`/userinfo`（OIDC）、`/jwks.json`、Discovery、ログアウト（OIDC の `end_session_endpoint`）など。auth の口の並びは、この定番どおり。

### Q. OAuth・OIDC のサーバーを実装するといった場合、ステップ4・ステップ5の内容を網羅して完成か。過不足があれば知りたい

**「自分のサービスのログインを1か所にまとめる」には、ほぼ足りている。**ただ、仕様の上での「完成」（OIDC の OP として名乗れる）には足りないものがあり、製品並みにするなら、さらに多くの拡張がある。3段に分けると次のとおり。

**今あるもの**：認可コード + PKCE、client の登録（管理用のコマンド）、同意、ID トークン、Discovery、JWKS、`/userinfo`、JWT のアクセストークン、リフレッシュトークン（取り替えと盗難の検知）、`/revoke`。OIDC の核と、OAuth 2.0 の今の推奨（RFC 9700）の主な部分。

**1. OIDC Core が、すべての OP に求めているのに、ないもの（15.1 節）**

| 項目 | 中身 | auth は |
| --- | --- | --- |
| RS256 での署名 | ID トークンを RSA でも署名できること | ES256 だけ。RP の多くは ES256 も読めるので困らないが、厳密には満たさない |
| `prompt` | `none`（画面を出さずに、ログイン済みかだけ確かめる）、`login`（必ずログインし直させる）、`consent` | 受け取らない |
| `max_age` と auth_time | 「N秒以内にログインした人でなければ、ログインし直させて」 | auth_time は入れているが、max_age を見ない |
| `display`、`ui_locales`、`acr_values` | 画面の形、言語、ログインの強さの希望 | 受け取らない（多くは「受け取って、できる範囲で従う」だけでよい） |

**2. 実際に運用すると欲しくなるもの**

| 項目 | なぜ |
| --- | --- |
| ログアウト（RP-Initiated Logout、Back-Channel Logout） | 今は demo-app からログアウトしても auth のセッションが残る。auth ごと、ほかの RP ごとログアウトさせる仕組み |
| 署名の鍵の入れ替え | JWKS に新旧を並べ、止めずに鍵を替える。鍵が漏れたときの手順 |
| 同意の管理画面 | 利用者が「このアプリへの許可をやめる」を自分でできる（今は DB を直接消すしかない） |
| client の管理 | client_secret の作り直し、redirect_uri の追加。今は登録しかない |
| public client（secret を持てない SPA やスマホのアプリ） | client_secret なしで、PKCE だけで受ける。リフレッシュトークンの取り替えが本当に効くのはここ（来歴の 7 節） |
| `/token` の回数の制限、監視 | 総当たりや、盗難の検知の通知 |

**3. 用途によって足す拡張**：client_credentials（サーバー同士）、デバイスの流れ（RFC 8628）、Introspection（opaque のトークンをよその API が確かめる）、動的な client の登録（RFC 7591）、PAR（RFC 9126。/authorize の要求を先に裏で送る）、DPoP（RFC 9449）や mTLS（送り手に結び付ける。来歴の 8 節）、FAPI（銀行などの厳しいプロファイル）、ペアワイズの sub（RP ごとに違う sub）など。

自分の OP がどこまで仕様に合っているかは、OpenID Foundation が公開している適合性のテスト（conformance suite）で確かめられる。たとえば「Basic OP」のテストに通すと、上の 1 の抜けがそのまま失敗として出るはず。

ロードマップの残り（ステップ5の認可モデル）は、OAuth・OIDC の外側で、「トークンに載せたロールを、アプリがどう使うか」の話。上の表のどれかを足すかは、ステップ5のあとで決めればよい。実用の面で優先するなら、ログアウトと鍵の入れ替えが先。

### Q. client_secret ってなんでしたっけ。JWT の署名に使う共有秘密のことでしたっけ？

違う。client_secret は、**RP（demo-app）が auth に対して「自分は本当に demo-app だ」と示すためのパスワード**。JWT の署名とは関係がない。

| | client_secret | ID トークン・アクセストークンの署名の鍵 |
| --- | --- | --- |
| 持ち主 | RP（demo-app）。auth は SHA-256 だけを持つ | auth だけ（秘密鍵）。公開鍵は JWKS で誰にでも配る |
| 種類 | 共有する秘密（合言葉） | 公開鍵の暗号（ES256） |
| 使う場面 | 裏の通信：`/token`（コードの引き換え、リフレッシュ）と `/revoke` で、Basic 認証として送る | auth がトークンを作るとき署名し、RP や API が公開鍵で確かめる |
| 漏れたら | 他人が demo-app になりすまして、盗んだコードやリフレッシュトークンを引き換えられる | 誰でも auth の名前でトークンを作れる |

署名に共有の秘密を使わないのは、ES256（公開鍵の暗号）にしたから。確かめる側に配るのは公開鍵だけで済み、RP が増えても秘密を配らない。

紛らわしい理由が1つある。OIDC では、署名を HS256（共有の秘密の HMAC）にした場合、**client_secret をその鍵に使う**と決まっている（OIDC Core 10.1）。つまり「client_secret ＝ JWT の署名の共有秘密」になる構成も仕様上はありうる。auth は ES256 だけなので、その使い方はしていない。

**続けての問い**：「アクセストークンの文脈ではなく、OIDC の文脈で出てくる話か。クライアントが持つ秘密鍵、みたいな位置づけか」

- **出どころは OAuth 2.0。**RFC 6749 の 2.3.1（client のパスワード）で決まったもので、OIDC はそれを受け継いでいるだけ。使う場面はステップ4（認可コードの引き換え）とステップ5（リフレッシュ、`/revoke`）で、どれも裏の通信。
- **「秘密鍵」より「client のパスワード」。**秘密鍵（公開鍵の暗号）なら相手は公開鍵しか持たないが、client_secret は auth の側も同じものを知っている（実際に持つのは SHA-256）。共有する秘密。
- **本当に client が秘密鍵を持つ方式もある。**`private_key_jwt`（OIDC Core 9）：client が自分の秘密鍵で署名した短い JWT を `/token` に出し、auth は登録された公開鍵で確かめる。auth に秘密を預けずに済み、FAPI など厳しいところで使う。auth は client_secret（`client_secret_basic`）だけ。

ひな形を共通基盤に載せるときは、client_secret を DB のパスワードと同じく Vault に置き、app VM が読み出してコンテナに渡す。手元にもリポジトリにも置かない。

## 認可

### Q. 認証の話にはいろいろ触れてきたが、認可の話にはあまり触れなかった気がする。体系的に認証認可を学ぶにあたって、今回あつかったトピック以外で何をさわればよいか

その感覚は正しい。ステップ1〜5で扱った認可は、**OAuth の scope（委譲の認可）だけ**。「利用者が、アプリ（client）に何を代わりにやらせてよいか」の話で、同意の画面がその決定にあたる。もう1つの認可、**「この利用者は、このデータに何をしてよいか」（アクセス制御）**には、ほとんど触れていない。

| 区分 | 問い | 扱ったか |
| --- | --- | --- |
| 委譲の認可（OAuth） | このアプリに、私の代わりに何をさせてよいか（scope、同意） | ステップ4・5 |
| アクセス制御 | この人は、このデータに、この操作をしてよいか | まだ |
| 判断の置き場所 | 判断をアプリの中に書くか、外の仕組みに出すか | まだ |

アクセス制御のモデルは、だいたい次の順で生まれた（来歴の記事の筋にもなる）。

| モデル | 考え方 | 例 | 不満と次へのつながり |
| --- | --- | --- | --- |
| DAC（任意アクセス制御）、ACL | 持ち主が、誰に何を許すかを決める | Unix のパーミッション、ファイルの ACL | 人と資源が増えると、一覧が管理できない |
| MAC（強制アクセス制御） | 組織が決めた等級で、本人にも変えられない | 軍の機密区分（Bell-LaPadula、1973）、SELinux | 硬すぎて、普通の業務に合わない |
| RBAC（ロール） | 人にロールを、ロールに権限を付ける | 管理者・編集者・閲覧者、NIST の RBAC（1992、2004 に ANSI 標準） | 「自分のメモだけ」「同じ部署だけ」のような、データごとの条件が書けない |
| ABAC（属性） | 人・資源・状況の属性を、規則（ポリシー）で照らす | XACML（2003）、NIST SP 800-162、AWS IAM のポリシー | 規則が複雑になり、「誰が何を見られるか」を逆に調べにくい |
| ReBAC（関係） | 「この人はこの文書の共有相手」という関係の、たどれるつながりで決める | Google Zanzibar（2019 の論文。Drive や YouTube の共有）、OpenFGA、SpiceDB | 今の主流の1つ。関係のデータを別の仕組みに持つ手間がある |

あわせて、次の論点がある。

- **判断の置き場所**：XACML の PEP（止める場所）・PDP（判断する場所）の分け方。今は、ポリシーを外に出すエンジン（OPA と Rego、AWS の Cedar（2023））がある。
- **トークンにロールを載せるか、その都度引くか**：JWT に載せると速いが、ロールを外しても期限までは古いまま（ステップ5の「取り消しが効く範囲」と同じ割り切り）。
- **委譲の広がり**：scope より細かく頼む（Rich Authorization Requests、RFC 9396）、サービスどうしで権限を受け渡す（Token Exchange、RFC 8693）。

題材として良いのは、sample-auth-client に「人ごとのデータ」を持たせ、モデルの限界を順に踏む流れ。

1. 自分のメモだけ見られる（持ち主の判断。いちばん単純な形）
2. 管理者は全部見られる（RBAC。auth がロールを ID トークンかアクセストークンに載せる。ロードマップに残っていた「認可モデル（E）」はここ）
3. 特定の人にメモを共有する（RBAC では書けない → ReBAC。関係のテーブルを持つ）
4. （任意）判断を OPA や Cedar に出して、アプリから外す

### Q. デプロイの手順の `npm run db:init` は、HeatWave MySQL に専用の表領域？と、必要な表を作る操作か

半分合っている。db:init が作るのは**スキーマ（MySQL では database と同じ意味。表を入れる名前空間）と、そのアプリ専用のユーザー**まで。表は作らない。表領域（Oracle の tablespace のような、置き場所の単位）でもない。

| 何を | いつ | どこで |
| --- | --- | --- |
| スキーマ `sample_auth_client`、ユーザー `sample_auth_client`、そのスキーマだけの権限 | `npm run db:init`（初回だけ） | 手元 → ssh で ops の VM → `mysql -u admin`（admin のパスワードも、アプリのパスワードも Vault から） |
| 表（`sessions`） | `npm run deploy` のたび | app VM の上のコンテナで `node dist/migrate.js`。まだ流していないマイグレーションだけを流す |

分けているのは、権限の違いのため。スキーマとユーザーを作るには HeatWave の admin が要るので、admin のパスワードを読める ops でだけやる。表を作るのはアプリ自身のユーザーで足りるので、デプロイのたびにアプリのコンテナが流す。

### Q. `npm run register-client` は具体的にどんな処理を動かしているのか。auth.alphajinsei.com の管理者専用コマンドを呼んでいるなら、外から気軽に叩けて大丈夫なのか。実態は、手元の auth フォルダの管理者用コマンドのラッパーか

どちらでもない。**HTTP で auth.alphajinsei.com を呼んではいない**し、**手元の auth のコードも動かしていない**。ssh で app VM に入り、**動いている本番の auth のコンテナの中で**管理用のコマンドを実行している。

1. 手元：Terraform の出力から、client_id（`sample-auth-client`）、redirect_uri（`https://sample-auth-client.alphajinsei.com/callback`）、Vault の secret の名前を読む
2. 手元 → app VM：`ssh oci-app`（OCI の Bastion を通る。OCI の認証と SSH の鍵が要る）で、`scripts/remote-register-client.sh` を流し込む
3. app VM：`platform-secret` で client_secret を Vault から読む（インスタンス・プリンシパル。VM 自身の権限）
4. app VM：`cd /opt/apps/auth && docker compose exec -T app node dist/admin.js create-client --secret-stdin ...` に、secret を標準入力で渡す。本番の auth のコンテナに入っている `dist/admin.js` が動く
5. auth のコンテナ：secret の SHA-256 と redirect_uri を、HeatWave の `oauth_clients` に書く

なので、外から叩ける口はない。auth には管理用の HTTP の API がなく、管理はすべて「サーバーに入れる人が、コンテナの中でコマンドを打つ」形（`create-user` も同じ）。守りは **app VM に ssh で入れるかどうか**（Bastion の IAM と SSH の鍵）。そこに入れる人は、もともと `.env` の DB のパスワードも読めるので、このコマンドがあっても危なさは増えない。

動くのが本番のコンテナの中の `dist/admin.js` なので、`--secret-stdin` を足した auth を先にデプロイする必要があった（手順の 1 番目）。

### Q. RBAC には k8s などでなじみがある。ほかのモデルはよく分からないが、RBAC が分かっていれば十分な気もする

実務の多くは RBAC で足りる、というのはそのとおり。1点だけ補足すると、RBAC が苦手なのは「**自分のものだけ**」「共有された相手だけ」のような、データごとの条件。k8s の RBAC も「自分が作った Pod だけ」は書けず、namespace（データの置き場所）で分けて補っている。個人のサービスで出てくる「自分のメモだけ見られる」は、ロールではなく持ち主の列（`sub`）で判断する形になる。

## 自分の言葉でのまとめ（添削）

学習のゴールを「結局なんだったのかを、自分の言葉で平易に人に説明できること（まず高いレイヤーの理解を固め、必要なら細部に降りられる状態）」に置き、TOTP・パスキー・OAuth／OIDC を自分の言葉でまとめた。その添削の記録。まとめ直したものは、各来歴の記事の「筆者の理解」（[OTP](../history/2-otp.md)、[FIDO](../history/3-fido.md)、[OAuth と OIDC](../history/4-oauth-oidc.md)、[トークン](../history/5-tokens.md)）。

### Q. TOTP のまとめ（PW は知識の証明、TOTP は共有秘密の所持の証明。QR で秘密を共有し、共有秘密と現在時刻から6桁をハッシュ関数の要領で作り、サーバーも同じものを作って照らす）は合っているか

大筋は合っている。「知っていること」の証明と「共有秘密を持っていること」の証明の対比、最初に QR で共有して両側が同じ計算をする骨格は、そのとおり。

直すとよいところ：

1. **6桁を作るのは「クライアント」ではなく、スマホの認証アプリ。**ブラウザが計算するわけではない。人がアプリの6桁を読んでブラウザに打ち込む。認証アプリはサーバーと一度も通信しない（機内モードでも動く）。ここが TOTP のおもしろいところ。→ まとめ直しで反映した。
2. **「ハッシュ関数の要領」は、より正確には HMAC（鍵付きのハッシュ）。**秘密を知らないと同じ値を作れない。使うのは時刻そのものではなく、**30秒ごとの区切りの番号**（時刻 ÷ 30 の切り捨て）なので、30秒の間は同じ6桁になる。

足すとよいところ：

- **サーバーは秘密を元に戻せる形で持つ必要がある。**パスワードはハッシュにできるが、TOTP の秘密はサーバーも同じ計算をするので元の値が要る。auth では暗号化して保存し、鍵は Vault。共有秘密の弱みはここに出る。
- **限界：フィッシングに弱い。**偽のサイトに6桁を打たせ、その場で本物に中継されると破られる。6桁には、どのサイトに打ったかの情報が入っていない。これがパスキーにつながる動機。
- （任意）来歴：HOTP（2005年、回数で数える）→ TOTP（2011年、時刻で数える）。

### Q. パスキーのまとめ（PW をやめて端末上の秘密鍵の所持を信頼の源にする。チャレンジ・レスポンスのデジタル署名。認証器が秘密鍵を守り、人が顔認証で使用を許し、署名をサーバーが検証する）は合っているか

本質、暗号の要点、ログインの4段の流れは合っている。

直すとよいところ：

1. **「端末上の秘密鍵」は、今は端末に閉じないことが多い。**iCloud キーチェーンや Google パスワード マネージャーのパスキーは、同じアカウントの端末どうしで同期される。「端末」より「自分のアカウントの鍵の保管庫」が正確。端末から出ないのはセキュリティキー（YubiKey など）。→ まとめ直しで反映した。
2. **顔認証は、サーバーに顔を送っているのではない。**手元の認証器が「本人がいる」と確かめて、鍵の使用を許すだけ。顔の情報は端末から出ない。

足すとよいところ（いちばん大事）：

- **パスワードや TOTP にない強みは2つ。**
  - **サーバーには公開鍵しかない。**漏れても、それでログインはできない。
  - **フィッシングに強い。**鍵はサイト（ドメイン）ごとに作られ、署名にはブラウザが見ているサイトの origin が入る。偽のサイトでは本物の鍵が使われず、使えたとしても署名に偽サイトの origin が入るので、本物のサーバーが弾く。TOTP の限界への答えなので、対にして書くと筋が通る。
- **登録の流れ。**最初に端末の中で鍵の組を作り、公開鍵だけをサーバーに渡す。ログインの流れと対で書くと全体がそろう。
- **1回で多要素になる。**「鍵を持っている（所持）」と「顔や PIN で解錠した（生体・知識）」が1回の操作でそろう。sample-auth-client の画面の `amr: ["swk", "mfa"]` がこれ。→ まとめ直しで反映した。

まとめ直しを読んでの補足：「FIDO2 から拡張されたサービス仕様としてパスキーと呼ばれる」は、少しだけ違う。パスキーは新しい仕様の名前ではなく、**FIDO2（WebAuthn）の discoverable な資格情報の呼び名**（2022年に FIDO Alliance と Apple・Google・Microsoft が使い始めた）。同期されるもの（synced passkey）も、端末から出ないもの（device-bound passkey）も、どちらもパスキーと呼ぶ。同期の仕組みそのものは、各社の鍵の保管庫の機能で、FIDO の仕様の外にある。

### Q. OAuth 2.0／OIDC のまとめ（権限の委譲、「あの人の紹介なら信用します」。住民票発行課と戸籍課のたとえ）は合っているか

1か所だけ大きく直すとよいところがあった。

直すとよいところ：

1. **「権限の委譲」と「あの人の紹介なら信用します」は、別々の仕組みの説明。**
   - **OAuth 2.0 ＝ 権限の委譲。**「このアプリに、私の代わりに API を使わせる」。駐車係に渡す、運転だけできる合鍵のようなもの。
   - **OIDC ＝ 紹介による本人確認。**OAuth の上に「誰がログインしたか」を伝える仕組みを足したもの。「あの人（IdP）が本人だと言うなら信じる」はこちら。
   - 2つを分けて書き、「OIDC は OAuth の流れを借りて、ログインに使ったもの」とつなぐとすっきりする。→ まとめ直しで反映した。
2. **たとえ話に、OIDC の主役の ID トークンが出てこない。**最後に住民票発行課が受け取るのは、手形（アクセストークン）だけではなく、「この人は確かに○○さんです」と戸籍課が署名した証明書（ID トークン）も。住民票発行課は、この署名を確かめて本人だと判断する。sample-auth-client がログインに使っているのは ID トークンのほうで、手形はそのあと `/userinfo` を呼ぶのに使っている。

足すとよいところ：

- **なぜ、わざわざ戸籍課を回るのか。**利用者が、戸籍課の身分証やパスワードを住民票発行課に渡さずに済むから。OAuth が生まれたそもそもの理由（パスワードを他のサービスに預けない）。
- **次の窓口（/callback）は、住民票発行課があらかじめ戸籍課に届け出ている。**戸籍課は届け出のある窓口にしか証書を渡さない（redirect_uri の事前登録）。
- **証書（認可コード）だけでは、手形はもらえない。**住民票発行課が問い合わせるとき、自分の職員証（client_secret）と、最初に作った合言葉の答え（PKCE の code_verifier）も見せる。証書は途中で盗まれても使えず、短命で一度きり。
- **手形には範囲と期限がある。**「氏名と生年月日だけ」（scope）、「5分だけ」（期限）。切れたら更新券（リフレッシュトークン）で替える。
- （任意）**2回目からは、戸籍課での本人確認が省ける。**その日のうちに一度確認していれば戸籍課が覚えている（auth のセッション）。これが SSO。
