## 全体像

### Q. 認証・認可は、どんな小分野に分かれているのか。FIDO2・OAuth 2.0・LDAP はどこに当たるのか

認証・認可と呼ばれるものは、突き詰めると3つの問いに分かれる。

| 問い | 名前 | 例 |
| --- | --- | --- |
| あなたは誰か | 認証（Authentication） | パスワード、パスキー、「Google でログイン」 |
| あなたは何をしてよいか | 認可（Authorization） | 「管理者だけが削除できる」「このアプリに Google カレンダーの読み取りだけ許す」 |
| 誰がいるのか | ID 管理（Identity Management） | 社員の名簿、グループ、退職者の無効化 |

これに、認証の結果を覚えておく仕組み（セッション）が加わる。毎回パスキーを求めるわけにはいかないので、「さっき認証した人だ」という証明を持ち回る。実際の事故は、認証そのものより、このセッションやトークンの扱いで起きることが多い。

細かくは8つの小分野に分けられる（A. 本人確認、B. セッション、C. 連携・SSO、D. 委譲された認可、E. アプリの中のアクセス制御、F. ID 管理・ディレクトリ、G. 機械同士の認証、H. 横断するもの）。興味のある3つは、地図の上では別々の場所にある。

- **FIDO2** は A。本人だとどう示すか、の話。
- **OAuth 2.0** は D。アプリに権限を渡す話で、認証そのものではない。認証にあたるのは、その上に載る OIDC（C）。
- **LDAP** は F。Web のログインの仕組みではなく、名簿を引くプロトコル。

auth は、これらをつなぐ中心になる。名簿を持ち（F）、パスキーなどで本人を確かめ（A）、Cookie でログイン状態を覚え（B）、アプリにトークンを出し（C・D）、アプリはそれを見て権限を判断する（E）。

→ [番外編：認証・認可の全体像](extra-auth-overview.md)

### Q. パスキーと OIDC は組み合わせられるのか。画面はいくつ作ることになるのか

組み合わせられる。というより、担当している場所が違うので、ぶつからない。

- **OIDC** が決めているのは、「IdP がアプリに、ログインしたのは誰かをどう伝えるか」だけ。
- **IdP がその人をどう確かめるか**（パスワード、TOTP、パスキー）は、OIDC の範囲外で、IdP の中の事情。

「Google でログイン」を思い浮かべると分かりやすい。アプリから見えるのは OIDC だけで、Google の画面でパスワードを使ったかパスキーを使ったかは、アプリには関係ない（ID トークンの `amr` という項目で、使った方式を伝えることはできる）。

なので画面は2つの側に分かれる。

- アプリ側（demo-app）：「auth でログイン」のボタンがあるだけ
- IdP 側（auth）：ログイン画面（パスワード／パスキーを選ぶ）、TOTP の6桁の入力、同意画面など

### Q. 「一度人間が画面でログインして、機械用のトークンを払い出す」OAuth を体験するには、CLI を作る必要があるのか

作らなくてよい。これは OAuth の**デバイスコードのフロー**（RFC 8628。`gh auth login` がこれ）。流れは次のとおりで、

1. CLI が認可サーバーに「デバイスコードをください」と頼む
2. CLI が「このコードをブラウザで入れて」と表示する
3. 人間がブラウザでログインし、コードを入れて承認する
4. その間、CLI は認可サーバーに「もう承認された？」と問い合わせ続け（ポーリング）、承認されたらトークンを受け取る

人間がブラウザでログインして承認する部分（3）は、普通のブラウザの流れ（認可コード）とまったく同じ。違うのは最後のトークンの受け取り方だけで、リダイレクトでアプリに戻る代わりに、CLI がポーリングで受け取る。本質は同じなので、自作の CLI は作らず、ブラウザでの流れを深く理解する方を優先した。

### Q. パスキーも、パスワードのように DB に手で入れて作れるのか

できない。パスキーの登録は、ブラウザと認証器（スマホやセキュリティキー）が**鍵ペアを作る一連の手順**（ceremony）そのものだから。秘密鍵は認証器の中で生まれ、外に出ない。サーバーが受け取るのは公開鍵だけなので、サーバー側で勝手に作ることはできない。TOTP も、利用者の認証アプリが秘密を読み取る手順が要る。

ここで大事なのは、**アカウントを作ること**と、**そのアカウントに認証の手段を登録すること**は別、という点。

- アカウントとパスワード：管理用のコマンドで作る（`admin.js create-user`）
- TOTP とパスキー：ログインしたあと、アカウントの画面から利用者自身が登録する

新規登録の画面（誰でもアカウントを作れる経路）とアカウントの回復は、auth を自分のサービス全体の認証基盤にしていくときに必要になるので、[設計](../design.md) の「今後の発展」に残した。

### Q. IdP、OP、認可サーバー、RP、クライアント……用語が多すぎる。何がどう違うのか

分かりにくさの大半は、**同じものが規格ごとに別の名前で呼ばれている**こと。

| 実体 | OAuth 2.0 | OIDC | SAML・一般 | このリポジトリでは |
| --- | --- | --- | --- | --- |
| ログインさせたいアプリ | クライアント | RP（Relying Party） | SP（Service Provider） | demo-app |
| ログインを引き受け、トークンを出すサーバー | 認可サーバー | OP（OpenID Provider） | IdP（Identity Provider） | auth |
| トークンを見て応じる API | リソースサーバー | （UserInfo エンドポイント） | — | auth の `/userinfo` |

- IdP・OP・認可サーバーは、このリポジトリでは全部 auth のこと。言い方が違うのは見ている面が違うから。「ログインした人が誰かを証明する」面を見れば IdP・OP、「トークンを発行して権限を渡す」面を見れば認可サーバー。
- RP は「OP の言うことを信頼（rely）する側」という意味。まさに「IdP がログインしてよいと言っているから、うちにもログインさせよう」という立場。
- OAuth の「クライアント」は**ブラウザではなく、トークンを受け取って使うアプリ**のこと。ブラウザは「ユーザーエージェント」と呼ぶ。最初に一番混乱しやすい点。

→ [番外編：OAuth・OIDC の用語](extra-auth-terms.md)

### Q. 段1でデプロイした auth は、IdP と RP がひとまとまりになったアプリなのか

違う。コンテナで動いているのは **IdP（auth）だけ**で、RP（demo-app）はまだどこにも作っていない。

ただし段1の auth は、ほかのアプリにログインの結果を渡す機能（OIDC）をまだ持たず、**自分自身へのログイン**しかできない。だから外から見ると普通のアプリと区別がつかない。

Google で言えば、今の auth は accounts.google.com にあたる。Google のアカウントにログインして、自分のアカウントの画面が見られるところまで。「Google でログイン」でほかのサイトに入れる機能はまだない。

| | 段1の時点 | 段4で足すもの |
| --- | --- | --- |
| auth（IdP） | ログイン画面、auth 自身のセッション、アカウントの画面 | `/authorize`、`/token`、`/userinfo` などの OIDC の窓口 |
| demo-app（RP） | ない | 手元で作り、「auth でログイン」する。のちに別のリポジトリ・別のコンテナ |

段1で作ったログイン画面は、そのまま **IdP のログイン画面**になる。段4で demo-app の「auth でログイン」を押すと、ブラウザが auth のこの画面に飛ばされ、ログインすると demo-app に戻る。`/account` は IdP の中の「自分のアカウントの管理画面」で、段2・3でここに TOTP やパスキーの登録を足す。

FIDO（パスキー）は「本人をどう確かめるか」（A）の方式で、フェデレーション（C）とは別の軸。段2・3はログイン画面に確かめ方を足す段、段4はほかのアプリに結果を渡す窓口を足す段で、段4で初めてフェデレーションになる。

### Q. ID/PW、ID/PW + OTP、FIDO をアカウントごとに自由に試せるようにしたい。アカウントの属性として「どの認証方式に対応しているか」を持つのか

属性（列）としては持たない。**アカウント**と、**そのアカウントに登録した認証の手段**を分け、どの方式でログインできるかは、登録されている手段から決める。Google や GitHub もこの形で、2段階認証を登録したアカウントには、ログインのたびに6桁を求める。

| 登録した手段 | ログインのしかた |
| --- | --- |
| パスワードだけ | パスワード |
| パスワード + 確認済みの TOTP | パスワードのあとに6桁を必ず求める |
| パスキー | パスキーだけで入れる（端末で指紋や PIN を確かめるので、1つで多要素になる） |

- 「対応している」という列を持つと、実際に登録されているものと食い違う心配がある。登録した手段から決めれば、食い違いようがない。
- 利用者は、アカウントの画面で手段を足したり外したりするだけで、方式を切り替えられる。
- デモ用には、方式ごとのアカウント（`demo-password`、`demo-totp`、`demo-passkey`）を管理用のコマンドで作っておけば、人にも見せられる。

「対応している方式は必ず1種類」でもない。1つのアカウントに複数の手段を登録でき、ログイン画面で利用者が選べる（パスワード + TOTP とパスキーの両方を登録した人は、どちらでも入れる）。強さの順は ID/PW < ID/PW + OTP < FIDO で、差を生むのはフィッシングへの強さ。パスキーだけが「偽のサイトでは鍵を使わない」を仕組みで保証する。

今の段階から仕込んだもの：

- TOTP を `users` の列にせず、別のテーブル（`totp_credentials`）にした。段3のパスキーも同じ形の別テーブル（`webauthn_credentials`）になる。パスキーだけのアカウントのために、段3でパスワードを空にできるようにする。
- セッションに、使った方式（`amr`）を記録し、アカウントの画面に出す。

### Q. TOTP 対応のアカウントは、users と totp_credentials の両方に登場するのか。方式の見分けは「totp_credentials にいれば TOTP、users にいれば ID/PW、どちらにもいなければ未登録」というロジックか

前半はそのとおり。アカウントは全員 `users` に1行あり（アカウントそのもの）、TOTP を登録した人だけが `totp_credentials` にも1行ある（そのアカウントに付けた手段）。

ただ、見分けるロジックは「どちらの表にいるかで方式を1つに決める」のではなく、**選ばれた入口ごとに、次に何を求めるかを決める**形になる。

```
「パスワードでログイン」が押された:
  users にいなければ → 失敗（未登録。画面には「どちらかが違う」とだけ出す）
  パスワードを照らす → 違えば失敗
  totp_credentials に確認済みの行があれば → 6桁を求める → 合えば amr = "pwd otp"
  なければ → そのまま完了 → amr = "pwd"

「パスキーでログイン」が押された（段3）:
  パスキーの署名を確かめる → 合えば完了 → amr = パスキーを表す値
```

### Q. sessions の amr には、登録した認証方式を書いておくのか。上のロジックの解釈と一致するのか。amr は何の略か

amr は「登録した方式」ではなく、**「このログインで実際に使った方式」の記録**。

| | 意味 | どこにあるか |
| --- | --- | --- |
| 登録した手段 | このアカウントが**使える**方式 | `users.password_hash`、`totp_credentials`、段3の `webauthn_credentials` |
| amr | このログインで**実際に使った**方式 | `sessions.amr`（段4では ID トークン） |

多くの場合は結果として一致する。ただし、パスキーも登録している人がパスワードで入れば、amr は `pwd otp` になる。amr はロジックの入力ではなく、ロジックを通った結果の記録。

amr は **Authentication Methods References**（認証方式の参照）の略。OIDC の ID トークンの項目として定義され、入れる値は RFC 8176 が決めている（`pwd` パスワード、`otp` ワンタイムパスワード、`hwk` ハードウェアの鍵、`user` 本人の確認（指紋など）、`mfa` 多要素、など）。auth のセッションにも同じ名前・同じ値で記録しておけば、段4で RP に「この人はパスワード + TOTP でログインした」とそのまま伝えられる。RP が「パスキーでログインした人だけ」と求める仕組み（`acr_values`）の土台にもなる。

### Q. sessions.amr が「実際に使った方式」なら、「登録した認証の手段」はどこに持つのか。個別の列は持たず、ロジック側で判断するのか

**認証に使うデータそのものが、登録の印**になっている。「方式の一覧」のような要約の列を別に持たない、という意味。

| 手段 | 「登録している」とは | 置き場所 |
| --- | --- | --- |
| パスワード | パスワードのハッシュがある | `users.password_hash`（段3からは空にできる） |
| TOTP | 確認済みの行がある | `totp_credentials`（`confirmed_at` が空でない行） |
| パスキー（段3） | 公開鍵の行が1つ以上ある | `webauthn_credentials`（1人で複数の端末を登録できる） |

ロジックは、この表を見て判断する。上の問いのロジックの「`totp_credentials` に確認済みの行があれば → 6桁を求める」が、まさに「TOTP が登録されているか」をデータそのもので見ている箇所。

おすすめしなかったのは、`users` に `methods = 'pwd,otp'` のような列を足して、そちらを見る形。TOTP を削除したのに列を直し忘れた、といった食い違いが起きうる。データそのものを見れば、食い違いようがない。

（経緯：「登録した手段から決める」と「sessions に amr を記録する」を同時に説明したので、登録した手段＝ `sessions.amr` と読めてしまった。amr はあくまで、そのログインで使った方式を、セッションと一緒に持っておくもの。）

## パスワードとセッション

### Q. パスワードの保存は、どういう思想で今の形になったのか

パスワードは、1台の計算機を大勢で共有した MIT の CTSS（1961年）で生まれた。最初はファイルに平文で置かれ、すぐに漏洩の事件が起きた（1962年の持ち出し、1966年の「今日のお知らせ」の取り違え）。

そこで出てきた思想が「**照合に、秘密そのものは要らない**」。パスワードを一方向の関数にかけた結果だけを保存し、照合のときは入力をもう一度同じ関数にかけて比べる。サーバーが秘密を持たなければ、ファイルが漏れても秘密は漏れない。

以後は、この思想は変えずに、攻撃者の計算のコストをどう上げるかの競争が続いた。

| 工夫 | 解消した不満 |
| --- | --- |
| わざと遅くする（1979年、crypt） | 辞書の単語を片っ端から試せた |
| ソルト | 辞書を一度ハッシュにしておけば、全員に使い回せた |
| bcrypt（1999年） | 計算機が速くなると遅さが効かなくなる → 遅さを数値で上げられる |
| scrypt（2009年） | GPU で並べて総当たりされる → メモリを大量に使わせる（GPU は演算器ごとのメモリが少ない） |
| Argon2（2015年） | 公開のコンペで選ばれた、メモリと時間の両方を調整できるもの。auth はこれ（Argon2id） |

→ [番外編：パスワードとセッションの来歴](extra-history-password-session.md)

### Q. フォームでのログイン + Cookie のセッションは、何かの規格なのか

規格ではない。Web の作り手が自然に行き着いた、事実上の標準。

HTTP は利用者を覚えない（ステートレス）。最初の解決は HTTP/1.0 の Basic 認証で、ブラウザがパスワードを覚えて**すべてのリクエストに**付けて送った。これには不満が多かった。

- 見た目を変えられない（ブラウザ標準のダイアログ）
- ログアウトできない（ブラウザが覚えている限り送り続ける）
- 期限がない
- パスワードが毎回流れる（base64 は暗号化ではない）

1994年に Netscape が Cookie を作った（もとは買い物かごのため）。これを使って、「フォームでパスワードを1回だけ受け取り、合っていれば乱数のセッション ID を Cookie で渡し、以後はその ID で判断する」と組み立てると、Basic 認証の不満が全部解ける。

Cookie の属性（`HttpOnly`・`Secure`・`SameSite`・`__Host-`）は、どれも過去の攻撃への答えとして、あとから足されたもの。

| 属性 | 答えた攻撃 |
| --- | --- |
| `HttpOnly`（2002年） | XSS で `document.cookie` を読まれて盗まれる |
| `Secure` | 平文の HTTP から Cookie を拾われる（2010年の Firesheep で、誰でもできるようになった） |
| `SameSite`（2016年〜） | CSRF：よそのサイトから、ログイン中のサイトへのリクエストを送らせる |
| `__Host-` | 別のサブドメインから Cookie を上書きされる |

### Q. ログインに失敗したとき、なぜ「どちらが違うか」を言わず、存在しない利用者でもハッシュを計算するのか

存在するユーザー名を探す手がかりを与えないため。

- メッセージ：「ユーザー名かパスワードが違います」とだけ言う。「そのユーザーはいません」と言うと、存在するユーザー名を一覧にできてしまう。
- 応答時間：メッセージをそろえても、**時間の差**が手がかりになる。利用者がいないときは Argon2id の計算（数十ミリ秒）を省けるので、速く返ってしまう。この差から「このユーザー名は存在する」と分かる（タイミング攻撃）。

そのため、利用者がいないときも、起動時に作っておいた捨てのハッシュで同じだけ照合してから断る。手元で測ると、存在する利用者でも、しない利用者でも、0.05〜0.08秒でほぼ同じになった（最初の1回だけ遅いのは、立ち上がりのため）。

同じ考え方で、止めている間（5回失敗したあと）も、画面には同じメッセージを出し、同じだけ時間をかける。「止まっています」と言うこと自体が、そのユーザー名が存在する手がかりになるから。

### Q. ログインの POST のあと、なぜ 303 でリダイレクトするのか

Post/Redirect/Get という定石。ログインのフォームの POST に、HTML を直接返すのではなく、「303 See Other → /account」を返して、ブラウザに `/account` を GET で開き直させる。

こうすると、ログイン後の画面でブラウザの再読み込みを押しても、フォームが再送されない（「フォームを再送信しますか？」のダイアログが出ない）。302 ではなく 303 を使うのは、「POST の結果として、別の URL を **GET で**開け」という意味がはっきりしているから。

### Q. ログアウトを GET ではなく POST にし、`Origin` を確かめるのはなぜか

GET だと、よそのサイトに `<img src="https://auth.alphajinsei.com/logout">` を置くだけで、そのページを見た人を勝手にログアウトさせられる。画像を読むつもりで、ブラウザが GET を送ってしまうから。

状態を変える操作は POST にし、さらに `Origin` ヘッダーで「自分の画面から送られたか」を確かめる（CSRF の対策）。ブラウザは POST に `Origin`（送信元のページのスキーム・ホスト・ポート）を必ず付け、JavaScript からは偽れない。Cookie の `SameSite=Lax` でも、よそのサイトからの POST には Cookie が付かないが、古いブラウザや例外に備えて二重にしている。

ログアウトで大事なのは、**サーバーの DB の行を消すこと**。Cookie を消すのは、ブラウザに後片付けを頼んでいるだけ。Cookie が残っていても、行がなければそのセッションは無効。

### Q. 自分の origin（`https://auth.alphajinsei.com`）を、なぜリクエストの URL から決めず、環境変数にするのか

経路は Cloudflare → OCI LB → app VM で、**LB で TLS が終わる**。アプリには HTTP で届くので、リクエストの URL から決めると `http://...:3000` のようになってしまう。

`Origin` の確認や、段4の OIDC の issuer（発行者の URL）は、外から見た正しい origin でなければならない。そのため環境変数（`PUBLIC_ORIGIN`）で固定する。本番は `compose.yaml` に `https://auth.alphajinsei.com`、手元は `local.env` に `http://localhost:3000`。手元でポートを変えたときは `PUBLIC_ORIGIN` も変えないと、POST が 403 になる。

### Q. 失敗の回数は、どう数えれば数え漏れがないのか

1つの `UPDATE` で、数えるのと止めるのを同時に行う。

```sql
UPDATE users
SET failed_count = failed_count + 1,
    locked_until = IF(failed_count >= 5, <15分後>, locked_until)
WHERE id = ?
```

いったん `SELECT` で回数を読み、アプリで1足して `UPDATE` で書くと、同時に来た2つの失敗が同じ値を読み、1回分を数え漏らす。1つの `UPDATE` なら、DB が行をロックして順に処理するので漏れない。

MySQL の `SET` は左から順に評価され、右の式（`IF(failed_count >= 5, ...)`）は、**足したあとの** `failed_count` を見る。この性質を使っている（標準の SQL とは違う、MySQL の挙動）。

回数はログインに成功したときだけ0に戻す。15分が過ぎたあとも回数は5以上のままなので、また1回間違えるとすぐ止まる。総当たりの速さを、15分に1回まで落とすことになる。手で解くときは `admin.js unlock <ユーザー名>`。

### Q. 手元で試したら、止める期限が9時間ずれていた。なぜか

日時の扱いが2通り混ざっていた。

- Drizzle の通常の `insert`・`update` は、日時を **UTC** の文字列にして送り、読むときも UTC とみなす。
- 生の SQL（`` sql`...` ``）に `Date` を埋め込むと、ドライバー（mysql2）が既定で**プロセスの時刻**（手元なら JST）で文字列にする。

失敗の回数の `UPDATE` は生の SQL で書いたので、「15分後」が JST で書き込まれ、Drizzle がそれを UTC として読んだ。結果、9時間長く止まった。

接続の設定に `timezone: 'Z'` を付け、ドライバーも UTC にそろえて直した（[src/db/client.ts](../../src/db/client.ts)）。本番のコンテナは UTC なので、手元でしか出ない種類の不具合。

## ワンタイムパスワード

### Q. OTP は、どういう思想で生まれ、何が決め手で普及したのか

最初の思想は「**一度流れたものは、二度と使えないようにする**」。telnet などが平文でパスワードを流し、1994年には盗聴で大量に集められていた。盗み見られても、それがもう使い終わったパスワードなら価値がない。

その後、RSA の SecurID などのハードウェアトークン（6桁が1分ごとに変わる小さな機械）で、意味が変わった。盗聴の対策から、「**この機械を持っている**」ことの証明、つまり認証の要素の「所持」になった。パスワード（知識）と組み合わせれば2要素認証になり、パスワードがリスト型攻撃で漏れても、機械がなければ入れない。

ハードウェアトークンは、高い・1社に縛られる（計算の方法が非公開）という不満があった。そこで計算の方法が公開の規格になり（HOTP 2005年、TOTP 2011年）、さらに Google Authenticator（2010年）で、機械を配らずにスマートフォンがトークンになった。

普及の決め手は、次の3つがそろったこと。

- 公開の規格（誰でもサーバーとアプリを作れる）
- 誰もが持つスマートフォン（機械を配らなくてよい）
- QR を読むだけの登録（`otpauth://totp/...` の URL。どの認証アプリも同じ QR を読める）

残った弱点は、リアルタイムのフィッシング。偽の画面に入れさせた6桁を、30秒以内に本物のサイトへ中継されると防げない。人間が数字を読み写す限り、どのサイトに入力しているかを確かめるのは人間の目になる。この限界を、仕組みでサイトを見分けて越えたのがパスキー（段3）。

→ [番外編：ワンタイムパスワードの来歴](extra-history-otp.md)

### Q. Lamport の鎖（100乗、99乗……）だと、OTP で認証できる回数に限りがあるのか。それとも十分大きいので実質無限なのか

**限りがある。**100回分の鎖を作ったら、使えるのは100回まで。使い切ったら、新しい秘密で鎖を作り直して、サーバーに登録し直す（S/KEY では `keyinit` というコマンド）。「十分大きいので実質無限」という位置づけではない。鎖を長くすると、1回のログインごとに最大その回数だけハッシュを計算することになるので、数百回程度が普通だった。

限りがある理由は、一方向の関数の性質。`h(x)` から `x` には戻れないので、使う順番は「鎖の後ろから前へ」しかない。サーバーが持つのは「次に来るはずの値を、もう一度ハッシュした値」だけで、盗まれても次のパスワード（鎖の1つ手前）は計算できない。

つまり Lamport の鎖は、**サーバーが秘密を持たないかわりに、回数に限りがある**という取引になっている。紙の一覧を持ち歩く面倒さもあり、SSH（1995年）が通信路ごと暗号化して盗聴の問題を別の方法で解いたこともあって、S/KEY は普及しきらなかった。

### Q. 回数に限りがあるのは原型の Lamport の鎖だけで、今の TOTP は時刻を使うので制限がない、ということか。HOTP と TOTP のどちらが主流か

そのとおり。HOTP も TOTP も、`HMAC(秘密, カウンタか時刻)` を毎回計算するので、何度でも使える。そのかわり、サーバーも秘密そのものを持つ（Lamport の鎖の逆の取引）。どちらが良いかではなく、トレードオフ。

主流は **TOTP**。認証アプリ（Google Authenticator、Microsoft Authenticator、1Password など）は、ほぼ TOTP を前提にしている。HOTP は、ボタンを押すたびにカウンタが進むので、押しただけで使わないと機械とサーバーでカウンタがずれ、サーバー側でずれを探し直す手間が要る。時刻なら、ずれるのは時計だけ。HOTP が残っているのは、ボタンを押すと数字が出るハードウェアトークンや、YubiKey の一部の機能くらい。

### Q. 秘密を共有して双方で OTP を導出するのは、共通鍵に近い気がする。何か違いはあるのか

**実体は同じで、共通鍵（対称鍵）そのもの**。TOTP の秘密は HMAC の鍵。違うのは使い方だけで、暗号化には使わず、「この鍵を持っていなければ作れない値」を作って見せるのに使う。

構造としては、チャレンジ・レスポンス（相手が出した問題に、鍵を使って答えを返す）の一種。チャレンジが「今の時刻」なので、サーバーが送らなくても双方が知っている。

共通鍵なので、サーバーも同じ鍵を持つ。パスワードはサーバーがハッシュしか持たなくても照合できるが、TOTP はサーバーが秘密そのものを持つ（共有の秘密）。サーバーが破られれば全員分が漏れる。2011年に RSA が侵入され、SecurID のシードに関わる情報が盗まれ、直後に Lockheed Martin が攻撃を受けたのは、この弱点が現実になった例。

段3のパスキーは、ここを**公開鍵**に替えたもの。サーバーが持つのは公開鍵だけなので、DB が漏れても秘密は漏れない。

### Q. 共有する秘密は、登録時に QR で受け渡される。秘密がインターネットを流れるが、HTTPS で経路が暗号化される前提なのか

前提。経路は2区間に分かれる。

1. auth → ブラウザ：HTTPS で1回だけ流れる
2. 画面 → スマホ：カメラで読むので、ネットワークを通らない

これは共通鍵の宿命で、「最初に秘密を、安全に相手に渡す方法」が別に要る（**鍵配送の問題**）。TOTP では、その安全な経路として「HTTPS」と「パスワードでログイン済みのセッション」を使っている。そのため、登録の画面はログインした人にしか開けない。

逆に言えば、画面を覗かれたり、QR のスクリーンショットを撮られたりすれば、秘密は漏れる。QR の中身が画面に出るのは、登録のときの1回だけにしている。

### Q. 共有する秘密は、利用者ごとに新しく発行するのか。「DB が漏れたら全員分の2要素目が漏れる」とは、全ユーザーで何かを共有しているのか

利用者ごとに、登録のたびに乱数で新しく作る（20バイト）。全員で共有するものはない。

「全員分が漏れる」は、「DB にはそれぞれの利用者の秘密が並んでいるので、DB が漏れると全員の秘密が一度に漏れる」という意味。パスワードのハッシュなら漏れても元に戻すのに総当たりが要るが、TOTP の秘密はそのまま使えてしまう。だから暗号化して保存する（下の問い）。

### Q. OTP の前後1回のずれは許容する仕様なのか。登録のときだけか

**登録とログインの両方で許す。**RFC 6238 は、通信の遅れのために「少なくとも1つ前の枠を受け付けること」を推奨している。多くの実装は、時計のずれも考えて前後1つ（±30秒）にしている。クラウドのコンソールにログインするとき、入力している間に次の6桁が表示されてもログインできるのは、この仕様のおかげ。

その分、同じ6桁が最大90秒ほど計算上は合い続ける。盗み見られた6桁をすぐに使われないよう、**最後に使った時刻の枠を記録し、それ以前の枠を拒む**（RFC 6238 も、同じコードを2回受け付けてはならないと定めている）。

また、6桁は100万通りしかなく、前後1つの幅を許すと1回の試行で3つの値が当たりになる。回数制限がないと総当たりで破れるので、段1の失敗の回数を、パスワードと6桁の両方で数える。

### Q. TOTP の秘密を暗号化して保存するとき、何がどこに置かれるのか

決めた形（B1）では、置き場所が3つに分かれる。

| もの | 置き場所 |
| --- | --- |
| 利用者ごとの TOTP の秘密 | **暗号文**として DB |
| それを暗号化する鍵（全利用者で共通の1つ） | 本体は **Vault**。**デプロイのとき**に、デプロイのスクリプトが app VM の上で Vault から取り出して `.env`（権限 600）に書き、コンテナはそれを環境変数として読む（DB のパスワードと同じ経路）。動いている間は、鍵はコンテナのメモリにある |
| 復号した秘密 | 6桁を照らすその場でだけメモリに置く。どこにも保存しない |

OTP の認証のリクエストが来たら、その利用者の暗号文を、環境変数の鍵で復号し、それを使って6桁を照らす。

これで、DB だけが漏れた場合（バックアップの流出、SQL インジェクションなど）は守れる。コンテナ（app VM）を乗っ取られると、鍵も取られる。

もう1つの形（B2）として、Vault の鍵管理の機能（KMS）で暗号化・復号する方法がある。鍵は Vault から一度も出ず、コンテナはログインのたびに Vault の API に「これを復号して」と頼む（AWS KMS などで実務によく使う形）。app VM を乗っ取られても鍵そのものは持ち出せない。そのかわり、OCI の SDK を入れる手間と、Vault が落ちるとログインできなくなる依存が増える。今回の学習の主題は TOTP なので、鍵の管理で回り道をしすぎないよう、B1 にした。

## TOTP の実装（src/totp.ts）

### Q. `hotp()` を行ごとに解説してほしい（TypeScript 自体に詳しくない）

RFC 4226 の例（秘密 `12345678901234567890`、カウンタ 0）を、実際の数値でたどる。

```ts
export function hotp(secret: Buffer, counter: number, digits = DIGITS): string {
```

関数の宣言。

- `export`：ほかのファイルから使えるようにする印。
- 引数は3つ。`secret: Buffer` は「secret はバイト列（Buffer は Node.js のバイト列の型）」という意味で、`:` の右が型。`counter: number` は数値。`digits = DIGITS` は「省略されたら DIGITS（6）を使う」という既定値の書き方。
- 最後の `: string` は、戻り値が文字列だという宣言。

```ts
	const message = Buffer.alloc(8);
	message.writeBigUInt64BE(BigInt(counter));
```

カウンタを、HMAC に入れる**8バイトのバイト列**にする。HMAC は数値ではなくバイト列を受け取るので、変換が要る。

- `Buffer.alloc(8)`：0で埋めた8バイトを用意する。
- `writeBigUInt64BE`：そこに 64ビットの符号なし整数を、ビッグエンディアン（大きい桁が先）で書き込む。カウンタ 0 なら `00 00 00 00 00 00 00 00`。
- `BigInt(...)`：JavaScript の普通の数値は 64ビットの整数を正確に扱えないので、64ビットを書くときは BigInt（任意の大きさの整数）に変換して渡す決まり。

この形式（8バイト、ビッグエンディアン）は RFC 4226 が決めている。クライアントも同じ形にするので、同じ値になる。

```ts
	const mac = createHmac('sha1', secret).update(message).digest(); // 20バイト
```

HMAC-SHA1 を計算する。メソッドを順につなげる書き方で、「秘密を鍵に HMAC-SHA1 の計算器を作る → message を流し込む → 結果を取り出す」。結果は20バイト。例では次の値。

```
cc 93 cf 18 50 8d 94 93 4c 64 b6 5d 8b a7 66 7f b7 cd e4 b0
```

```ts
	const offset = mac[mac.length - 1] & 0x0f;
```

切り出す位置を決める。

- `mac[mac.length - 1]`：最後のバイト（例では `b0`）。
- `& 0x0f`：下位4ビットだけを残すビット演算。`0xb0` は 2進で `1011 0000` なので、下位4ビットは `0000` で、offset は 0。
- 4ビットなので、offset は 0〜15 のどれか。20バイトから4バイトを取るので、最大でも 15+4=19 で、はみ出さない。

```ts
	const binary = mac.readUInt32BE(offset) & 0x7fffffff;
```

offset の位置から4バイトを、32ビットの整数として読む。例では `cc 93 cf 18`。`& 0x7fffffff` で最上位の1ビットを0にし、31ビットの正の整数にする。`0xcc93cf18` の最上位ビットを落とすと `0x4c93cf18`、10進で **1284755224**。最上位ビットを捨てるのは、言語によって32ビット整数を符号付きで扱うものがあり、そこで結果が食い違わないようにするため（RFC の決まり）。

```ts
	return String(binary % 10 ** digits).padStart(digits, '0');
```

ここで**6桁にする**。

- `10 ** digits` は 10の6乗（100万）で、`%` は割った余り。1284755224 % 1000000 = **755224**。
- `String(...)` で文字列にし、`.padStart(6, '0')` で6桁に満たなければ前を0で埋める（余りが 42 なら `000042`）。

RFC 4226 の付録の、カウンタ 0 の答え `755224` と一致する。テストで確かめているのはこれ。

### Q. この「決まった桁数の数字を切り出す」処理は、クライアント側でも同じ処理を実行するのか。認証アプリに出るのは6桁だが、hotp の途中は31ビットの正の整数とある。この2つを直接比較するわけではないのか

比べない。31ビットの整数は**途中の値**で、`hotp()` が返すのは最後の行の6桁の文字列。

認証アプリ（クライアント）も、**まったく同じ計算**をしている。同じ秘密、同じカウンタ（時刻から求めた枠の番号）、同じ手順なので、同じ6桁になる。画面に出ているのは、この最後の6桁。サーバーは同じ計算で6桁を作り、`verifyTotp()` で、入力された6桁と文字列どうしで比べる。

### Q. TOTP は HOTP のカウンタに時刻を使ったもの、とのこと。ミリ秒とあるので、その瞬間のミリ秒が使われるのか。サーバーとクライアントで同じミリ秒の値は持てないと思う。プロトコルの中で「この時刻で計算しよう」と合意するのか

ミリ秒は一致しない。そして、一致させる必要もない。ミリ秒は入口で使うだけで、計算に使うのは**30秒ごとの枠の番号**だから。

```ts
export function stepAt(ms: number): number {
	return Math.floor(ms / 1000 / STEP_SECONDS);
}
```

- `Date.now()` は、1970年1月1日（UTC）からの経過ミリ秒。JavaScript の時刻はミリ秒で表すので、ミリ秒で受け取っている。
- 1000で割って秒にし、30で割って、`Math.floor` で小数を切り捨てる。たとえば 2026-11-12 の昼なら、ミリ秒は 1794000000000 前後で、枠の番号は 59800000 前後。この番号は **30秒の間ずっと同じ**。

合意しているのは「1970年からの秒数を30で割って切り捨てた番号」で、これは RFC 6238 が決めている。両者の時計が数秒ずれていても、同じ30秒の枠の中にいれば同じ番号になり、同じ6桁になる。

枠の境目をまたいだとき（スマホでは 59800000、サーバーに届いたときには 59800001 になった、など）や、時計のずれのために、`verifyTotp()` は前後1つの枠まで許している。スマホもサーバーも、時計はネットワーク（NTP や携帯の網）で数秒以内に合わせられているのが前提。

**理解の確認**：「30秒おきの枠で、サーバー・クライアントともに『共有の秘密 + 30秒おきの枠 → 6桁』を計算し、それが一致することを確かめる。これで、共有の秘密を『所持している』ことを示す、2要素目の認証ができる」で合っている。

### Q. totp.ts の残りの部分（generateSecret、totp、verifyTotp、base32、otpauthUri）は何をしているのか

**`generateSecret()`**：`randomBytes(20)` で、暗号論的に安全な乱数を20バイト作る。利用者ごとの秘密。

**`totp()`**：`hotp(secret, stepAt(ms), digits)` を呼ぶだけ。TOTP は「HOTP のカウンタに枠の番号を入れたもの」なので、関数の中身も1行。`ms = Date.now()` は既定値の書き方で、省略すると今の時刻を使う。テストでは過去の時刻を渡して、RFC の値と比べている。

**`verifyTotp()`**：入力された6桁を照らす。

```ts
export function verifyTotp(secret: Buffer, code: string, lastStep: number | null, ms = Date.now()): number | null {
```

- `lastStep: number | null` は「数値か null（まだ一度も使っていない）」。`|` は「どちらか」を表す型の書き方。
- 戻り値も `number | null` で、合えば合った枠の番号、合わなければ null を返す。

```ts
	if (!/^\d{6}$/.test(code)) return null;
```

`/^\d{6}$/` は正規表現で、「先頭から末尾まで、数字がちょうど6個」。それ以外（5桁、英字など）は計算せずに断る。

```ts
	const now = stepAt(ms);
	for (const step of [now - 1, now, now + 1]) {
		if (lastStep !== null && step <= lastStep) continue;
		if (timingSafeEqual(Buffer.from(hotp(secret, step)), Buffer.from(code))) return step;
	}
	return null;
```

- 前の枠、今の枠、次の枠の3つについて、順に試す。
- `continue` は「この回は飛ばして次へ」。最後に使った枠以前は試さないので、同じ6桁の再利用が拒まれる。
- `timingSafeEqual`：2つのバイト列を比べる。普通の `===` は、1文字目が違えばすぐ false を返すので、何文字目まで合っていたかが応答時間に出る。この関数は、どこで違っても同じ時間をかけて比べる。段1の「存在しない利用者でもハッシュを計算する」と同じ考え方。
- 合えば、その枠の番号を返す。呼び出し側（2-c）が、それを「最後に使った枠」として DB に記録する。

**`base32()`**：秘密（20バイト）を、QR に入れる文字列にする。Base32 は、5ビットずつ区切って、32種類の文字（A〜Z と 2〜7）に置き換える方式。人が手で打つこともあるので、0と O、1と I のような紛らわしい文字が入っていない。中のビット演算は「8ビットずつ溜めて、5ビット以上溜まったら上から5ビット取り出す」をくり返している。20バイト＝160ビットは5で割り切れるので、32文字になる。

**`otpauthUri()`**：QR の中身の URL を作る。`otpauth://totp/auth.alphajinsei.com:alice?secret=...&issuer=...` の形で、Google が決めた書き方。どの認証アプリもこれを読める。

- `encodeURIComponent`：`:` や日本語などを URL で使える形にする。
- `URLSearchParams`：`?a=1&b=2` の部分を組み立てる。
- `` `...${...}...` ``（バッククォート）は、文字列の中に値を埋め込む書き方（テンプレートリテラル）。

### Q. TOTP の秘密の暗号化（src/secretbox.ts）は、どういう形で暗号化しているのか

AES-256-GCM で暗号化し、`base64url( nonce 12バイト | 暗号文 | 認証タグ 16バイト )` の形で DB に置く。20バイトの秘密が、64文字になる。

- **GCM は認証付き暗号**：暗号化と同時に「改ざんされていないか」を確かめるタグを作る。DB の値を書き換えられたら、復号のときにエラーになる。
- **nonce**（一度だけ使う乱数）は、暗号化のたびに作る。同じ鍵で nonce を使い回すと、GCM は安全でなくなる。
- **AAD（追加の認証データ）に利用者の ID を渡す**：AAD は暗号化はされないが、タグの計算に混ぜられる。別の利用者の行に暗号文をそのまま写しても、ID が違うのでタグが合わず、復号できない。
- 鍵は環境変数 `TOTP_KEY`（32バイトを base64 で）。起動時になければ、アプリは起動しない（設定漏れに早く気づくため）。手元は `local.env` の開発用の鍵、本番は Vault（2-d）。

### Q. 「AAD に利用者の ID を混ぜる」とは、6桁の導出に利用者 ID も入力として含まれるのか（ユーザー側でも ID を知って同じ計算をするのか）。それとも、サーバーが秘密を暗号化して保管するときの追加の安全策で、基本原理（共有の秘密と時刻からお互いに6桁を計算する）は変わっていないのか

**後者で合っている。**AAD は、サーバーが秘密を DB に保管するときの追加の安全策。基本原理は変わらない。6桁の計算に利用者の ID は入らず、ユーザー側（認証アプリ）は ID も暗号化も知らない。

層が2つに分かれている。

| 層 | 誰が関わるか | 中身 |
| --- | --- | --- |
| TOTP の層 | サーバーと認証アプリの両方 | 秘密（QR で渡した20バイトそのもの）+ 時刻の枠 → 6桁。RFC 6238 のとおり |
| 保管の層 | サーバーだけ | 秘密を DB に置く前に `TOTP_KEY` で暗号化する。ログインのときに復号して、平文の秘密に戻してから TOTP の層に渡す。AAD はここだけの話 |

認証アプリが持っているのは、QR から読んだ平文の秘密そのもので、サーバーの暗号化とは無関係。

言葉の補足：AAD は「ソルト」とは少し違い、**「暗号化はしないが、改ざんの検知（タグ）の対象には含めるデータ」**。タグは共通鍵で作る署名のようなもの（MAC）で、「暗号文」と「AAD」の両方をまとめて覆う。復号するときに同じ AAD（利用者の ID）を渡さないと、タグが合わずに失敗する。

**防いでいる攻撃**：攻撃者が DB に書き込めるようになった（SQL インジェクションなど）が、`TOTP_KEY` は持っていない、とする。

1. 攻撃者は、自分のアカウントで TOTP を登録する。自分の秘密（QR）は知っていて、DB にはその暗号文が入る。
2. その暗号文を、被害者の行にそのまま写す。
3. AAD がなければ、サーバーは被害者の行を「攻撃者の秘密」として復号してしまう。攻撃者は自分の認証アプリで、被害者の6桁を作れる。
4. AAD に利用者の ID を混ぜておけば、攻撃者の ID で作ったタグは被害者の ID では合わないので、復号が失敗し、6桁は通らない。

暗号化で「読めない」ことに加えて、AAD で「その暗号文は、その利用者のものだ」と結び付けている。

### Q. TOTP の利用者で、失敗の回数をいつ0に戻すのか

**ログインが最後まで済んだとき（6桁が通ったとき）だけ**。段1では、パスワードが通った時点で0に戻していた。TOTP の利用者でも同じにすると、パスワードを知っている攻撃者は「パスワードを通す（回数が0に戻る）→ 6桁を4回試す」をくり返せて、6桁を無制限に試せてしまう。6桁は100万通りで、前後1つの幅を許すと1回の試行で3つが当たりになるので、回数制限が効かなくなると破られる。

手元で試すと、6桁を1回間違えると `failed_count` が1になり、正しい6桁が通ったところで0に戻った。

### Q. 同じ6桁が、同時に2つのリクエストで送られたらどうなるのか

「最後に使った枠」を、次の1つの `UPDATE` で記録している。

```sql
UPDATE totp_credentials SET last_step = <今回の枠>
WHERE user_id = ? AND (last_step IS NULL OR last_step < <今回の枠>)
```

書き換えに成功するのは、先に着いた1つだけ。もう1つは `affectedRows` が0になり、断られる。いったん `SELECT` で読んでから `UPDATE` で書くと、2つのリクエストが同じ古い値を読み、両方が通ってしまう（失敗の回数の数え方と同じ考え方）。

次のログインで同じ6桁を使い回した場合は、`verifyTotp()` が「最後に使った枠以前」を最初から試さないので、6桁の照合の段階で断られる（失敗として数えられる）。

## パスキー

### Q. FIDO2・パスキーは、どういう思想で生まれ、何が決め手で普及したのか

出発点は、パスワードも OTP も**人間が値を読み写す**ので、偽サイトに入力させてその場で中継されると防げないこと（人間はサイトを見分けられない）と、TOTP でもサーバーが秘密を持つこと。思想は「**人間ではなく、仕組みにサイトを見分けさせる。サーバーには公開鍵だけを置く**」。

公開鍵で本人を確かめる仕組み（TLS のクライアント証明書、IC カード、SSH の公開鍵）は昔からあったが、どれも「この鍵は誰のものか」を証明する CA や名簿を前提にしていて、一般の Web サイトには重かった。FIDO は逆に、鍵が誰のものかは証明せず、**サイトごとに新しい鍵ペアを作り、そのサイトに公開鍵を預けるだけ**にした。

フィッシングに強い理由は2つ。署名の対象に、ブラウザが見ている本当の origin が入る（偽サイトで操作すると偽サイトの origin が入り、本物のサイトが拒む）。鍵はサイト（RP ID）ごとに別で、認証器は偽サイトに本物の鍵を使わない。

流れは、U2F（2014年。Google と Yubico のセキュリティキーでの2要素目）→ FIDO2（WebAuthn が 2019年に W3C 勧告。全ブラウザで同じ API、端末に内蔵の認証器）→ パスキー（2022年に Apple・Google・Microsoft が発表。鍵を端末の間で同期する）。端末から鍵が出られず、機種変更や紛失で困る、という導入の壁を、同期で越えた。そのかわり、鍵の安全がクラウドのアカウントに依存し、最高水準（AAL3）からは一段譲った。

→ [番外編：FIDO2 とパスキーの来歴](extra-history-fido.md)

### Q. パスキーは、本質的には公開鍵認証によるクライアントの証明か。SSH の公開鍵認証に近いが、サーバー側で authorized_keys に公開鍵を置く作業がなくなっているのか。なぜ SSH は鍵の登録を自動化できないのか（登録する公開鍵が正当なユーザーのものだと判断するロジックが自動化できないのか）。FIDO は、事前に ID/PW で認証してから設定を入れるので、本当のユーザーの公開鍵だと示せるのか

その理解で合っている。FIDO では、`authorized_keys` に公開鍵を置く作業を、ブラウザと認証器が自動で行う。

自動化できる理由も推察のとおりで、**「この公開鍵は正当な本人のものだ」という信頼を、すでにある別の認証から借りている**から。登録はログイン済みの画面からしかできないので、「パスワード（+ TOTP）でログインした人が、今この鍵を出した」ことをもって、その鍵を本人のものと認める。新規登録の画面で最初のパスキーを作る場合は、「アカウントを作った人が持ち主」という、SSH の初回接続（known_hosts）と同じ「最初の1回は信じる」形になる。

SSH にも同じ仕組みはある。「一度 ID/PW でログインしてから鍵を送る」という発想は実在する。

| 仕組み | 信頼を借りる先 |
| --- | --- |
| `ssh-copy-id` | パスワードで1回ログインし、公開鍵を `authorized_keys` に書き足す |
| クラウドの VM の作成（OCI の `ssh_authorized_keys` など） | クラウドの API の認証（OCI の IAM）。VM を作る権限のある人が渡した鍵を、最初から置く |
| OCI Bastion のセッション | OCI の API の認証。公開鍵を API に渡すと、その鍵で3時間だけ入れる。FIDO の登録とほぼ同じ構図 |

ただ、インターネットに向けて SSH のパスワード認証を開けることはしない（感想のとおり）。そのため SSH の世界では、「SSH 自身の中で ID/PW から鍵へ段階的に上げる」形ではなく、「別の経路（クラウドの API）で認証して鍵を置く」形が広まった。

### Q. シーケンスにチャレンジ・レスポンスは含まれるのか。ID/PW で認証していても必要なのか。秘密鍵で署名する原文として challenge を送っているのか。チャレンジ・レスポンスは生のパスワードを送らないための仕組みだと理解していたが、ここでは秘密鍵を外に出さないために使っているのか

含まれる。FIDO の中心はチャレンジ・レスポンス。「秘密鍵で署名するときの原文として challenge を送っている」も合っている。署名の原文は「authenticatorData」と「clientDataJSON のハッシュ」をつなげたもので、clientDataJSON の中に challenge と origin が入っている。

ただし、使う目的は少し違う。

- パスワードのチャレンジ・レスポンス（CHAP、HTTP Digest など）の目的は2つだった。① 秘密（パスワード）を送らずに、知っていることを示す。② 使い回し（リプレイ）を防ぐ。
- **公開鍵の署名では、① は署名そのものが引き受ける。**署名から秘密鍵は計算できないので、challenge がなくても秘密鍵は外に出ない。
- そのため、ここでの **challenge の役目は ② の使い回しの防止**（新しさの保証）。毎回同じ原文に署名するなら、一度盗んだ署名を何度でも使えてしまう。サーバーが毎回新しい乱数を出し、一度使ったら消すので、盗んだ署名は二度と通らない。

ID/PW でログイン済みの登録のときにも challenge が要るのは、同じ理由。「この登録の応答は、今このサーバーが求めたものへの応答だ」と確かめ、古い登録の応答を流し込ませないため。

TOTP と並べると、TOTP は「今の時刻」が暗黙の challenge だった。FIDO は、サーバーが明示的に乱数を渡す。

### Q. FIDO のシーケンスは難解だが、技術の要素に還元すると数種類で、その組み合わせでこのシーケンスになる、という理解はできるか

できる。7つの要素の組み合わせ。

| # | 要素 | 何を保証するか | 由来 |
| --- | --- | --- | --- |
| ① | 公開鍵の署名 | 秘密鍵を持っていること（秘密を見せずに） | SSH、TLS のクライアント証明書 |
| ② | challenge | 署名が今回のための新しいもの（使い回しでない） | チャレンジ・レスポンス |
| ③ | origin を署名に入れる | どのサイトで操作したか（偽サイトの中継を見破る）。origin はブラウザが書き込むので、ページの JavaScript には偽れない | FIDO で新しく入った |
| ④ | 鍵をサイト（RP ID）ごとに分ける | 偽サイトには本物の鍵を使わない。サイトをまたいで同一人物だと追跡されない | FIDO で新しく入った |
| ⑤ | 端末の中でのユーザー検証 | 鍵を使ったのが端末の持ち主本人（指紋・PIN）。生体情報はサーバーに送られない | スマホのロック解除 |
| ⑥ | 登録の信頼を、既存のログインから借りる | 登録された公開鍵が本人のもの | `ssh-copy-id`、クラウドの鍵の登録 |
| ⑦ | カウンタ | 鍵が複製されていない（任意。同期されるパスキーでは 0） | ハードウェアトークン |

- **登録** ＝ ⑥ ログイン済みの画面から始める → ② challenge を渡す → ⑤ 本人を確かめて、④ この RP ID 用の鍵ペアを作る → ③ origin 入りの応答を返す → サーバーは ②③④ を確かめ、① の公開鍵を保存する
- **ログイン** ＝ ② challenge を渡す → ④ この RP ID の鍵を選び、⑤ 本人を確かめて、① 署名する（原文には ② と ③ が入っている）→ サーバーは ②③④ を確かめ、① を公開鍵で検証し、⑦ カウンタを見る

シーケンス図の Note の「〜を確かめる」は、どれもこの番号のどれかに当たる。どれも単独では昔からある考え方で、新しいのは組み合わせ方（特に ③④）。

### Q. RP、RP ID、RP サーバー、RP アプリケーションは、それぞれどう対応するのか。auth が両方を兼ねているのか。IdP 相当はどちらか。RP ID はどちらの持ち物か。そもそも RP とは何を意味する言葉か（relaying party なら、認証をお願いしたい側のアプリケーションか）

**RP は Relying Party（信頼する側）**で、relay（中継）ではなく rely（頼る・信頼する）。**誰かが出した認証の結果を信じて、利用者を受け入れる側**。

一番混乱しやすいのは、**同じ RP という言葉が、層によって違うものを指す**こと。

| 層 | 証明を出す側 | 証明 | RP（それを信じる側） |
| --- | --- | --- | --- |
| WebAuthn（段3） | 認証器 | 署名（assertion） | **auth** |
| OIDC（段4） | auth（OP） | ID トークン | **demo-app** |

auth は WebAuthn の層では RP で、OIDC の層では OP（IdP）。WebAuthn の世界での「RP」は「パスキーでログインさせるサイト」のことで、今回は IdP である auth 自身。用語の番外編で「RP ＝ demo-app」と書いたのは、OIDC の層の話。

- **RP サーバーと RP アプリケーション**：WebAuthn の RP は2つの部分からできている。**RP サーバー**は challenge を作り、署名を検証するところ（信頼できる側で、合否を決めるのはここだけ）。**RP アプリケーション**は利用者が操作する画面と、その中で `navigator.credentials` を呼ぶ JavaScript（スマホのアプリならアプリ本体）。今回は推察のとおり **auth が両方を兼ねている**。
- **IdP 相当はどちらか**：両方とも auth の中。IdP（auth）が、自分のログイン画面のために WebAuthn の RP になっている。
- **RP ID は誰の持ち物か**：RP 全体の持ち物で、**RP サーバーが決めて、守らせる**。サーバーが options で RP ID を渡し、検証のときに「authenticatorData の RP ID のハッシュが自分のものか」を確かめる。ブラウザは「その RP ID が、今のページの origin のドメインと合っているか」を確かめる（`auth.alphajinsei.com` のページから `google.com` の RP ID は使えない）。親のドメイン（`alphajinsei.com`）を指定すると、サブドメインの間で同じパスキーを使える。

**RP サーバーと RP アプリケーションを分離する予定はあるか**：分けない。企業では、検証専用の「FIDO サーバー」を置いて各業務アプリが API で呼ぶ構成をよく見かけるが、プロトコル上で大事なのは「challenge の発行と検証が、利用者の手の届かないサーバー側にあること」だけで、別のサービスに分けることは必須ではない。このリポジトリでは、より大事な分離が段4で入る。**パスキーを扱うのは IdP（auth）だけにし、各アプリ（demo-app）は WebAuthn に一切触れず、OIDC で結果だけを受け取る**形。今の一般的な構成で（「Google でログイン」の先でパスキーを扱うのは Google だけ）、アプリを増やしても、パスキーの登録や検証を各アプリに実装しなくて済む。分けた形を見たければ、段4のあとの発展として検討する。

### Q. RP は「よそで認証されたことを信じる側、認証をよそに委託する側」ということか。「Google でログイン」の文脈では、RP はそのバナーを出す Web サイトのことが多い（OIDC の立場で議論することが多い）か

そのとおり。**何を「よそ」と見るかが、層によって変わる**だけ。

「Google でログイン」の話をするときは、ほとんどが OIDC の層の話で、RP はバナーを出すサイト。WebAuthn の層の RP（Google 自身。自分のログイン画面でパスキーを使わせる）は、外のサイトからはほとんど見えない。外のサイトはパスキーに一切触れず、Google から ID トークンを受け取るだけ。

**理解の確認**：WebAuthn と OIDC で RP に当たるものが違うのは驚きだったが、「証明を出す側と、それを信じる側」という原理を聞けば納得できた。

### Q. RP ID は RP サーバー（Google の例なら Google）が決めているのか。つまり Google は「本人であることは認証した。ただ、この認証でログインしてよいのは、事前に知っているこのドメインだけ」と言っているのか。Google の認証で OIDC を実装したいなら、自分のドメインでフェデレーションできるように Google に設定を入れてもらう必要があるのか

半分当たりで、**別の2つの制限が混ざっている**。

| | 何を縛るか | 誰が決める | 「Google でログイン」の例 |
| --- | --- | --- | --- |
| **RP ID**（WebAuthn の層） | **パスキーを使ってよいページのドメイン** | RP サーバー（Google） | `google.com`。パスキーは Google のログイン画面の中だけで使う。自分のアプリのドメインは関係しない |
| **クライアントの登録**（OIDC の層） | **ID トークンを渡してよい相手（client_id と redirect_uri）** | OP（Google） | 自分のアプリの `https://app.example.com/callback` を事前に登録する |

「本人であることは認証した。ただ、結果を渡してよいのは事前に知っているこのドメインだけ」は、**OIDC のクライアント登録**の方に当たる。

- 連絡は要らない。Google Cloud Console で「OAuth クライアント ID」を自分で作り、許可する redirect URI を書き込む（セルフサービス）。
- Google は、登録にない redirect URI には結果を返さない。そうしないと、偽サイトが「結果を自分に送って」と頼めてしまう。
- 段4で、auth にもこの仕組み（クライアントの表と redirect_uri の照合）を作る。

RP ID の方は「Google の鍵は Google のページでしか使わせない」という縛りで、パスキーに触れない自分のアプリが関わることはない。

**理解の確認**：OIDC の層では、結果を受け取る側（RP）ごとに OP への登録が要る。WebAuthn（を含む FIDO）の層は、Google の認証ページとその裏の認証サーバーの中で完結するので、どこからフェデレーションされても同じで、アプリごとに設定が発生する箇所ではない。

### Q. ブラウザの実装を信じていることが前提になっている箇所がいくつかある。ブラウザを独自に実装したら破れる穴はないのか

前提は実際にある。ただ、**破るには被害者の端末そのものを乗っ取る必要がある**。

ブラウザを信じているのは3か所。

- clientDataJSON に本当の origin を書く
- RP ID がページのドメインと合っているかを確かめてから、認証器に渡す
- 認証器には「どの RP ID 用か」をブラウザが伝える（認証器はそれを信じる）

| 誰のブラウザが細工されているか | 何が起きるか |
| --- | --- |
| **攻撃者が、自分の端末で独自のブラウザを作る** | 何も得られない。origin を好きに書けても、**被害者の秘密鍵は被害者の認証器の中**にあり、署名できない。サーバーは署名を公開鍵で検証するので、ここはブラウザを信じていない |
| **偽サイト（普通のフィッシング）** | ページの JavaScript には origin を書き換えられない。FIDO が守るのはこの場面 |
| **被害者のブラウザ自体が悪意のもの**（マルウェア、悪い拡張機能） | 破れる。偽の origin を書き、本物の RP ID で認証器に署名させれば、中継が通る |

最後の行は、FIDO が守らないと決めている範囲（仕様もクライアントを信頼するものとして扱っている）。そこまで乗っ取られた端末では、どの方式も守れない。入力したパスワードはそのまま盗めるし、ログイン後のセッションの Cookie も盗める（今いちばん多い攻撃は、この Cookie を盗むマルウェア＝インフォスティーラー）。**パスキーが消したのは、その手前の「偽サイトに入力させる」攻撃**。

それでも、OS は「誰でもブラウザを名乗れる」状態にはしていない。

- **Windows**：USB のセキュリティキーに直接話しかけるには管理者の権限が要る。普通のアプリは Windows の WebAuthn API を通すしかない。
- **iOS・Android**：任意のサイトの RP ID でパスキーを使えるのは、OS がブラウザと認めたアプリだけ（Apple は専用の権限、Android は許可されたブラウザの一覧）。普通のアプリは、自分と結び付いたドメイン（そのドメインが `/.well-known/` のファイルで「このアプリは自分のもの」と宣言している）でしか使えない。

Cookie を盗まれる問題への次の手として、セッションも端末の鍵に結び付ける仕組み（DBSC：Device Bound Session Credentials）が Chrome で進んでいる。パスキーの考え方をセッションにも広げるもの。

**理解の確認**：被害者のブラウザに細工できた時点で、こんな高級な仕組みを考えなくても悪用の方法はいくらでもある。なので、そのパターンは守る範囲の外と仕様でも決めている。

### Q. RP ID は今回は auth.alphajinsei.com で、Google の例でも google.com なのか。直観では「relying party ＝ 認証サーバーへ遷移する元の Web アプリの FQDN」だと思ってしまうが、そうではなく認証サーバーの方の ID なのか。WebAuthn の文脈では RP は認証サーバーの側（端末の認証器を信じる側）なので、RP ID は認証サーバーの FQDN を指す、ということか。RP という言葉が多義的なことによる分かりにくさか

そのとおり。**RP ID は「WebAuthn の RP の ID」**で、WebAuthn の RP は「認証器の署名を信じる側」＝ 署名を検証するサーバー。だから RP ID は、パスキーでログインさせる画面とその裏のサーバーのドメインになる。

| | 直観で思い浮かべるもの | 実際の RP ID |
| --- | --- | --- |
| 「Google でログイン」 | バナーを出した元のアプリのドメイン | `google.com`（Google のログイン画面のドメイン） |
| このリポジトリ（段4以降） | demo-app のドメイン | `auth.alphajinsei.com`（手元は `localhost`） |

直観の「元のアプリ」は、**OIDC の層の RP**。そちらには RP ID という言葉はなく、OP が持つ識別子は client_id（と redirect_uri）。つまり、

- **WebAuthn の RP ID**：認証サーバー（OP）のドメイン。パスキーの鍵を、どのサイトの画面で使ってよいかを縛る
- **OIDC の client_id**：元のアプリの識別子。ID トークンを誰に渡してよいかを縛る

と、名前も層も違う。分かりにくさの原因は推察のとおり、**「RP」という言葉が層によって別のものを指す**こと。元のアプリから見ると、パスキーは「認証サーバーの中の出来事」で、アプリのドメインは一切登場しない。

**理解の確認**：RP は「証明を信じる側」。WebAuthn では認証サーバーが認証器を信じる側なので、RP ID は認証サーバーの FQDN。元の Web アプリは OIDC の層の RP で、そちらは client_id で識別される。
