## 1. パスワード

### 1.1 始まり：計算機を共有したから（1961年）

パスワードは、MIT の CTSS（1961年）という、1台の計算機を大勢で同時に使うタイムシェアリングのシステムで生まれたとされる。それ以前の計算機は1人ずつ順番に使うもので、「誰が使っているか」を区別する必要がなかった。共有したとたんに、自分のファイルと他人のファイル、自分の計算時間の割り当てを分ける必要が出た。

- 認証は、**資源を共有したこと**から生まれた。Web のログインも、共有されたサーバーの上で利用者を分ける、という同じ構図。

最初のパスワードは、ファイルに平文で置かれていた。そこからすぐに事件が起きる。

- 1962年：計算時間の割り当てを増やしたかった研究者が、パスワードのファイルを印刷させて持ち出した。
- 1966年：エディタの一時ファイルの取り違えで、ログインした全員に表示される「今日のお知らせ」の代わりに、パスワードのファイルが表示された。

### 1.2 思想の転換：サーバーは知らなくてよい（1960年代後半〜1979年）

ケンブリッジ大学で、パスワードそのものではなく、**一方向の関数（元に戻せない変換）にかけた結果だけを保存する**というアイデアが出た。照合のときは、入力をもう一度同じ関数にかけて比べればよい。

> 照合に、秘密そのものは要らない。

これが今に至るまでのパスワードの保存の土台になっている。サーバーが秘密を持たなければ、ファイルが漏れても秘密は漏れない。Unix はこの考え方で作られ、Morris と Thompson の論文「Password Security: A Case History」（1979年）で、さらに2つの工夫を足した。

| 工夫 | 解消した不満 |
| --- | --- |
| **わざと遅くする**（DES を25回くり返す crypt） | 当時の計算機でも、よくある単語を片っ端から試せた（辞書攻撃）。1回の照合を遅くすれば、正規の利用者には気にならず、総当たりする側には効く |
| **ソルト**（利用者ごとの乱数を混ぜる） | 同じパスワードは同じハッシュになるので、辞書を一度ハッシュにしておけば全員に使い回せた。乱数を混ぜると、利用者ごとに計算し直しになる |

Dovecot の `SHA512-CRYPT` は、この crypt の系譜の上にある。

### 1.3 計算力の伸びとの競争（1999年〜2015年）

「わざと遅く」は、計算機が速くなると効かなくなる。そこで、遅さを調整できるハッシュが出てくる。

| 年 | 出来事 | 意味 |
| --- | --- | --- |
| 1999 | **bcrypt** | 遅さを数値（コスト）で上げられる。計算機が速くなったら、コストを上げればよい |
| 2009 | **scrypt** | 計算だけでなく、**メモリを大量に使わせる**。GPU や専用の回路は計算は速いが、1つ1つの演算器が使えるメモリが少ない。そこを突く |
| 2009 | RockYou の漏洩 | 3200万件のパスワードが**平文**で漏れた。人が実際にどんなパスワードを付けるかが公になり、以後の攻撃の辞書になった |
| 2012 | LinkedIn の漏洩 | ソルトなしの SHA-1。GPU で短期間に大半が解読された。「速い汎用のハッシュはパスワードに使えない」が常識になった |
| 2013〜2015 | Password Hashing Competition | 公開のコンペで、パスワード専用のハッシュを選んだ。**Argon2** が勝った。メモリと時間の両方を調整できる |

ここまでの流れは、「秘密を持たない」という思想は変えずに、**攻撃者の計算のコストをどう上げるか**の競争だった。auth で Argon2id を使うのは、この流れの今の到達点だから。

### 1.4 人間の側の見直し（2017年）

もう1つの流れは、利用者に課す規則。2003年に米国の NIST が「大文字・小文字・数字・記号を混ぜ、定期的に変える」という指針を出し、世界中のシステムに広がった。ところが、人は規則に対して予測可能な対応をする（`Password1!` → `Password2!`）。指針を書いた本人が、2017年に「間違いだった」と述べている。

2017年の NIST SP 800-63B は、これを改めた。

| 旧 | 新 | 理由 |
| --- | --- | --- |
| 文字種を混ぜる | 長さを求める | 文字種の強制は、覚えにくくするだけで、予測しにくくはならない |
| 定期的に変える | 漏れたときだけ変える | 定期的な変更は、少しだけ変えたパスワードを生む |
| — | 漏洩済みの一覧と照合する | 攻撃者が最初に試すのは、他所で漏れたパスワード |

攻撃の主流も、1つのアカウントを総当たりすることから、**他所で漏れた ID とパスワードの組を、別のサービスで試す**こと（リスト型攻撃）に移った。これはサーバーのハッシュをどれだけ強くしても防げない。回数制限と多要素認証が要るのは、このため。

### 1.5 なぜ廃れないのか

パスワードの欠点は、1960年代から知られている。それでも残っている理由は、2012年の論文「The Quest to Replace Passwords」（Bonneau ほか）がよく整理している。35種類の代替の方式を、使いやすさ・導入しやすさ・安全性の25の観点で比べたところ、**安全性で勝る方式は多いが、導入しやすさでパスワードに勝る方式は1つもなかった**。

- 費用がかからない。専用の機械も、端末も要らない
- どの端末からでも、キーボードさえあれば使える
- 誰でも仕組みを知っている。説明が要らない
- 変えられる（指紋は漏れても変えられない）
- サーバーの実装が単純で、どの言語・フレームワークにもある

パスキー（段3）は、この「導入しやすさ」の壁を、OS とブラウザが鍵を同期するという形で初めて越えかけている方式、と位置づけられる。

## 2. セッション

### 2.1 前提：HTTP は利用者を覚えない（1991年）

Web は、もともと論文などの文書を取り寄せるための仕組みだった。HTTP の1回1回のリクエストは独立していて、前のリクエストと同じ人かどうかを知る方法がない（ステートレス）。文書を配るだけなら、それで困らなかった。

### 2.2 最初の解決：毎回パスワードを送る（1996年）

HTTP/1.0 には Basic 認証が入った。ブラウザがパスワードを覚えておき、**すべてのリクエストに**付けて送る。

| 不満 | 中身 |
| --- | --- |
| 見た目を変えられない | ブラウザ標準のダイアログが出るだけ。アプリのデザインに合わせられない |
| ログアウトできない | ブラウザが覚えている限り送り続ける。サーバーから「忘れて」と言えない |
| 期限がない | 一度入れたら、ブラウザを閉じるまで有効 |
| パスワードが毎回流れる | base64 で符号化されているだけで、暗号化ではない。HTTPS がない時代は、経路で丸見え |

### 2.3 Cookie の発明（1994年）

Netscape の Lou Montulli が、ネットショップの買い物かごを実現するために Cookie を作った。サーバーが「この値を覚えておいて、次から付けてきて」と言い（`Set-Cookie`）、ブラウザは同じサイトへのリクエストに自動で付ける（`Cookie`）。もとは認証のためではなく、**ステートレスな HTTP に状態を持たせる**ための汎用の仕組みだった。

これを使うと、ログインを次のように組み立てられる。

1. アプリが自分でデザインしたフォームでパスワードを受け取る（1回だけ）
2. 合っていれば、乱数の**セッション ID** を作ってサーバーに記録し、Cookie で渡す
3. 以後は、ブラウザが自動で付けてくるセッション ID を見て、誰かを判断する

Basic 認証の不満が全部解ける。画面はアプリが決められ、サーバーの記録を消せばログアウトでき、期限も自由に付けられ、パスワードは最初の1回しか流れない。**フォームでのログイン + Cookie のセッション**は、規格で決められたものではなく、Web アプリの作り手が自然に行き着いた事実上の標準。今もこれが基本の形。

### 2.4 攻撃が見つかるたびに、属性が足された（2001年〜2020年）

ここからは、攻撃が見つかり、対策が Cookie の属性として足されていく歴史になる。今の「Cookie にはこの属性を付ける」という定石は、全部どこかの事件への答え。

| 年 | 攻撃 | 何が起きるか | 足された対策 |
| --- | --- | --- | --- |
| 2001 | **CSRF**（クロスサイト・リクエスト・フォージェリ） | 悪意のあるサイトに、ログイン中のサイトへのフォームを仕込む。ブラウザが Cookie を自動で付けるので、本人の操作として通ってしまう | トークンをフォームに埋める、のちに `SameSite`（2016年に Chrome、2020年に Lax が既定） |
| 2002 | **XSS によるセッションの窃取** | 掲示板などに仕込んだ JavaScript が `document.cookie` を読み、攻撃者に送る | `HttpOnly`（JavaScript から読めなくする。2002年に IE6 が最初） |
| 2002 | **セッション固定** | 攻撃者が自分の取ったセッション ID を被害者に使わせ、被害者がログインした後に同じ ID で入る | ログインの瞬間にセッション ID を作り直す |
| 2010 | **Firesheep** | カフェの Wi-Fi で、他人の HTTP の通信から Cookie を拾い、そのままなりすますブラウザの拡張が公開された。誰でもクリック1つでできた | `Secure`（HTTPS のときだけ送る）、そして Web 全体の HTTPS 化 |
| 2016〜 | サブドメインからの Cookie の上書き | 別のサブドメインが、親ドメイン向けの Cookie を書いて割り込む | `__Host-` の接頭辞（そのホスト専用で、`Secure` 必須） |

Cookie の仕様そのもの（RFC 6265）は2011年にようやく整理された。今の定石は OWASP の Session Management Cheat Sheet などにまとまっている。

### 2.5 なぜ Cookie のセッションが普及したか

- ブラウザが自動で付けて送るので、アプリの JavaScript が何もしなくてよい
- 中身は乱数なので、漏れても推測されない。サーバーの記録を消せば、即座に無効にできる
- どの言語のフレームワークにも最初から入っている

一方で、「ブラウザが自動で付けて送る」という同じ性質が、CSRF の原因にもなった。便利さと危うさが同じ根から出ている。2015年ごろからは、サーバーに記録を持たない JWT をセッションに使う流れも出たが、失効できないこと、XSS で盗まれやすい置き場所になりがちなことから、ブラウザ向けには Cookie のサーバー側セッションが今も推奨されている。

## 3. まとめ

| | パスワード | Cookie のセッション |
| --- | --- | --- |
| 生まれた理由 | 計算機を共有したので、利用者を分ける必要が出た | HTTP が利用者を覚えないので、状態を持たせる必要が出た |
| 思想 | 照合に秘密そのものは要らない（一方向の関数） | 秘密は最初の1回だけ流し、以後は推測できない乱数の札で代える |
| 解消した不満 | 平文の保存による漏洩 → ハッシュ、ソルト、遅いハッシュ | Basic 認証の、見た目・ログアウト・期限・毎回の送信 |
| 普及した理由 | 導入しやすさで勝る方式がない | ブラウザが自動で送る。どのフレームワークにもある |
| 今の形 | Argon2id、長さ重視、漏洩済みとの照合、回数制限 + 多要素 | `HttpOnly`・`Secure`・`SameSite`・`__Host-`、ログイン時の作り直し |

段1の実装は、この表の右下の「今の形」を、そのままなぞる。
