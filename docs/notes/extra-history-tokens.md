# 番外編：アクセストークンとリフレッシュトークンの来歴

最終更新：2026-11-18

ステップ5（アクセストークンとリフレッシュトークン）の背景。OAuth 2.0 と OIDC が生まれるまでの全体の流れは [番外編：OAuth 2.0 と OpenID Connect の来歴](extra-history-oauth-oidc.md) に書いた。この記事は、その中の「トークン」だけに絞って、**API は、届いたトークンが本物で、まだ有効だと、どうやって知るのか**という問いが、どう答えられてきたかを追う。参照か値か、という型の話は [番外編：引換券を挟むという型](extra-pattern-claim-ticket.md) の 4 節。

## 1. 問い：API は、毎回の要求をどう信じるか

ログイン（ステップ1〜4）は1回で終わる。API の呼び出しは、1日に何百回、何千回と来る。そのたびに「この要求は、誰の、どの許可によるものか」を確かめる必要がある。確かめ方には、ずっと2つの力が働いてきた。

| 力 | 欲しいもの |
| --- | --- |
| 安く確かめたい | 毎回 DB や認可サーバーに問い合わせたくない。API の台数が増えても、認可サーバーを詰まらせたくない |
| すぐ取り消したい | 利用者が「このアプリの許可を外す」と押したら、すぐ止まってほしい。盗まれたら、すぐ無効にしたい |

この2つは引っ張り合う。取り消しを即座に効かせるには、毎回どこかの記録を見に行く必要がある。見に行かなければ安いが、取り消しは効かない。トークンの歴史は、この綱引きの落としどころを探してきた歴史。

## 2. トークン以前：毎回パスワード、または API キー（〜2000年代後半）

| やり方 | 例 | 不満 |
| --- | --- | --- |
| 毎回パスワードを送る（Basic 認証） | 初期の Twitter の API。サードパーティのアプリが利用者のパスワードを保存して、要求のたびに送っていた | アプリにパスワードを丸ごと渡す。範囲を絞れない。取り消すにはパスワードを変えるしかなく、変えると全部のアプリが止まる |
| API キー | Web の地図や写真のサービスの API で、開発者に配る固定の文字列 | 「どのアプリか」は分かるが、「どの利用者の許可か」は表せない。期限がない |

## 3. OAuth 1.0：長生きのトークンと、毎回の署名（2007年〜2010年）

OAuth 1.0（2007年12月に公開、2010年に RFC 5849）は、パスワードの代わりに**アクセストークン**を渡す形を作った。利用者ごと・アプリごとに発行され、範囲を絞れ、利用者は設定画面で1つずつ取り消せる。2010年8月31日、Twitter は API の Basic 認証を止めて OAuth だけにした（開発者の間では「OAuthcalypse」と呼ばれた）。

| 足したもの | 中身 |
| --- | --- |
| アクセストークン | パスワードの代わりの、アプリ専用の許可証。取り消しても、パスワードもほかのアプリも影響を受けない |
| トークンの秘密と署名 | トークンには対になる秘密があり、要求のたびにそれで署名する（HMAC-SHA1）。トークンを盗み見ても、秘密がなければ使えない |

残った不満：

- **トークンに期限がないのが普通だった。**一度もらえば、取り消されるまで使える。
- **API は、毎回トークンを記録と照らす必要があった。**署名を確かめるにはトークンの秘密が要り、それは認可サーバーの DB にある。
- **署名が難しい。**パラメーターの並べ方やエンコードを1つ間違えると、「署名が合わない」とだけ言われる。

## 4. 発明：短命のアクセストークンと、リフレッシュトークン（2009年 OAuth WRAP）

2009年、Yahoo!、Google、Microsoft の技術者（Allen Tom、Brian Eaton、Dick Hardt、Yaron Goland）が **OAuth WRAP**（Web Resource Authorization Profiles）を出した。大きなサービスを運営する側から見た OAuth 1.0 の不満を、トークンを2つに分けることで解いた。

| トークン | 寿命 | 誰に見せるか | どう確かめるか |
| --- | --- | --- | --- |
| アクセストークン | 短い（分〜時間） | API（リソースサーバー）に、毎回 | 安く。期限が短いので、取り消しの確認を省いてもよい |
| リフレッシュトークン | 長い（日〜月） | 認可サーバーにだけ、アクセストークンが切れたときに | 厳しく。認可サーバーが記録を見て、取り消されていないかを確かめる |

1 節の綱引きを、**確かめる場所を分けて**ほどいた発想。

- 毎回の要求（数が多い）は、短命のアクセストークンで安く通す。取り消しは「次に切れるまで」の遅れで効く。
- 取り消しの確認（厳しい）は、たまにしか来ないリフレッシュのときにだけ、認可サーバーでする。

あわせて、トークンの署名をやめた。アクセストークンは **Bearer**（持参人）トークンで、持っている者が使える。盗み見の対策は HTTPS（TLS）に任せる。WRAP の仕様は、リフレッシュトークンは長い期間の許可を表すので、必ず HTTPS で送ると書いている。名前の変遷も残っていて、0.9.7.0 の版で「Delegation Token」を「Refresh Token」に改めている。

## 5. OAuth 2.0：形を決めない枠組み（2012年）

WRAP を土台に IETF で作り直した OAuth 2.0 は、2012年10月に RFC 6749（本体）と RFC 6750（Bearer トークンの使い方）になった。アクセストークンとリフレッシュトークンの2本立ては、そのまま入った。

ただし、RFC 6749 は**アクセストークンの中身の形を決めなかった**。「認可サーバーとリソースサーバーの間の取り決め」として、実装に任せた。決めなかったことで、あとから2つの流儀が生まれる。

| 流儀 | 中身 | API の確かめ方 |
| --- | --- | --- |
| 参照（opaque トークン） | 意味のない乱数 | 認可サーバーの記録を引く（ステップ4の auth の `/userinfo` がこれ。`access_tokens` の表を SHA-256 で引く） |
| 値（自己完結のトークン） | 中身（誰の、どの scope、いつまで）を書いて署名したもの | 署名と期限を、API が自分で確かめる。記録を引かない |

参照の流儀で、API が認可サーバーと DB を共有していないときのために、**Token Introspection**（RFC 7662、2015年）が決まった。API が認可サーバーに「このトークンは有効か、中身は何か」と問い合わせる口。取り消しの口は **Token Revocation**（RFC 7009、2013年）で、アプリがログアウトのときなどに「このトークンを無効にして」と頼む。

編集者の1人だった Eran Hammer は、2012年7月に編集を降り、「OAuth 2.0 は地獄への道だ」と書いた。その不満の1つが、署名をやめて Bearer トークンにしたこと（盗まれたら使える）だった。この指摘は、8 節でふたたび出てくる。

## 6. JWT のアクセストークン：値の流儀が広がる（2015年〜）

2015年5月、JWT（RFC 7519）が規格になった。署名した JSON を URL に収まる文字列にする形で、OIDC の ID トークンもこれを使う。認可サーバーの製品やクラウドの多くが、**アクセストークンも JWT にする**ようになった。

広がった理由：

- **API が増えた。**1つのサービスが、小さな API（マイクロサービス）の集まりになった。全部が認可サーバーに問い合わせると、認可サーバーが詰まり、落ちたら全部が止まる。JWT なら、各 API が公開鍵（JWKS）だけで確かめられる。
- **ID トークンと同じ道具が使える。**署名と JWKS の仕組みは OIDC ですでに用意されている。

一方で、各社の JWT の中身はばらばらだった（項目の名前、aud の入れ方、scope の書き方）。2021年10月の **RFC 9068**（JWT Profile for OAuth 2.0 Access Tokens）が、項目（iss、exp、aud、sub、client_id、iat、jti、scope など）と、ヘッダーの `typ: at+jwt` を決めた。`typ` を分けたのは、ID トークンとアクセストークンを取り違えさせないため（ID トークンを API に、アクセストークンを RP のログインに使い回す攻撃がある）。

値の流儀の弱点は、**取り消しが効かない**こと。API は記録を見ないので、利用者が許可を外しても、JWT は期限まで通る。だから JWT のアクセストークンは短命（5分〜1時間）にして、4 節のリフレッシュトークンと組み合わせる。WRAP の2本立てが、ここで本来の力を出す。

| | 参照（opaque） | 値（JWT） |
| --- | --- | --- |
| API の確かめ方 | 記録を引く（DB、または Introspection） | 署名と期限を自分で |
| 認可サーバーの負荷 | 要求のたびに | 鍵を配るだけ |
| 取り消し | 即座に効く | 期限まで効かない（短命で補う） |
| 中身が漏れると | 乱数なので何も分からない | 誰の、どの scope かが読める（署名だけで、暗号化はしていない） |
| 大きさ | 小さい（数十文字） | 大きい（数百文字〜） |

## 7. リフレッシュトークンの悩み：ブラウザとスマホ（2010年代後半〜）

2本立ては、リフレッシュトークンを安全にしまえることが前提だった。client_secret を持つサーバー（ステップ4の demo-app）なら、リフレッシュトークンを盗まれても、secret なしでは使えない。ところが、client_secret を持てないアプリが増えた。

- **SPA**（ブラウザの JavaScript だけで動くアプリ）：コードは誰でも読めるので、secret を隠せない。リフレッシュトークンを localStorage に置けば、XSS で盗まれる。
- **スマホのアプリ**：アプリの中の secret は、取り出せる。

こうした「public client」でリフレッシュトークンが盗まれると、長い期間、取り消されるまで使われる。対策としてまとまったのが**リフレッシュトークンの取り替え**（rotation）。

1. リフレッシュするたびに、新しいリフレッシュトークンを出し、古いものを無効にする
2. 無効にしたはずの古いトークンが来たら、盗まれたと見なして、その系統（同じログインから続くトークン全部）を取り消す

正しい持ち主と盗んだ人の、どちらかが先に使うと、もう片方が使ったときに「古いトークン」が来て、盗難が見つかる。ステップ4の認可コードの「一度きりで、異常に気づける」と同じ考え。

この慣行は、OAuth のセキュリティの最善の慣行（Security BCP）として長く議論され、2025年1月に **RFC 9700**（BCP 240）として出た。public client のリフレッシュトークンは、取り替えるか、次の 8 節の「送り手に結び付ける」ことを求めている。

## 8. Bearer の穴をふさぐ：送り手に結び付ける（2020年〜）

5 節で Hammer が指摘した「盗まれたら使える」には、トークンを**持ち主の鍵に結び付ける**形で答えが出てきた。

| 規格 | 年 | 中身 |
| --- | --- | --- |
| mTLS（RFC 8705） | 2020年2月 | トークンを、クライアントの TLS の証明書に結び付ける。サーバー同士向け |
| DPoP（RFC 9449） | 2023年9月 | クライアントが自分で鍵の組を作り、要求のたびにその秘密鍵で小さな JWT（証明）に署名して添える。トークンは、その公開鍵に結び付いている。ブラウザやスマホでも使える |

これは、OAuth 1.0 の「要求ごとの署名」が、使いやすい形で戻ってきたとも言える。OAuth 1.0 の署名は共通の秘密（HMAC）で、両側が秘密を持つ必要があった。DPoP は公開鍵の署名で、秘密鍵はクライアントだけが持つ（ステップ3のパスキーと同じ考え）。

## 9. なぜ広く使われるようになったか

- **役割を分けられた。**認可サーバー（トークンを出す・取り消す）と、リソースサーバー（API。トークンを確かめるだけ）を別々に作れる。API の側は、ログインの画面も、パスワードも、パスキーも知らなくてよい。
- **確かめ方を、規模に合わせて選べた。**小さいうちは参照（DB を引く）、API が増えたら値（JWT）、と、形を決めなかった OAuth 2.0 の枠組みの中で切り替えられた。
- **スマホと API の時代に合った。**アプリがサーバーの API を直接呼ぶ形が当たり前になり、「Cookie のセッション」に代わる、ヘッダー1つで渡せる許可証が要った。

## 10. まとめ

| | |
| --- | --- |
| 生まれた理由 | API は1日に何千回と呼ばれる。そのたびにパスワードを送るのも、毎回記録を引くのも、つらい |
| 思想 | 許可証を2つに分ける。数の多い確かめ（アクセストークン）は安く、たまの厳しい確かめ（リフレッシュトークン）は認可サーバーで |
| 解消した不満 | パスワードを渡さない（OAuth 1.0）、取り消しと負荷の綱引き（WRAP の2本立て）、API ごとの問い合わせ（JWT） |
| 普及した理由 | 認可サーバーと API を分けられ、規模に合わせて確かめ方を選べた。スマホと API の時代に合った |
| 残った弱点 | Bearer は盗まれたら使える（DPoP などで結び付ける）。JWT は取り消しが効かない（短命で補う）。public client のリフレッシュトークン（取り替えで盗難に気づく） |
| 今の形 | 短命のアクセストークン（参照か JWT）＋ 取り替えるリフレッシュトークン。RFC 6749・6750・7009・7662・9068・9700 |

ステップ5では、この「今の形」を小さく作る：`/userinfo` のアクセストークンを、ステップ4の参照（DB を引く乱数）から JWT（RFC 9068 の形）に替えて両方を比べ、リフレッシュトークンを取り替えと盗難の検知つきで出す。
