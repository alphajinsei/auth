# 番外編：FIDO2 とパスキーの来歴

最終更新：2026-11-12

段3（パスキー）の背景。パスワードと OTP の来歴は [番外編：パスワードとセッションの来歴](extra-history-password-session.md)、[番外編：ワンタイムパスワードの来歴](extra-history-otp.md)。

## 1. 不満：人間がサイトを見分けられない

OTP の来歴の最後で見た限界から始まる。パスワードも OTP も、**人間が値を読み写す**。偽のログイン画面に入れさせ、その場で本物のサイトへ中継されると（リアルタイムのフィッシング）、2要素認証でも破られる。2017年には、これを自動で行う道具（Evilginx）が公開された。

問題の根は、「どのサイトに入力しているか」を確かめるのが**人間の目**だという点にある。`alphajinsei.com` と `alphajlnsei.com` を、人間は確実には見分けられない。パスワードも6桁も、どのサイトに渡すかを自分では選ばない。

もう1つの不満は、TOTP でも残った**サーバーが秘密を持つ**こと。パスワードはハッシュにできても、TOTP の秘密はサーバーにそのまま（か、復号できる形で）置くしかない。

> 人間に見分けさせるのをやめ、仕組みにサイトを見分けさせる。サーバーには秘密を置かない。

これが FIDO の思想。道具は昔からある**公開鍵暗号の署名**だった。

## 2. 前史：公開鍵での認証は昔からあった

公開鍵で本人を確かめる仕組みそのものは、新しくない。

| 方式 | 中身 | 普及しなかった（一般向けにならなかった）理由 |
| --- | --- | --- |
| TLS のクライアント証明書（1990年代〜） | ブラウザが利用者の証明書を出して TLS の相手に自分を証明する | 証明書を発行する認証局（CA）が要る。発行・更新・失効の運用が重い。ブラウザの証明書の選択画面は分かりにくい |
| IC カード（政府の職員証、銀行のカードなど） | カードの中の秘密鍵で署名する | カード、読み取り機、ドライバー（ミドルウェア）が要る。企業や政府の中にとどまった |
| SSH の公開鍵 | `authorized_keys` に公開鍵を置く | 技術者向け。鍵の配布を人が手でやる |

どれも**「この鍵は誰のものか」を証明する仕組み（CA、名簿）**を前提にしていた。そのせいで、一般の Web サイトが気軽に使えるものにならなかった。

FIDO は、ここを逆にした。鍵が誰のものかは証明しない。**サイトごとに新しい鍵ペアを作り、そのサイトに公開鍵を預けるだけ**にした。最初の登録のときに「このアカウントにこの公開鍵」と結び付ければ、以後は「その鍵を持っている」ことだけを確かめればよい。CA も名簿も要らない。SSH の公開鍵認証に近いが、鍵の作成と登録をブラウザと機械が自動でやる。

## 3. FIDO Alliance と U2F（2012年〜2016年）

2012年、PayPal などが FIDO（Fast IDentity Online）Alliance を作り、2013年に公表した。同じころ Google は、Yubico と組んで、USB に挿す小さなセキュリティキーで2要素目を行う仕組みを社内で作っていた。これが FIDO に持ち込まれ、2014年に2つの規格として公開された。

| 規格 | 中身 |
| --- | --- |
| **U2F**（Universal 2nd Factor） | パスワードのあとの2要素目として、セキュリティキーで署名する。Google と Yubico の流れ |
| **UAF**（Universal Authentication Framework） | スマートフォンの指紋などで、パスワードなしでログインする。Nok Nok Labs などの流れ |

U2F の仕組みは、今のパスキーとほぼ同じ骨格を持っていた。

```
Registration
  site --challenge, appId--> browser --> security key
  key: create a NEW key pair for this appId, keep the private key inside
  key --public key, key handle--> site stores them

Login
  site --challenge, key handle--> browser --> security key
  browser adds the origin it actually sees
  key: sign (challenge + origin + counter) with the private key for this appId
  site: verify with the stored public key, check origin and challenge
```

**フィッシングに強い理由**は2つの仕掛けにある。

- **署名の対象に、ブラウザが見ている本当の origin が入る。**偽サイト（`alphajlnsei.com`）で操作すると、署名には偽サイトの origin が入る。中継しても、本物のサイトは「origin が違う」と拒む。
- **鍵はサイトごとに別。**認証器は、偽サイトのドメインに対しては本物のサイトの鍵を使わない（そもそも持っていない）。

人間が見分けなくても、仕組みが見分ける。これが OTP との本質的な違い。

Google は2017年初めに、8万5千人を超える社員にセキュリティキーを義務付けた。2018年には、それ以来フィッシングでアカウントを乗っ取られた社員はいないと公表した。U2F の有効性を示す、よく引かれる実例になった。

ただし U2F は、**別売りのセキュリティキー**と、Chrome などの一部のブラウザの独自の対応が前提だった。一般の利用者にはまだ遠かった。

## 4. Web の標準へ：FIDO2 と WebAuthn（2018年〜2019年）

U2F と UAF の経験をまとめ、Web の標準にしたのが **FIDO2**。2つの規格から成る。

| 規格 | 決めた団体 | 中身 |
| --- | --- | --- |
| **WebAuthn**（Web Authentication） | W3C（2019年3月に勧告） | ブラウザの JavaScript の API（`navigator.credentials.create()` / `get()`）と、サイトとやりとりするデータの形 |
| **CTAP2**（Client to Authenticator Protocol） | FIDO Alliance | ブラウザ（OS）と認証器の間の通信（USB・NFC・BLE） |

これで、プラグインなしに、**すべての主要ブラウザ**で同じ API が使えるようになった。もう1つの大きな変化は、認証器の種類が広がったこと。

- **ローミング認証器**：持ち運ぶセキュリティキー（YubiKey など）
- **プラットフォーム認証器**：端末に内蔵されたもの。Windows Hello、Mac の Touch ID、Android の指紋。秘密鍵は端末の安全な領域（TPM、Secure Enclave）に入る

端末で指紋や PIN を確かめてから鍵を使う（**ユーザー検証**）ので、FIDO2 の認証器1つで「所持 + 生体（か知識）」の多要素になる。UAF が目指した「パスワードなし」が、Web の標準の上で可能になった。

## 5. 残った不満：鍵が端末から出られない

FIDO2 の秘密鍵は、端末から取り出せない。安全性の要だが、利用者から見ると困ったことになる。

- スマホを機種変更したら、全サイトで鍵を登録し直す
- 端末をなくしたら、そのサイトに入れなくなる。予備の鍵を複数登録しておくのが推奨されたが、ほとんどの人はやらない
- 結局、回復の手段としてパスワードやメールを残すことになり、そこが一番弱い入口になる

パスワードの来歴で見た「導入しやすさ」の壁に、ここでも阻まれた。2010年代の終わりまで、一般の利用者が FIDO2 で日常的にログインする光景は、ほとんどなかった。

## 6. パスキー：鍵を同期する（2022年〜）

2022年5月、Apple・Google・Microsoft が共同で、FIDO の資格情報を端末の間で同期できるようにすると発表した。これが**パスキー**。

| 年 | 出来事 |
| --- | --- |
| 2022年9月 | Apple が iOS 16 で、iCloud キーチェーンで同期されるパスキーを提供 |
| 2022年〜2023年 | Google が Android と Chrome で対応（Google パスワードマネージャーで同期）。2023年10月、Google アカウントのログインで、パスキーを既定の方式にした |
| 2023年〜 | 1Password などのパスワードマネージャーも、パスキーを保存・同期できるようになった |
| 2024年 | NIST が SP 800-63B の補足を出し、同期されるパスキーを AAL2（多要素の水準）として認めた |

パスキーで変わったことは3つある。

- **同期**：秘密鍵が、端末の間でエンドツーエンドの暗号化をかけて同期される。機種変更しても、なくしても、同じ Apple ID・Google アカウントの別の端末で使える。
- **ユーザー名を入れなくてよい**（discoverable credential）：認証器が「このサイトの鍵」を自分で覚えているので、ログイン画面で利用者の一覧から選ぶだけ。
- **別の端末のスマホで入れる**（hybrid）：パソコンの画面の QR をスマホで読み、Bluetooth で近くにいることを確かめて、スマホの鍵で署名する。パソコンにパスキーがなくても入れる。

そのかわり、**秘密鍵が1台の端末の中にとどまる**という FIDO の元の強さは、少し緩んだ。鍵の安全は、クラウドのアカウント（Apple ID、Google アカウント）の安全に依存する。そのため、最高水準（AAL3、取り出せないハードウェアの鍵）を求める場面では、今も同期しないセキュリティキーが使われる。**導入しやすさと引き換えに、強さを一段だけ譲った**選択と言える。

## 7. なぜ広がったか

- **OS とブラウザの3社がそろって乗った。**利用者は何も買わず、何も入れなくてよい。
- **使い心地が、スマホのロック解除と同じ。**指紋か顔で終わる。パスワードを覚える必要も、6桁を写す必要もない。
- **フィッシングに強い。**仕組みでサイトを見分けるので、利用者の注意力に頼らない。
- **サーバーが秘密を持たない。**DB が漏れても、漏れるのは公開鍵だけ。パスワードのハッシュや TOTP の秘密のように、攻撃者が使えるものがない。
- **規格が公開で、サーバー側の実装は小さい。**challenge を作り、署名を検証するだけ。

パスワードの来歴で「導入しやすさでパスワードに勝る方式はなかった」と書いた。パスキーは、端末とクラウドの同期を OS が引き受けることで、その壁を初めて本格的に越えつつある方式と位置づけられる。

## 8. まとめ

| | |
| --- | --- |
| 生まれた理由 | パスワードも OTP も、偽サイトに入力させて中継されると防げない（人間がサイトを見分けられない）。サーバーが秘密を持つ |
| 思想 | 人間ではなく、仕組みにサイトを見分けさせる。サイトごとに鍵ペアを作り、サーバーには公開鍵だけを置く |
| 解消した不満 | フィッシング（origin を署名に入れる、鍵がサイトごと）。サーバーからの秘密の漏洩。CA や名簿が要る従来の公開鍵の認証の重さ |
| 普及した理由 | Web の標準の API（WebAuthn）、端末に内蔵の認証器、そしてパスキーの同期（OS とクラウドが鍵の持ち運びを引き受けた） |
| 残った弱点 | 同期により、鍵の安全がクラウドのアカウントに依存する。端末を全部なくしたときの回復は、結局ほかの方式に頼る |
| 今の形 | WebAuthn。discoverable（ユーザー名なし）、ユーザー検証あり、attestation なし。サーバーは challenge・origin・RP ID・署名・カウンタを確かめる |

段3の実装は、表の最後の行をなぞる。サーバーがやることは、challenge を作って渡し、返ってきた署名を、登録のときに預かった公開鍵で検証すること。
